1. 냠냠플래닛가장 많이 물어볼 프로젝트

기간
2026.04.17 – 2026.05.31 (약 1.5개월)
형태
팀 프로젝트 · 국비 과정 수료작
내 역할
AI 기능 개발 · 프론트-백엔드 연동
기술
Java, Spring Boot, React, Axios, KNN, MediaPipe
이 프로젝트가 뭔가요?
🧒 쉬운 설명

키·몸무게·목표를 입력하면 오늘 뭘 먹을지 한 끼를 짜주는 사이트예요. 그리고 웹캠을 켜면 운동 자세가 맞는지 봐주는 기능도 있어요.

💼 면접 답변

사용자의 신체 정보와 목표 데이터를 입력받아 AI가 맞춤 식단을 구성해주고, 웹캠 영상으로 운동 자세를 실시간 분석해 피드백하는 식단·운동 관리 웹 서비스입니다. 저는 이 중 AI 식단 추천 알고리즘과 자세 분석 기능, 그리고 프론트엔드와 백엔드를 연결하는 API 연동을 담당했습니다.

KNN이 뭔가요? 왜 썼나요?
🧒 쉬운 설명

KNN은 "나랑 제일 비슷한 애들 몇 개를 찾아줘" 하는 방법이에요.

예를 들어 600칼로리짜리 메뉴가 필요하면, 음식 목록에서 600에 제일 가까운 것들을 골라옵니다. 키 재서 줄 세워놓고 "내 키랑 제일 비슷한 사람 5명 데려와" 하는 것과 같아요.

💼 면접 답변

KNN(K-Nearest Neighbors)은 입력값과 거리가 가장 가까운 K개의 데이터를 찾아내는 알고리즘입니다. 식단 추천은 "사용자의 목표 칼로리와 가장 가까운 음식을 찾는" 문제로 볼 수 있어서, 복잡한 학습 없이 바로 적용할 수 있다는 점 때문에 처음에 KNN을 선택했습니다.

다만 실제로 적용해보니 칼로리라는 한 가지 기준만으로는 쓸 만한 결과가 나오지 않는다는 한계를 확인했고, 그 부분을 개선한 것이 이 프로젝트에서 제일 중요한 작업이었습니다.

어떤 문제가 있었고 어떻게 해결했나요? — 가장 중요
🧒 쉬운 설명

문제: 칼로리 숫자만 맞추다 보니, 추천 결과에 케첩이나 생고기 같은 게 "한 끼"로 나왔어요. 칼로리는 맞는데 그걸 그냥 먹을 수는 없잖아요.

왜 그랬냐면: 컴퓨터한테 "칼로리만 맞춰" 라고 시켰기 때문이에요. 밥인지 반찬인지, 조리를 한 건지 안 한 건지는 알려주지 않았어요.

어떻게 고쳤냐면: 음식마다 붙어 있는 '분류명'(밥 / 국 / 메인 / 반찬)을 조건으로 추가했어요. 그리고 "밥 150g, 국 200g…" 처럼 양까지 자동으로 나눠서 계산하게 했어요.

결과: 밥 + 국 + 메인 + 반찬이 갖춰진 한 상이 나오게 됐어요.

💼 면접 답변

[문제] KNN으로 목표 칼로리에 맞춰 추천했더니, 소스나 조리되지 않은 재료가 한 끼 식단으로 반환되는 문제가 있었습니다.

[원인] 추천 기준이 칼로리 수치 하나뿐이어서, 음식의 역할이나 조리 여부가 전혀 반영되지 않았기 때문입니다. 수치상 정확도는 높았지만 결과물이 실제로 쓸모가 없는 상태였습니다.

[해결] 데이터에 있는 '분류명' 속성을 활용한 카테고리 필터링을 추가해 밥·국·메인·반찬이 각각 선택되도록 했고, 여기에 목표 칼로리에 맞춰 메뉴별 섭취량(g)을 자동으로 계산해 분배하고 DB에 동적으로 매핑하는 로직을 더해 하이브리드 추천 구조로 재설계했습니다.

[결과] 정식 형태의 한 끼가 출력되도록 추천 품질을 개선했습니다. 이 경험을 통해 알고리즘의 수치 정확도보다 결과가 실제로 쓸모 있는지를 먼저 확인해야 한다는 것을 배웠습니다.

MediaPipe 자세 분석은 어떻게 만들었나요?
🧒 쉬운 설명

MediaPipe는 구글이 만든 "사람 몸에 점 찍어주는 도구"예요. 카메라에 사람이 보이면 어깨·팔꿈치·무릎 같은 곳에 점을 찍고 좌표를 알려줍니다. 그 점들이 어디 있는지 보면 자세가 맞는지 알 수 있어요.

문제가 생긴 부분: 카메라는 1초에 30번 화면을 보내요. 그때마다 화면을 전부 새로 그리게 했더니 컴퓨터가 버거워서 뚝뚝 끊길 위험이 있었어요.

해결: 바뀐 부분만 다시 그리도록 정리해서 끊김 없이 움직이게 했어요.

💼 면접 답변

MediaPipe는 영상에서 사람의 관절 좌표(랜드마크)를 추출해주는 구글의 비전 라이브러리입니다. 웹캠 스트림에서 실시간으로 관절 좌표를 받아와 자세를 분석하고, 화면에 피드백하는 기능을 구현했습니다.

[문제] 초당 수십 프레임의 분석 결과가 들어오는데, 이를 그대로 상태에 반영하면 불필요한 리렌더링이 연쇄적으로 발생해 렌더링 지연과 브라우저 과부하가 생길 수 있었습니다.

[해결] 프레임 단위의 상태 관리를 최적화해 꼭 필요한 변화만 화면에 반영되도록 바꾸고, 데이터 처리 파이프라인을 정리했습니다. 분석 결과값은 백엔드 서버로 안정적으로 동기화되도록 연동했습니다.

[결과] 실시간 스트리밍 환경에서도 끊김 없는 자세 피드백을 구현했고, 프론트엔드–백엔드–AI 비전이 하나의 흐름으로 이어지는 구조를 경험했습니다.

API 연동은 뭘 하신 건가요?
🧒 쉬운 설명

웹사이트는 겉모습(화면)과 속(데이터 보관소)이 따로 있어요.

화면이 "이 사람 식단 좀 줘" 하고 물으면, 속에서 "여기 있어" 하고 보내줘야 해요. 이 주고받는 창구를 만드는 일이 API 연동이에요. 저는 그 창구를 3개 만들었어요.

💼 면접 답변

React 프론트엔드와 Spring Boot 백엔드 사이에서 Axios를 사용해 RESTful API 엔드포인트 3개를 설계하고 연동했습니다. 사용자의 신체 정보와 목표 데이터를 받아 가공한 뒤 추천 로직에 전달하고, 그 결과를 화면으로 되돌려주는 데이터 흐름 전체를 설계한 것이 제 역할이었습니다.

2. 1분호기심 — 유튜브 자동화차별화 포인트

기간
2026.08 ~ 운영 중
형태
개인 프로젝트 (1인)
성과
매일 2편 무인 발행 · 누적 50편+ · 일평균 조회 2,175회
기술
Python, Claude Code(헤드리스), YouTube Data API v3, ffmpeg, edge-tts
이게 뭐 하는 프로그램인가요?
🧒 쉬운 설명

제가 아무것도 안 해도 유튜브에 매일 영상 2개가 올라가는 프로그램이에요.

컴퓨터가 알아서 ① 요즘 뭐가 인기인지 찾아보고 → ② 대본을 쓰고 → ③ 목소리를 입히고 → ④ 자막과 그림을 붙여 영상을 만들고 → ⑤ 유튜브에 올리고 → ⑥ 일주일 뒤에 "이번 주 잘됐나?" 스스로 점검까지 해요.

💼 면접 답변

트렌드 수집 → AI 대본 생성 → 내레이션·자막·영상 렌더링 → 업로드 → 성과 수집 → 주간 회고까지 전 과정을 사람 개입 없이 수행하는 자동화 파이프라인입니다. Windows 작업 스케줄러로 매일 정해진 시각에 실행되며, 현재 약 두 달째 무인 운영 중입니다. 단순 자동 실행이 아니라 성과 데이터를 수집해 다음 주 전략을 스스로 수정하는 회고 루프를 넣은 것이 핵심입니다.

AI가 만든 결과물의 품질은 어떻게 관리했나요?
🧒 쉬운 설명

AI한테 그냥 맡기면 매번 제멋대로 써요. 그래서 규칙을 코드로 박아뒀어요.

  • 아침 영상과 저녁 영상의 형식을 다르게 고정
  • 어제랑 같은 종류는 못 올리게 막기
  • 완성된 대본에 위험한 단어(의료 관련)가 있나 자동 검사 → 있으면 다시 쓰게 하고, 또 걸리면 미리 준비해둔 예비 대본으로 교체

그래서 제가 안 보고 있어도 이상한 영상이 올라간 적이 한 번도 없어요.

💼 면접 답변

LLM 출력은 편차가 크기 때문에 검증을 코드 레벨에서 강제했습니다. 시간대별 포맷을 슬롯으로 고정하고, 카테고리 분류와 연속 중복 금지를 규칙으로 구현했습니다. 생성된 대본은 의료 표현·모호한 제목을 정규식으로 사후 검사해 위반 시 1회 자동 재생성하고, 재차 위반하면 상시 보유 중인 예비 대본으로 대체하도록 했습니다. 그 결과 무인 운영 상태에서 정책 위반 발행 0건을 유지하고 있습니다.

가장 기억에 남는 트러블슈팅은? — 꼭 준비
🧒 쉬운 설명

상황: 프로그램이 "조회수가 76% 폭락했어요!" 하고 알려줬어요. 전략을 다 뒤엎을 뻔했어요.

알고 보니: 유튜브에서 조회수를 가져올 때 최근 50개만 가져오고 있었어요. 영상이 50개를 넘어가니까 앞쪽만 세고 뒤는 안 센 거예요. 그래서 숫자가 줄어든 것처럼 보였어요.

고친 방법: 전부 가져오게 바꾸고, 합계 대신 "하루 평균"과 "몇 개를 셌는지"를 같이 적게 했어요.

진짜 결과: 폭락이 아니라 44% 오르는 중이었어요. 전략을 안 버리길 잘했죠.

💼 면접 답변

[문제] 주간 회고 리포트가 조회수 76% 급락으로 진단해, 정상 작동하던 전략을 폐기할 뻔했습니다.

[원인] 통계 수집 함수가 YouTube API의 기본 페이지네이션(한 번에 최대 50건)에 걸려, 영상이 50편을 넘어간 시점부터 잘린 표본으로 합계를 산출하고 있었습니다.

[해결] 영상 목록을 전체 페이지네이션으로 순회하도록 수정하고, 지표 산출 방식을 합계 대신 일별 데이터 + 중앙값 + 표본 수 병기로 바꿨습니다.

[결과] 실제 추세는 44% 회복이었음을 확인하고 전략 폐기를 철회했습니다. 지표를 만드는 코드가 틀리면 그 위의 모든 의사결정이 함께 틀어진다는 것을 배웠고, 이후 모든 리포트에 표본 수를 함께 기록하도록 규칙화했습니다.

무인 운영에서 겪은 다른 문제는요?
🧒 쉬운 설명

증상: 내가 직접 실행하면 잘 되는데, 예약 실행만 하면 자꾸 실패했어요. 어떤 날은 이틀 전 옛날 코드가 돌아가기도 했고요.

원인 2가지

  • 파일을 클라우드 폴더에 뒀더니, 클라우드가 파일을 인터넷으로 치워버려서 컴퓨터에 실제 파일이 없었어요.
  • 실행 파일 안에 한글을 적었더니 글자가 깨지면서 명령어 구조가 무너졌어요.

해결: 파일을 클라우드 밖으로 옮기고, 실행 파일은 영어만 쓰기로 정했어요. 그 뒤로 한 번도 안 터졌어요.

💼 면접 답변

[문제] 수동 실행은 정상인데 스케줄러 실행만 오류 코드 9009로 실패하고, 간헐적으로 구버전 코드가 실행됐습니다.

[원인] ① 클라우드 동기화가 실행 파일을 온라인 전용 상태로 전환해 로컬에 실체가 없었고, 수정 반영도 지연됐습니다. ② 배치 스크립트 내부의 한글이 CP949로 해석되며 깨져 조건문 구조가 무너졌습니다.

[해결] 운영 코드를 동기화 폴더 밖 로컬 경로로 이전하고, 배치·PowerShell 스크립트는 ASCII로만 작성한다는 규칙을 세워 한글 알림은 별도 모듈이 담당하도록 분리했습니다. 추가로 실패 시 휴대폰 푸시 알림을 붙여 무인 상태에서도 장애를 즉시 인지하도록 했습니다.

[결과] 동일 원인의 실행 실패가 재발하지 않았습니다. "로컬에서 되는 것"과 "무인 환경에서 되는 것"은 다르다는 걸 배운 사례입니다.

3. 집가(ZipGa) — 마케팅 자동화

기간
2026.08 ~ 운영 중
형태
6인 팀 프로젝트 · 마케팅 자동화 단독 담당
기술
Python, ComfyUI(로컬 GPU), ffmpeg, YouTube·Meta Graph·Threads API
무엇을 담당했나요?
🧒 쉬운 설명

팀이 앱을 만들었으면 홍보를 해야 하잖아요. 그 홍보를 혼자서 자동으로 돌렸어요.

영상을 폴더에 넣고 버튼을 누르면 유튜브·인스타·쓰레드·블로그 등 5군데에 한 번에 올라가요. 홍보 문구도 채널마다 알아서 다르게 만들어줘요.

💼 면접 답변

팀 서비스의 출시 마케팅을 자동화했습니다. 영상 정규화 → 전사 → 9:16 클립 생성 → 채널별 문구 생성 → 유입 링크 → 발행 큐를 6단계 파이프라인으로 모듈화하고, 5개 채널에 원클릭으로 발행하는 업로더를 구현했습니다. 각 플랫폼의 공식 API(YouTube Data, Meta Graph, Threads 등)를 직접 연동했습니다.

설계에서 신경 쓴 점이 있다면?

문제를 해결한 경험이 있나요?
🧒 쉬운 설명

영상 만드는 프로그램이 자꾸 알 수 없는 오류를 뱉었어요. 그래픽카드 문제인 줄 알았죠.

그런데 찾아보니 진짜 원인은 메모리(RAM) 부족이었어요. 20GB짜리 큰 파일을 읽는 중에 다른 프로그램들이 메모리를 차지하고 있었던 거예요.

해결: 영상 만들기 전에 무거운 프로그램을 끄도록 정하고, 실패하면 30초 뒤 3번까지 다시 시도하게 했어요.

💼 면접 답변

로컬 GPU 영상 생성이 간헐적으로 실패했는데, 표면 오류 메시지만 보면 GPU 문제로 보였습니다. 로그를 따라가 보니 실제 원인은 윈도우의 시스템 리소스 부족 오류였고, 약 20GB 모델을 메모리에 스트리밍 로드하는 동안 다른 프로세스가 메모리를 점유한 것이 원인이었습니다. 생성 전 무거운 프로세스를 종료하는 절차를 넣고, 기동 직후 실패에 대비해 30초 간격 3회 자동 재시도를 추가해 해결했습니다. 표면 오류가 아니라 OS 레벨까지 원인을 추적해야 한다는 것을 배운 사례입니다.

재밌는 일: 매주 점검하는 기능이 "지금 설정은 벌어도 본전이에요" 라고 알려줬어요. 이익이 1.5% 나면 1.5% 떨어질 때 파는 설정이라 남는 게 없는 구조였던 거예요. 그래서 바꿨어요.

① 모르는 건 모른다고 하세요. 아는 척하다 꼬리 질문에 막히는 게 훨씬 치명적입니다. "거기까지는 아직 다뤄보지 못했습니다. 다만 비슷하게 ○○는 해봤습니다" 가 가장 안전한 답입니다.
