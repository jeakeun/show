## 1. 기준선 기록 (읽기만, 코드 변경 없음)

지금 회고가 어떻게 도는지 파악해 기록한다. 이게 나중에 비교할 기준선이다.
- 입력 데이터: 조회수 스냅샷, 10분 샘플, 슬롯 기록, Analytics 트래픽 소스, 벤치마크, 궁금증 후보, 가설 채점(`hypocheck`), 비용
- 호출 구조: 회고 모델·팩트체크 모델, `_create()` 헬퍼(스트리밍, `stop_reason` 확인), max_tokens·effort 설정
- 출력: 리포트, `playbook_proposed`, 검증 노트, 자동 적용 경로
- **최근 4주 기준선 숫자**
  - 회고 1회 비용과 걸린 시간
  - 팩트체크가 삭제하거나 표시한 주장 수
  - 실패 여부
  - 회고가 낸 가설 수와 다음 주 채점 결과

결과를 `show/docs/멀티에이전트/회고-멀티에이전트/01-기준선.md` 에 쓴다. 숫자는 로그·기록에서 온 것만 쓰고, 없으면 "기록 없음"이라고 쓴다.

## 2. 설계안 먼저 (코드 전에, 사용자 확인 받기)

아래는 출발점이다. 실제 데이터 구조를 보고 고친다.

```
[지휘자] 이번 주 볼 것을 정함 (데이터 요약만 보고)
   ├─ [조회수·유입 분석가]     공유 DB·Analytics (읽기)
   ├─ [댓글·궁금증 분석가]     curiosity 결과 (읽기)
   ├─ [경쟁 채널 분석가]       벤치마크 (읽기)
   └─ [지난 가설 채점]         코드 (hypocheck 결과를 그대로)
          ↓ Send로 병렬, 전부 읽기 전용. 각자 "요약 + 근거 숫자"만 돌려줌
[회고 작성자 1명]  리포트 + 플레이북 초안 (주장마다 근거 표시)
          ↓
[팩트체커]  근거 없는 주장·표본 부족·과대 목표를 지적만 함
          ↓ 조건부 엣지: 문제 있으면 작성자에게 1회 되돌림, 2번째면 지적을 표시한 채 저장
[저장]  그림자 전용 폴더에만 씀
```

설계 원칙 (이유를 설계안에 한 줄씩 적는다):
- **읽기는 나누고 쓰기는 한 곳**: 분석가는 읽기만 하고, 쓰는 건 작성자 한 명이다.
  기존 팩트체크는 결과를 직접 고치는 "두 번째 작성자"였다. 새 구조에서는 지적만 하고 작성자가 고치게 바꾼다. 두 방식을 비교하는 것도 이번 학습 포인트다.
- **숫자는 코드가** (ADR-04): 분석가에게 원자료 대신 코드가 계산한 숫자를 준다. 분석가는 해석만 한다.
- **LangGraph는 흐름 관리에만 쓴다.** 모델 호출은 검증된 기존 코드(`_create()` 등)를 노드 안에서 재사용하는 것을 먼저 검토한다.
  LangChain 모델 래퍼가 지금 쓰는 기능(프롬프트 캐싱, effort 설정, 사고 토큰을 포함한 max_tokens)을 그대로 지원하는지 확인한 뒤 고른다. 고른 이유를 기록한다.
- **max_tokens 교훈**: 사고 토큰이 한도에 포함된다. 9/13 실패를 반복하지 않는다.
- **역할별 모델** (ADR-08): 분석가는 저렴한 모델, 작성자는 지금 회고 모델과 같게 둔다. 그래야 "구조 차이"만 비교할 수 있다.

설계안을 `회고-멀티에이전트/02-설계.md` 에 쓰고, **사용자에게 쉬운 말로 설명한 뒤 확인을 받고** 구현에 들어간다.

## 3. 구현 (브랜치 작업 규칙 준수)

```
bash tools/gitwork.sh start yt-auto retro-graph      # D:\wt\yt-auto-retro-graph 에서 작업
```

- 새 모듈 예시: `src/retro_graph/` (그래프 정의, 노드, 상태). 기존 `insights.py` 는 데이터 수집 함수를 **가져다 쓰기만** 하고 동작을 바꾸지 않는다.
- **별도 가상환경**: langgraph·langchain 계열은 운영 `.venv` 에 설치하지 않는다. 예: `D:\yt-auto-graph-venv`. 버전을 고정한다.
- **출력은 그림자 전용 폴더만**: `data/shadow_retro/YYYY-MM-DD/` (리포트, 플레이북 초안, 지표 JSON, 단계별 실행 기록).
- **보호 확인 테스트**: 실행 전후에 `playbook.md`, `playbook_proposed.md`, 프롬프트 파일, `config.json` 해시가 같은지 검사한다. 다르면 실패 처리하고 원복한다.
- **비용 상한**: 1회 실행 비용이 기준선 회고 비용의 3배를 넘으면 중단하고 알린다. 첫 실행 비용은 반드시 보고한다.
- **오프라인 시험**: 지난주 데이터로 한 번 돌려 지난주 실제 회고와 나란히 비교한다. 결과를 사용자에게 보여준다.
- `gitwork.sh finish` 전에 사용자에게 요약을 보고한다.

## 4. 그림자 운영 등록 (3주)

- 예약 시간: 기존 회고·hub 적재가 끝난 뒤. 예) **월요일 01:10**. 다른 예약 작업과 겹치지 않게 확인한다.
- `.bat` / `.vbs` 는 ASCII만 쓰고, 기존과 같은 숨김 실행 방식으로 한다.
- 실패하면 ntfy 푸시("Shadow retro FAILED")와 바탕화면 경고 파일을 남긴다. 성공 판정은 결과 파일 실존과 종료 코드로 한다 (ADR-09).
- **새 회고 결과는 대본에 절대 반영하지 않는다.** 비교용이다.
