# RAG — 청킹 · 임베딩 · 벡터 검색

> 목표 공고 우대사항: "RAG 구성 경험 (Chunking, Embedding, Vector 검색 등 포함)"
> 이 문서의 실험은 2026-10-22에 실제로 돌린 결과입니다 ([예제/05_rag_chunking.py](예제/05_rag_chunking.py)).

## 1. RAG란

**질문이 오면 관련 문서를 먼저 찾아서(Retrieval), 그 내용을 AI에게 같이 주고(Augmented), 답하게 하는(Generation) 방식**입니다.

- AI가 학습하지 않은 사내 문서나 최신 정보로 답할 수 있습니다.
- 답에 출처를 붙일 수 있어서 검증이 됩니다.
- 문서가 바뀌면 다시 색인만 하면 됩니다. 모델을 다시 학습시킬 필요가 없습니다.

| 방법 | 언제 맞나 |
|---|---|
| **문서를 통째로 프롬프트에 넣기** | 문서가 적을 때 (수십 쪽). 오히려 RAG보다 정확하고 단순함 |
| **RAG** | 문서가 많을 때 (수천 쪽 이상), 자주 바뀔 때, 출처가 필요할 때 |
| **파인튜닝** | 지식 주입이 아니라 말투·형식·특정 작업 방식을 가르칠 때 |

면접 포인트: "무조건 RAG"가 아니라 **문서 양과 변경 빈도로 고른다**고 말할 수 있어야 합니다.

## 2. 전체 흐름

```
[미리 해두기: 색인]
문서 불러오기 → 자르기(청킹) → 숫자로 바꾸기(임베딩) → 벡터 DB에 저장
                     ↑ 출처·제목·날짜 같은 메타데이터도 함께 저장

[질문이 올 때: 검색 + 답변]
질문 → 질문도 임베딩 → 비슷한 조각 k개 찾기 → (재정렬) → 조각을 프롬프트에 넣고 답변 + 출처 표시
```

## 3. 청킹 (자르기)

**왜 자르나**
- 임베딩 모델은 한 번에 넣을 수 있는 길이에 한도가 있습니다.
- 한 덩어리에 주제가 여러 개 섞이면 검색이 흐려집니다.
- 프롬프트에 넣는 양이 곧 비용입니다.

**자르는 방법**

| 방법 | 어떻게 | 장단점 |
|---|---|---|
| 고정 길이 | N글자마다 자름 | 단순. 문장·표 중간이 잘림 |
| 재귀 분할 | 문단 → 줄 → 문장 → 글자 순으로 경계를 존중하며 자름 (`RecursiveCharacterTextSplitter`) | 기본값으로 무난 |
| 문서 구조 기준 | 마크다운 제목, HTML 태그, 코드 함수 단위로 자름 (`MarkdownHeaderTextSplitter`) | 의미 단위가 보존됨. 구조가 있는 문서에 최적 |
| 의미 기반 | 문장끼리 임베딩 유사도가 뚝 떨어지는 곳에서 자름 | 구조 없는 긴 글에 유리. 계산 비용 큼 |

**크기와 겹침(overlap)**
- 너무 작으면 맥락이 부족하고, 너무 크면 주제가 섞입니다.
- 겹침은 경계에서 잘린 문장을 앞뒤 조각이 함께 갖게 해줍니다.
- **정답 크기는 없고 평가셋으로 비교해서 정합니다.** 면접에서 "청크 크기 어떻게 정했어요?"에 대한 좋은 답입니다.

**메타데이터**: 출처 파일, 섹션 제목, 날짜, 권한을 조각에 붙입니다. 출처 표시와 필터 검색(날짜·부서·권한)에 씁니다.

대상: [02-내-설계결정-기록.md](02-내-설계결정-기록.md) (ADR 10개, 2026-10-22 판. 문서가 바뀌면 조각 수도 바뀝니다)

| 자르는 방법 | 조각 수 | 조각에 붙은 정보 |
|---|---|---|
| 글자 수로만 (500자, 겹침 50) | 41 | 없음. 어느 ADR인지 모름 |
| 제목 기준 | 13 | `h2: ADR-01. 만드는 AI와…` |
| 제목 기준 + 500자 | 31 | 제목 정보 유지 |

글자 수로만 자르면 표가 중간에 잘리고, 조각만 봐서는 어느 결정에 대한 내용인지 알 수 없습니다.

## 4. 임베딩

**뜻**: 문장을 의미를 담은 숫자 목록(벡터)으로 바꾸는 것. 뜻이 비슷하면 숫자도 가깝습니다.
"환불 규정"과 "돈 돌려받는 방법"은 단어가 달라도 가까운 벡터가 됩니다.

**고르는 기준**
- **한국어 성능**: 다국어 모델인지, 한국어 평가 결과가 있는지
- **비용과 위치**: API형(호출마다 요금, 문서가 외부로 나감)과 로컬형(무료, 내 GPU 필요, 문서가 밖으로 안 나감)
- **최대 입력 길이**, **벡터 크기**(저장 공간)
- **문서와 질문은 같은 모델로** 임베딩해야 합니다. 모델을 바꾸면 전부 다시 색인합니다.

**선택지 예**
- API형: OpenAI 임베딩, Voyage AI, Upstage(국내) 등.
  앤트로픽은 자체 임베딩 모델이 없고, 문서에서 Voyage AI를 안내합니다.
- 로컬형: BAAI `bge-m3`, `multilingual-e5` 계열처럼 한국어를 포함한 다국어 모델. 메인 PC(RTX 4080)에서 무료로 돌릴 수 있습니다.

### 내 실험 2 — 가짜 임베딩으로 검색하면

질문 "사람 승인은 어디에 두나"의 정답은 ADR-07입니다.
뜻을 담지 않은 시험용 가짜 임베딩으로 검색했더니 1등이 **ADR-06(감사)** 이었습니다.
흐름(자르기 → 임베딩 → 검색)이 똑같아도 **임베딩 품질이 검색 품질을 결정**한다는 걸 보여줍니다.

## 5. 벡터 검색

**유사도**: 보통 코사인 유사도를 씁니다. 두 벡터의 방향이 얼마나 같은지 봅니다.

**벡터 저장소**

| 종류 | 예 | 언제 |
|---|---|---|
| 시험용 메모리 | `InMemoryVectorStore` | 학습·테스트 |
| 로컬 라이브러리 | FAISS | 서버 없이 빠르게 |
| 로컬 DB | Chroma | 작은 서비스 |
| 기존 DB 확장 | PostgreSQL + pgvector | **이미 Postgres를 쓰는 회사.** 레거시 DB 옆에 붙이기 좋음 |
| 전용 벡터 DB | Qdrant, Milvus, Pinecone 등 | 데이터가 많고 검색이 핵심일 때 |

고르는 기준은 데이터 양, 회사가 이미 쓰는 인프라, 필터 기능, 운영 부담입니다.

**검색을 더 좋게 만드는 기법**

| 기법 | 내용 |
|---|---|
| **하이브리드 검색** | 벡터(의미) + 키워드(BM25, 정확한 단어). 사내 문서는 제품 코드·약어·고유명사가 많아 키워드가 중요 |
| **재정렬 (reranker)** | 넓게 20~50개를 뽑고, 더 정확한 모델로 다시 순위를 매겨 상위만 사용 |
| **MMR** | 비슷한 조각만 반복해서 뽑히지 않게 다양성을 줌 |
| **메타데이터 필터** | 날짜, 부서, **권한**으로 먼저 거름 |
| **질문 재작성** | 대화 맥락을 반영해 검색에 맞는 질문으로 바꿈 |
| **조각에 맥락 붙이기** | 조각 본문 앞에 문서·섹션 제목을 붙여 색인 (아래 실험 3) |

### 내 실험 3 — 제목이 검색에 안 쓰이고 있었다

키워드 검색(BM25, 한국어는 두 글자씩 겹쳐 잘라 비교)을 써봤습니다.

| 색인 방식 | 상위 3개 | 정답(ADR-07) |
|---|---|---|
| 제목을 메타데이터로만 저장 | ADR-03, 한눈에 보기, ADR-10 | ❌ 없음 |
| **제목을 본문 앞에 붙여 저장** | **ADR-07**, ADR-03, ADR-07 | ✅ 1등 |

원인은 제목 기준 분할기가 제목을 본문에서 빼서 메타데이터로만 옮긴다는 데 있었습니다.
ADR-07의 제목 "사람 승인 위치는…"이 검색 대상 본문에 없었던 겁니다.

- **교훈**: 메타데이터는 필터와 출처 표시용이고, 검색에 쓰려면 본문에 넣어야 합니다.
- **한계**: 질문 하나로 한 실험입니다. 일반화하려면 평가셋으로 확인해야 합니다 (7절).

## 6. 에이전트형 RAG

| | 기본 RAG | 에이전트형 RAG |
|---|---|---|
| 검색 | 질문마다 항상 1번 | 검색을 **도구**로 줌. 할지, 무엇으로 할지, 다시 할지를 AI가 결정 |
| 흐름 | 고정 | 검색 → 관련성 채점 → 부족하면 질문 바꿔 재검색 → 답변 → 근거 검사 |
| 구현 | 체인 하나 | LangGraph 갈림길과 반복 |

멀티 에이전트와 연결하면:
- 검색은 **읽기**라 여러 출처를 병렬로 뒤져도 안전합니다. 예를 들어 문서 검색과 DB 조회를 동시에 할 수 있습니다.
- 답변 **쓰기**는 작성자 하나가 합니다.
- 검수 AI가 "답의 모든 문장이 검색된 근거에 있는가"를 검사합니다. ADR-01·05의 원칙을 그대로 씁니다.

**내 경험과 연결**: 클로드 메모리는 `MEMORY.md` 색인을 먼저 보고 필요한 파일만 열어 읽습니다.
**벡터 없이 하는 "색인 기반 검색"** 인 셈입니다. 문서가 적고 사람이 색인을 관리할 수 있으면 이게 더 정확하고 저렴합니다.
문서가 수천 개로 늘거나 질문이 예측 불가능해지면 벡터 검색이 필요해집니다.

## 7. 평가

| 무엇을 | 어떻게 |
|---|---|
| **검색** | 정답 조각이 상위 k개 안에 들어온 비율, 정답이 몇 등에 나왔는지 |
| **답변** | 근거 충실도(답이 검색된 내용에만 근거하나), 질문과의 관련성, 정답 일치 |
| **운영** | 응답 시간, 질문당 비용 |

방법은 이렇습니다.
1. 질문, 정답, 정답이 있는 문서 위치를 30~50개 묶은 **평가셋을 먼저** 만듭니다.
2. 청킹 크기, 임베딩 모델, k값, 하이브리드 여부를 하나씩 바꿔가며 숫자를 비교합니다.

RAGAS나 LangSmith 평가 기능 같은 도구가 있습니다.

## 8. 자주 나는 실패

| 증상 | 원인 | 처방 |
|---|---|---|
| 엉뚱한 문서를 찾음 | 임베딩 모델이 안 맞음, 조각에 주제가 섞임 | 모델 교체, 구조 기준 청킹 |
| 제품 코드·약어를 못 찾음 | 벡터 검색만 씀 | 하이브리드 검색 |
| 섹션 제목으로 물으면 못 찾음 | 제목이 메타데이터에만 있음 | 제목을 본문 앞에 붙여 색인 (실험 3) |
| 검색은 맞는데 답이 틀림 | 근거만 쓰라는 지시가 없음, 조각을 너무 많이 넣음 | 근거 기반 답변 지시, 출처 표시, 검수 AI |
| 표가 깨짐 | 글자 수로 자름 | 표 단위 보존 |
| 옛날 문서가 답에 나옴 | 날짜를 안 봄 | 날짜 필터, 재색인 주기 |
| 권한 없는 문서가 노출됨 | 검색 단계에 권한 필터 없음 | 검색 전에 사용자 권한으로 거름 |

## 9. 알아둘 변화

`langchain-community` 패키지는 지원 종료가 진행 중입니다 (2026-10 설치 시 경고 확인).
경고 문구는 개별 통합 패키지로 옮겨가라고 안내합니다. 새 프로젝트에서는 쓰려는 기능의 개별 패키지가 있는지 먼저 찾습니다.
예제의 BM25 검색기는 학습용으로 이 패키지를 그대로 썼습니다.

## 10. 면접 질문

<details><summary>Q1. RAG가 뭐고 왜 쓰나요? 파인튜닝과 차이는?</summary>

질문과 관련된 문서를 먼저 찾아서 AI에게 같이 주고 답하게 하는 방식입니다. 학습하지 않은 사내 문서로 답하고 출처를 붙일 수 있습니다.
파인튜닝은 지식을 넣기보다 말투나 작업 방식을 가르칠 때 맞고, 문서가 바뀔 때마다 다시 학습해야 합니다.
문서가 적으면 RAG 없이 통째로 넣는 게 더 정확할 수 있어서, 문서 양과 변경 빈도로 고릅니다.
</details>

<details><summary>Q2. 청크 크기는 어떻게 정하나요?</summary>

정답 크기는 없고 평가셋으로 비교해서 정합니다. 출발점은 문서 구조입니다.
제 문서로 해보니 글자 수로만 자르면 41조각인데 어느 섹션 내용인지 정보가 사라졌습니다. 제목 기준으로 자르면 조각마다 섹션 정보가 붙었습니다.
그다음 크기와 겹침을 바꿔가며 정답 조각이 상위에 오는 비율을 비교합니다.
</details>

<details><summary>Q3. 임베딩 모델은 어떻게 고르나요?</summary>

한국어 성능, API형인지 로컬형인지(비용과 데이터 반출), 최대 입력 길이, 벡터 크기를 봅니다.
문서와 질문은 같은 모델로 임베딩해야 해서, 바꾸면 전부 재색인해야 한다는 점도 고려합니다.
사내 문서처럼 밖으로 나가면 안 되는 데이터라면 bge-m3 같은 다국어 로컬 모델을 먼저 검토합니다.
</details>

<details><summary>Q4. 벡터 검색만으로 부족한 경우는?</summary>

제품 코드, 약어, 고유명사처럼 정확한 단어가 중요한 경우입니다. 그래서 키워드 검색(BM25)과 섞는 하이브리드 검색을 쓰고, 상위 후보는 재정렬 모델로 다시 순위를 매깁니다.
제 실험에서는 섹션 제목이 메타데이터에만 있고 본문에 없어서 제목에 있는 말로 물으면 못 찾았습니다. 제목을 본문 앞에 붙이니 정답이 1등으로 올라왔습니다.
</details>

<details><summary>Q5. RAG의 환각은 어떻게 막나요?</summary>

검색된 근거만 쓰라고 지시하고 문장마다 출처를 붙이게 합니다.
그다음 별도 검수 AI가 답의 모든 주장이 근거에 있는지 확인합니다. 제 운영 시스템에서 작성 AI와 검수 AI를 나누고, 회고를 다른 AI가 반박 검증하게 한 것과 같은 원칙입니다.
근거가 없으면 "모른다"고 답하게 하는 것도 중요합니다.
</details>

<details><summary>Q6. 기본 RAG와 에이전트형 RAG의 차이는?</summary>

기본 RAG는 항상 한 번 검색하고 답합니다. 에이전트형은 검색을 도구로 줘서 AI가 검색 여부, 검색어, 재검색을 스스로 결정합니다.
LangGraph로는 검색 → 관련성 채점 → 부족하면 질문을 바꿔 재검색 → 답변 → 근거 검사 흐름을 갈림길과 반복으로 만듭니다.
</details>

<details><summary>Q7. RAG 실무 경험이 있나요? (솔직 버전)</summary>

**지금**: "운영 시스템에는 아직 없습니다. 학습용으로 제 설계 문서에 청킹과 검색을 실험해서, 제목 처리 하나로 검색 결과가 바뀌는 걸 확인했습니다.
다음 프로젝트에서 실제 운영 문서와 데이터를 대상으로 평가셋을 만들고 구현할 계획입니다."

**2단계 후 채울 것**: 평가셋 크기, 비교한 설정, 정답 적중률 숫자.
</details>
