# 1단계 · 기준선 — 지금 주간 회고는 어떻게 도는가

> 작성: 2026-10-22 메인 PC. 코드는 하나도 바꾸지 않고 읽기만 했습니다.
> 숫자는 `D:\yt-auto` 의 로그·기록(`logs/insights.log`, `data/api_usage.csv`, `data/approvals.jsonl`, `reports/*-주간리포트.md`)에서 온 것만 썼습니다.
> 이 문서가 새 멀티 에이전트 회고와 비교할 **기준선**입니다.

## 1. 한 장 요약

```
매일 23:50 run_insights.bat ─ 일요일이 아니면 바로 종료
   │ (일요일만)
   ▼
[데이터 모으기 - 코드]  내 영상 조회수, 벤치마크 채널, 인기 급상승, 일별 추이, 슬롯 기록,
                        유입 경로(Analytics), 슬롯별 유입, 시청자 댓글, 가설 자동 채점, 논문 검토
   ▼
[회고 AI 1명 - Opus 5.5]  위 자료를 한 번에 다 읽고 리포트 + 플레이북을 JSON 하나로 씀 (웹검색 최대 3회)
   ▼
[팩트체크 AI - Haiku 4.5]  리포트·플레이북을 "직접 고쳐서" 돌려줌 (두 번째 작성자)
   ▼
[저장·적용 - 코드]  리포트 저장 → 플레이북 제안본 → auto_approve 로 바로 적용 → 폰 알림
   ▼
(이어서 00:00 무렵 프롬프트 감사가 따로 돈다 - 이번 비교 범위 밖)
```

## 2. 입력 데이터 (모두 코드가 모아서 글로 붙임)

| 자료 | 어디서 | 코드 |
|---|---|---|
| 내 영상 목록 (조회·좋아요·댓글·길이) | 유튜브 Data API | `fetch_video_stats()` |
| 벤치마크 채널 영상 + 인기 댓글 | 유튜브 검색 3개 키워드 | `fetch_benchmark()` |
| 인기 급상승 제목 | 유튜브 API | `fetch_trending_titles()` |
| 일별 채널 추이 + 영상별 하루 증가 상위 15 | `data/stats_daily.jsonl` | `_daily_trend_lines()` + 본문 |
| 슬롯 기록 최근 20편 | `data/strategy.json` | 본문 |
| 유입 경로 10일 (일별 × 출처) | 유튜브 Analytics | 본문 |
| 슬롯별 유입 14일 | 유튜브 Analytics | `_traffic_by_slot()` |
| 시청자 댓글 14일 | 유튜브 API | `_viewer_comments()` |
| 편별 가설 자동 채점 | `data/hypotheses.jsonl` | `hypocheck.recent_text()` |
| 논문 적용 검토 최신본 | `D:\ai-daily\뉴스논문` | 본문 (6,000자까지) |
| 직전 플레이북·리포트 | `data/playbook.md`, `reports/` | 본문 (2,000자·2,500자까지) |

모든 자료가 지시문 하나(`ANALYSIS_PROMPT`)에 들어갑니다. 회고 AI 입력은 **매주 7.5만~24.4만 토큰**이었습니다(아래 표).

## 3. 호출 구조

| 칸 | 모델 | 설정 | 비고 |
|---|---|---|---|
| 회고 | `claude-opus-5-5` (10/5 전에는 `claude-opus-5`) | `max_tokens` 24,000, `effort` medium, 웹검색 최대 3회 | `_create()` 가 스트리밍으로 부르고 `stop_reason == "max_tokens"` 면 명시적 오류. 웹검색이 길어 `pause_turn` 이면 최대 4번 이어 받음. 본문에 JSON이 없으면 검색 없이 1회 재시도 |
| 팩트체크 | `claude-haiku-4-5` | `max_tokens` 16,000, JSON 문법 오류면 1회 재시도 | 결과를 **직접 고침**. 고친 결과가 원본의 40~50%보다 짧으면 원본 유지(요약 오작동 방지). 실패하면 자동 적용을 막고 알림 |
| 사후 처리 | 코드 | — | `_keep_hypotheses()` 가 팩트체크가 지운 「검증 중인 가설」 절을 되살림(10/12~), `approve._keep_old()` 가 빠진 절·주인 결정 줄을 되살림(10/21~) |

**max_tokens 교훈 (ADR-08)**: 9/13에 한도를 10,000으로 낮췄다가 오퍼스의 사고(thinking) 토큰이 한도를 다 써서 본문 0자로 실패했습니다. 지금은 24,000 + effort medium + 한도 초과를 오류로 처리합니다.

## 4. 출력

- `reports/YYYY-MM-DD-주간리포트.md` (바탕화면에도 사본), 끝에 「🔍 검증 노트 (자동 팩트체크)」
- `data/playbook_proposed.md` → `auto_approve` 로 `data/playbook.md` 에 바로 적용, 이전본은 `data/playbook_history/`
- 리포트의 「🙋 채널 주인 결정 필요」 절 → 바탕화면 파일과 폰 알림
- `data/stats_history.jsonl` 에 그 주 영상 통계 한 줄 추가

## 5. 최근 4주 기준선 숫자

| 회고일 | 비용 (회고 + 팩트체크) | 걸린 시간 ※ | 회고 입력 / 출력 토큰 | 팩트체크 지적 | 실패 | 다음 전략(가설) 수 | 다음 주 채점 결과 (표의 판정 칸) |
|---|---|---|---|---|---|---|---|
| 9/27 | US$0.76 (0.72 + 0.04) | 약 4분 | 7.5만 / 1.3만 | 5건 | 없음 | 4 | 10/4 채점: ✅2 ⚠️3 ❌2 (7줄) |
| 10/4 | US$1.60 (1.54 + 0.06) | 약 7분 | 19.4만 / 2.2만 | 6건 | 없음 | 3 | 10/11 채점: ✅3 ⚠️1 ❌2 ⏳2 (8줄) |
| 10/11 | US$1.20 (1.15 + 0.06) | 약 6.5분 | 15.6만 / 2.5만 | 8건 | 없음 ※※ | 3 | 10/18 채점: ✅1 ❌6, 판정 기호 없는 줄 6 (13줄) |
| 10/18 | US$1.66 (1.60 + 0.06) | 약 7.5분 | 24.4만 / 3.1만 | 7건 | 없음 ※※ | 3 | 10/25 회고에서 채점 예정 |
| **평균** | **US$1.31** | **약 6분** | | **6.5건** | **0/4** | **3.25** | |

- ※ 걸린 시간: 로그에 끝 시각이 없어서 「23:50 시작 기록 → 팩트체크 비용 기록 시각」으로 계산했습니다. 9/27은 시작 시각 줄이 로그에 없어 23:50으로 가정했습니다.
- ※※ 실행 실패는 없었지만 **조용한 결함**이 두 번 있었습니다.
  - 10/11: 팩트체크가 플레이북의 「검증 중인 가설」 절을 통째로 지웠습니다(플레이북 길이비 0.70). 10/12에 코드로 막았습니다.
  - 10/18: 자동 적용된 플레이북에서 "10/16 저녁 형식" 주인 결정 줄이 빠졌습니다. 10/21에 코드로 막았습니다.
- 채점 결과는 다음 주 리포트의 「지난 전략 회고 — 자기 채점표」 표의 마지막 칸 기호를 코드로 센 것입니다. 표 형식이 매주 달라 10/18은 6줄이 기호 없이 글로만 판정돼 있습니다. **같은 기준의 정밀 채점은 그림자 운영 때 코드로 만듭니다.**
- 회고 비용 비교 기준: **1회 평균 US$1.31, 최대 US$1.66**. 지시서의 비용 상한(기준선의 3배)은 약 **US$4.5** 로 잡습니다.
- 4주 이전에는 실패가 있었습니다: 9/13 본문 0자(출력 한도), 9월 초 팩트체크 JSON 오류 여러 번 (`logs/insights.log`).

## 6. 지금 구조의 약한 곳 (새 구조가 답해야 할 질문)

1. **한 AI가 24만 토큰을 한 번에 읽는다.** 자료가 늘수록 입력비가 커지고(4주 사이 7.5만 → 24.4만), 무엇을 근거로 썼는지 추적이 어렵다.
2. **팩트체크가 두 번째 작성자다.** 직접 고치다 보니 절을 통째로 지우는 사고가 났다(10/11). 지적만 하고 작성자가 고치는 쪽과 비교할 가치가 있다.
3. **주장마다 근거 표시가 없다.** 팩트체크가 "출처 없음"을 찾으려면 리포트 전체를 다시 읽어야 한다.
4. **채점 형식이 매주 다르다.** 다음 주 채점을 코드로 셀 수 없다.

## 학습노트 — 1단계

**무엇을 했나**
- 지금 돌아가는 주간 회고의 입력·호출·출력을 코드에서 읽어 그림으로 정리했습니다.
- 최근 4주 비용·시간·팩트체크 지적·가설 수를 로그에서 뽑았습니다.
- 숫자가 없는 칸은 "기록 없음"이 아니라 계산 방법을 같이 적었습니다.

**왜 이렇게 했나**
- 새 구조가 "더 낫다"고 말하려면 비교할 기준이 먼저 있어야 합니다. 기준선 없이 만들면 느낌으로만 비교하게 됩니다.
- 버린 대안: "새 구조부터 만들고 나중에 비교" → 그사이 운영 회고가 바뀌면(실제로 10/12, 10/21에 바뀜) 비교 기준이 흔들립니다.

**새 용어**

| 용어 | 한 줄 뜻 | 비유 |
|---|---|---|
| 기준선 (baseline) | 바꾸기 전 상태를 숫자로 적어 둔 것 | 다이어트 시작 전 몸무게 |
| 그림자 운영 (shadow mode) | 새 시스템을 진짜와 나란히 돌리되 결과는 실제로 쓰지 않는 것 | 수습 직원이 같은 일을 해 보고 선배 결과와 비교만 함 |
| 두 번째 작성자 | 검사하는 AI가 지적만 하지 않고 글을 직접 고치는 구조 | 교정자가 원고를 직접 고쳐 써 버림 |
| 조용한 결함 | 실행은 성공했는데 결과물이 잘못된 것 | 시험지는 냈는데 한 페이지가 빠짐 |

**면접 한 줄**: "바꾸기 전에 운영 중인 회고를 4주치 로그로 측정해 기준선을 만들었습니다. 평균 US$1.31, 약 6분, 팩트체크 지적 6.5건이었고, 실패는 0번이었지만 팩트체크가 절을 지우는 조용한 결함이 두 번 있었습니다."

<details><summary>점검 질문 1 — 실패가 0번인데 왜 구조를 바꿔 보려 하나?</summary>

실행 실패는 없었지만, 팩트체크가 직접 고치는 구조 때문에 「검증 중인 가설」 절과 주인 결정 줄이 사라지는 조용한 결함이 두 번 있었습니다.
또 입력이 4주 사이 3배 넘게 늘어 한 AI가 다 읽는 방식의 비용과 추적성이 나빠지고 있습니다. 그래서 바꾸는 게 아니라 **나란히 돌려 비교**해 보려는 것입니다.
</details>

<details><summary>점검 질문 2 — 비용 상한을 왜 "기준선의 3배"로 잡나?</summary>

멀티 에이전트는 호출이 늘어 토큰을 더 쓰는 게 보통입니다(업계 측정 약 15배). 그래도 회고는 주 1회라 몇 달러 차이는 감당할 수 있고,
3배(약 US$4.5)를 넘으면 구조가 잘못됐다는 신호로 보고 멈춥니다. 상한이 없으면 재시도 루프 같은 버그가 비용으로만 드러납니다.
</details>
