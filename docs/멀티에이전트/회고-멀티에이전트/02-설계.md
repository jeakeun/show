> 작성: 2026-10-22. **아직 코드 없음.** 주인 확인을 받은 뒤 구현합니다.
> 기준선: [01-기준선.md](01-기준선.md) (1회 평균 US$1.31·약 6분·팩트체크 지적 6.5건·실패 0/4, 조용한 결함 2번)

## 1. 그림

```
[0. 자료 모으기 - 코드]  운영 회고와 같은 함수로 같은 자료를 모음 + 숫자 표를 코드가 계산
        │
[1. 지휘자 - Haiku 5.5]  숫자 표의 요약만 보고 "이번 주 각 분석가가 꼭 볼 질문" 1~2개씩 정함
        │  Send (병렬, 전부 읽기 전용)
        ├──────────────┬──────────────┬──────────────┐
[2a. 조회·유입 분석가] [2b. 댓글·궁금증 분석가] [2c. 경쟁 채널 분석가] [2d. 지난 가설 채점 - 코드]
  Haiku 5.5            Haiku 5.5             Haiku 5.5            hypocheck + 지난 전략 표
        │ 각자 "요약 + 근거 숫자(번호 붙은 근거 카드)"만 돌려줌
        ▼
[3. 회고 작성자 1명 - Opus 5.5]  리포트 + 플레이북 초안. 주장마다 [근거 A3] 같은 근거 번호
        ▼
[4. 팩트체커 - Haiku 4.5]  고치지 않고 지적만: 근거 없음 / 표본 부족 / 과대 목표 / 주인 결정 위반
        │ 갈림길(조건부 엣지)
        ├─ 지적 없음 ─────────────────────────────┐
        ├─ 지적 있음 + 첫 번째 → 3으로 1회 되돌림  │
        └─ 지적 있음 + 두 번째 → 지적을 표시한 채 ─┤
                                                   ▼
[5. 저장 - 코드]  data/shadow_retro/YYYY-MM-DD/ 에만 씀 (운영 파일은 절대 안 씀)
```

## 2. 칸별 설계

| 칸 | 종류 | 모델 | 받는 것 | 돌려주는 것 | 왜 이렇게 (한 줄) |
|---|---|---|---|---|---|
| 0 자료 모으기 | 코드 | — | 유튜브 API·Analytics·`stats_daily`·`strategy.json`·댓글·`hypotheses.jsonl`·벤치마크·논문검토 | 원자료 + **숫자 표**(슬롯별 48시간 중앙값, 첫날 밤 조회, 쇼츠 피드 비율, 좋아요율, 형식별 비교) | 숫자는 코드가 (ADR-04). 운영 회고와 **같은 수집 함수를 가져다 쓰기만** 함 |
| 1 지휘자 | LLM | Haiku 5.5 | 숫자 표 요약 + 주인 결정 목록 | 분석가별 초점 질문 1~2개 | 판단이 있는 칸이라 AI (ADR-02). 원자료 대신 요약만 줘서 싸게 |
| 2a 조회·유입 | LLM | Haiku 5.5 | 숫자 표 + 영상 목록 + 유입 경로 + 슬롯 기록 | 요약 + 근거 카드 `A1, A2…` (근거마다 숫자와 출처 칸 이름) | 해석만 함. 숫자는 이미 계산돼 있음 |
| 2b 댓글·궁금증 | LLM | Haiku 5.5 | 시청자 댓글 + 궁금증 후보 | 요약 + 근거 카드 `B1…` | 댓글은 숫자보다 글 해석이라 따로 |
| 2c 경쟁 채널 | LLM | Haiku 5.5 | 벤치마크 영상·인기 댓글 + 인기 급상승 + 논문 검토 | 요약 + 근거 카드 `C1…` | 외부 자료는 출처가 섞이기 쉬워 따로 묶음 |
| 2d 가설 채점 | 코드 | — | `hypotheses.jsonl` + 지난주 리포트의 다음 전략 | 가설별 ✅/❌/⏳ 표 `D1…` | 채점은 매번 같은 답이 나와야 함 (ADR-04). 기준선에서 표 형식이 매주 달라 셀 수 없었던 문제를 같이 해결 |
| 3 작성자 | LLM | **Opus 5.5** (운영 회고와 같은 모델·`max_tokens` 24,000·`effort` medium·웹검색 최대 3회) | 분석가 요약·근거 카드·숫자 표·직전 플레이북·리포트·주인 결정 규칙 | 리포트 + 플레이북 초안 (JSON), 주장마다 근거 번호 | 쓰기는 한 곳. 모델을 운영과 똑같이 둬야 **구조 차이만** 비교됨 (ADR-08) |
| 4 팩트체커 | LLM | Haiku 4.5 (운영 팩트체크와 같은 모델) | 작성자 초안 + 근거 카드 목록 | 지적 목록 `[{문장, 문제 종류, 이유}]` | 지적만 함 → 절을 통째로 지우는 사고(10/11)가 구조적으로 불가능 (ADR-01·05) |
| 갈림길 | 코드 | — | 지적 수, 되돌린 횟수 | 다음 칸 | 무한 루프 방지: 되돌림 최대 1회 |
| 5 저장 | 코드 | — | 최종 초안 + 지적 + 실행 기록 | 그림자 폴더 파일들 | 운영 회고·플레이북과 완전히 분리 |

### 근거 카드 형식 (분석가 → 작성자)

```json
{"id": "A3", "claim": "저녁 순위형 48h 중앙값이 대화형보다 높다",
 "numbers": "순위형 905 (n=4) / 대화형 158 (n=3)", "source": "숫자표.슬롯별_48h", "sample_ok": false}
```
작성자는 리포트 문장 끝에 `[A3]` 를 붙입니다. 팩트체커는 근거 번호가 없는 숫자 주장과 `sample_ok=false` 인 근거로 단정한 문장을 찾습니다. 표시가 있으니 다시 읽지 않고 대조할 수 있습니다.

## 3. LangGraph 에서 쓰는 것과 이유

| 기능 | 어디에 | 이유 |
|---|---|---|
| `StateGraph` + 상태(State) | 전체 | 칸끼리 주고받는 자료를 한 곳에 정의 → 실행 기록이 남음 |
| `Send` | 1 → 2a·2b·2c·2d | 분석가 넷은 서로 의존이 없고 읽기만 해서 병렬로 돌려도 충돌이 없음 (ADR-06) |
| 조건부 엣지 | 4 → 3 또는 5 | 평가자-최적화자 루프 + 되돌림 상한 |
| 체크포인터 (SQLite) | 전체 | 중간에 죽으면 마지막 칸부터 이어서. 칸별 입력·출력이 남아 비교·디버깅에 씀 |
| `interrupt` | **쓰지 않음** | 그림자 운영은 되돌릴 수 없는 행동이 없어서 사람 승인 지점이 필요 없음 (ADR-07). 3주 뒤 교체 결정이 사람 몫 |

### 모델 부르는 방법 — 혼합 (확인한 사실과 선택 이유)

LangChain `ChatAnthropic` 문서를 확인했습니다 (2026-10-22).
- 지원: `effort`, 프롬프트 캐싱(`cache_control`), 캐시 토큰까지 담긴 사용량 기록, 웹검색 도구 연결, `betas`
- 문서에 없음: 웹검색이 길어질 때의 `pause_turn` 이어 받기, 거절 시 서버 쪽 대체 모델(지금 회고가 쓰는 `server-side-fallback`)

그래서 이렇게 나눕니다.
- **작성자(3)**: 운영 회고의 검증된 호출 코드(`_create()` - 스트리밍, `max_tokens` 초과를 오류로, `pause_turn` 이어 받기)를 노드 안에서 그대로 씁니다. 운영과 호출 방식까지 같아야 "구조만 다른" 비교가 됩니다.
- **지휘자·분석가·팩트체커(1, 2a~c, 4)**: LangChain `ChatAnthropic` + 구조화 출력(`with_structured_output`). 근거 카드·지적 목록처럼 모양이 정해진 출력을 검사까지 해서 받기 좋고, 공고의 LangChain 경험도 이 칸에서 보여줍니다.
- 모든 호출의 사용량은 운영과 같은 `apicost` 형식으로 그림자 전용 기록에 남깁니다(운영 `api_usage.csv` 는 섞지 않음).

## 5. 비교 방법

- **같은 채점기로 두 회고를 채점**: 운영 리포트와 그림자 리포트를 똑같은 채점 지시문(근거 없는 주장 수, 표본 부족 단정 수, 과대 목표 수, 주인 결정 위반 수)으로 한 번씩 채점합니다. 운영 팩트체크 결과를 그대로 쓰면 기준이 달라 비교가 안 됩니다.
- 가설은 2d 칸이 만드는 같은 형식의 표로 다음 주에 코드가 채점합니다.
- 비용·시간·실패는 실행 기록에서 코드가 셉니다.
- 매주 `주간비교-YYYY-MM-DD.md`, 3주 뒤 종합 보고와 A/B/C/D 선택지(교체 / 일부만 반영 / 더 관찰 / 폐기).

## 학습노트 — 2단계 (설계)

**무엇을 했나**
- 회고를 지휘자 1 + 분석가 3 + 코드 채점 1 + 작성자 1 + 팩트체커 1 로 나누는 설계안을 썼습니다.
- 칸마다 모델·입력·출력·이유를 한 줄씩 붙였습니다.
- 모델 래퍼(LangChain)가 지금 쓰는 기능을 다 지원하는지 문서로 확인하고, 안 되는 칸은 기존 코드를 쓰기로 했습니다.

**왜 이렇게 했나 (대안과 버린 이유)**
- 대안 A "분석가 없이 작성자 1명 + 지적만 하는 팩트체커": 가장 단순하지만, 24만 토큰을 한 번에 읽는 문제와 근거 추적 문제가 그대로 남습니다.
- 대안 B "분석가가 각자 리포트 일부를 직접 씀": 글쓴이가 여럿이라 말투·주장이 어긋나고, 쓰기를 한 곳에 모으는 원칙에 어긋납니다.
- 대안 C "전부 LangChain 래퍼": 운영 회고와 호출 방식이 달라져 구조 차이와 호출 차이가 섞입니다. `pause_turn`·서버 대체 모델 지원도 문서로 확인이 안 됐습니다.

**새 용어**

| 용어 | 한 줄 뜻 | 비유 |
|---|---|---|
| 지휘자 (supervisor) | 일을 나눠 주고 결과를 모으는 에이전트 | 팀장이 오늘 볼 것을 정해 줌 |
| Send | LangGraph 에서 같은 일을 여러 칸에 동시에 보내는 명령 | 같은 서류를 세 부서에 동시에 돌림 |
| 조건부 엣지 | 결과를 보고 다음 칸을 고르는 갈림길 | 시험 불합격이면 재시험, 합격이면 다음 단계 |
| 근거 카드 | 주장 + 숫자 + 출처를 묶은 작은 기록 | 논문의 각주 |
| 구조화 출력 | AI 답을 정해진 모양(JSON 칸)으로 받게 강제하는 것 | 자유 서술 대신 서식 있는 신청서 |
| 체크포인터 | 칸마다 상태를 저장해 두는 장치 | 게임 세이브 포인트 |

**면접 한 줄**: "운영 중인 회고를 읽기 전용 분석가 셋과 코드 채점으로 나누고, 쓰기는 작성자 한 명, 검증은 지적만 하는 팩트체커로 바꿨습니다. 작성자 모델과 호출 코드를 운영과 똑같이 둬서 구조 차이만 비교되게 했습니다."

<details><summary>점검 질문 1 — 왜 작성자는 여럿이 아니라 한 명인가?</summary>

여러 AI가 리포트를 나눠 쓰면 말투와 주장이 어긋나고, 누가 무엇을 썼는지 추적이 어렵습니다. 읽기(분석)는 충돌이 없어 나누고, 쓰기는 한 곳에 모읍니다.
운영 회고의 팩트체크가 글을 직접 고치다 절을 지운 사고(10/11)가 바로 "작성자가 둘"이라 생긴 문제였습니다.
</details>

<details><summary>점검 질문 2 — 왜 interrupt(사람 승인)를 이번엔 안 쓰나?</summary>

그림자 운영 결과는 아무 데도 반영되지 않아서 되돌릴 수 없는 행동이 없습니다. 승인 지점은 "되돌릴 수 없는 일 앞"에 두는 게 원칙이라(ADR-07),
여기서는 3주 뒤 "교체할지"를 사람이 고르는 것이 승인 지점입니다.
</details>
