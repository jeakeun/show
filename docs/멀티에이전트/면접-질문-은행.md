## A. 기본기

### Q1. 멀티 에이전트가 뭔가요? 에이전트 하나와 무엇이 다른가요?
<details><summary>30초 답변</summary>

"각자 따로 맥락을 가진 AI 여러 개가 일을 나누고, 코드나 지휘 에이전트가 조율하는 구조입니다.
에이전트 하나는 한 대화 안에서 모든 걸 처리해서 맥락이 길어지고, 자기 결과를 스스로 검사하게 됩니다.
나누면 맥락 보호, 병렬 처리, 역할별 모델 선택, 만든 쪽과 검사하는 쪽의 분리가 가능합니다.
대신 토큰 비용이 크게 늘고 맥락이 끊기는 대가가 있습니다."

**꼬리 질문 대비**
- "같은 모델을 두 번 부르는 것도 멀티 에이전트인가요?" → 맥락이 분리돼 있으면 그렇다. 본질은 모델 종류가 아니라 맥락 분리.
- "비용이 얼마나 늘어나나요?" → Anthropic 측정으로 일반 채팅의 약 15배 토큰.
</details>

### Q2. 언제 멀티 에이전트를 쓰고, 언제 쓰지 말아야 하나요?
<details><summary>30초 답변</summary>

"읽기 중심이고 독립적으로 나눌 수 있는 일, 예를 들어 리서치나 감사는 병렬로 나누면 효과가 큽니다.
여럿이 같은 결과물을 동시에 쓰는 일은 각자 다른 암묵적 결정을 내려서 합치면 깨지기 쉽습니다.
그래서 '읽기는 나누고, 같은 결과물을 쓰는 건 한 곳으로'를 원칙으로 삼습니다.
에이전트 하나로 먼저 해보고, 실패 원인이 나누기로 해결되는 종류일 때만 늘립니다."

**꼬리 질문 대비**
- "근거가 있나요?" → Anthropic 리서치 시스템(읽기 중심, 병렬로 90.2% 향상)과 Cognition의 반론, 그리고 Cognition의 2026년 후속 글(생각은 여럿, 쓰기는 하나).
</details>

### Q3. 5가지 기본 패턴을 아나요? 직접 쓴 건 무엇인가요?
<details><summary>30초 답변</summary>

"프롬프트 체이닝, 라우팅, 병렬화, 오케스트레이터-작업자, 평가자-최적화자입니다.
- 유튜브 파이프라인과 AI데일리의 수집 → 검수 2단 구조가 체이닝입니다.
- 8/27 첫 전수 감사에서 읽기 전용 감사 에이전트 3기를 동시에 돌린 게 병렬화입니다.
- 대본 작성 후 검수 AI가 채점하고 작성 AI가 다시 쓰는 게이트가 평가자-최적화자입니다.
라우팅과 오케스트레이터는 운영 시스템에 정확한 사례가 없습니다.
다음 프로젝트(맞춤 지원서 에이전트)에서 공고마다 요구 항목 수가 달라, 그 수만큼 검색 작업자를 실행 중에 나눠 보내는 오케스트레이터형 구조를 만들 계획입니다."

**꼬리 질문 대비**
- "병렬화와 오케스트레이터 차이는?" → 칸이 미리 정해져 있나(병렬화), 지휘자가 그때그때 나누나(오케스트레이터).
- "아침·저녁 슬롯별 대본은 라우팅 아닌가요?" → 입력을 분류하는 게 아니라 시간표 코드가 정하는 것이라 라우팅으로 보지 않는다.
</details>

## B. 내 시스템 설명

### Q4. 직접 만든 시스템을 2분 안에 설명해 주세요.
<details><summary>답변 뼈대</summary>

1. **무엇**: 유튜브 채널 운영, AX 채용 수집, 코인 모의투자, 주간 자가감사를 사람 손 없이 매일 돌리는 자동화 묶음. 2026-08부터 운영 중.
2. **구조**: 모든 구성요소를 수집·규칙·분석·실행 4칸 중 하나에 넣었다. 분석 AI는 운영 설정을 직접 고치지 못하고 제안만 쓴다 (ADR-03).
3. **AI가 하는 칸**
   - 대본 작성 ↔ 검수 (ADR-01)
   - 회고 ↔ 팩트체크 (ADR-05)
   - 읽기 전용 감사 (ADR-06)
4. **경계**: 판단 없는 단계는 코드 (ADR-02). 숫자와 고정 문자열도 코드가 만든다 (ADR-04).
5. **운영**
   - 사람 승인은 되돌릴 수 없는 결정에만 둔다 (ADR-07).
   - 역할별 모델을 쓰고 비용을 호출마다 기록한다 (ADR-08).
   - 성공은 결과물로 판정하고, 실패하면 폰으로 알린다 (ADR-09).
</details>

### Q5. 왜 그 부분은 에이전트를 나눴나요?
<details><summary>30초 답변</summary>

"작성 과정을 함께 겪은 AI는 자기 결과에 관대해지기 쉽습니다. 그래서 대본은 별도 검수 AI가 기준표로 채점하고, 회고는 다른 AI가 반박하게 나눴습니다.
감사는 읽기 전용이라 나눠서 동시에 돌려도 서로 충돌할 쓰기가 없습니다."

**꼬리 질문 대비**
- "검수 AI도 틀리면요?" → 실제로 틀렸다. 일주일 재생성 3건이 전부 검수 오탐이라 슬롯별 기준으로 고쳤다.
  코드 사후검사는 항상 같이 돌고, 주간 감사가 결과를 다시 대조한다 (ADR-01·06).
</details>

### Q6. 반대로 에이전트로 만들지 않은 부분은 어디고, 왜인가요?
<details><summary>30초 답변</summary>

"슬롯 결정, 렌더링, 업로드, 자막 맞추기는 코드로 뒀습니다. '부서별 에이전트로 나누자'는 안은 판단 없는 공정에 감독관을 붙이는 격이라 기각했습니다.
코인 매매도 AI 판단 없이 코드 규칙으로만 돌고, AI는 주간 회고에서 제안만 합니다." (ADR-02)
</details>

### Q7. 에이전트끼리 정보는 어떻게 주고받나요?
<details><summary>30초 답변</summary>

"대부분 파일로 주고받습니다. 회고 AI는 제안 파일을 쓰고, 적용 코드가 그걸 읽습니다. 수집 결과는 구조화된 기록 파일과 공유 데이터베이스에 쌓입니다.
실시간은 아니지만 모든 전달 내용이 파일로 남아서 추적하고 다시 돌려보기 쉽습니다."

**꼬리 질문 대비**
- "실시간 협업은요?" → 운영 시스템에서는 아직 안 해봤다. LangGraph로 지휘자가 하위 에이전트를 부르고 결과를 합치는 구조를 학습 예제로 돌려봤고, 다음 프로젝트에서 실제로 만든다.
  핵심은 전체 대화가 아니라 필요한 요약만 넘기는 것(맥락 보호).
</details>

## C. 신뢰성·안전

### Q8. 환각(지어내기)은 어떻게 막나요?
<details><summary>30초 답변</summary>

"세 겹으로 막습니다.
1. 숫자와 카운터는 AI가 세지 않고 코드가 계산해서 넘깁니다. AI가 손으로 센 카운터가 부풀었던 걸 겪고 바꿨습니다.
2. 대본은 검수 AI와 코드 검사를 거칩니다. 차단급이면 재생성하거나 예비 대본으로 바꿉니다. 검수 API가 장애면 통과시키지만 코드 검사는 유지됩니다.
3. 읽기 전용 감사가 리포트의 주장을 원본 데이터와 대조합니다. 첫 감사에서 AI데일리의 없는 회차 기록과 코인봇 수수료 계산 오류를 찾았습니다." (ADR-04·01·06)
</details>

### Q9. 에이전트에게 권한을 얼마나 주나요?
<details><summary>30초 답변</summary>

"필요한 만큼만 줍니다.
- 분석 AI는 리포트와 제안 파일만 씁니다.
- AI데일리는 허용 도구를 지정해서 실행합니다. 헤드리스 클로드가 작업 폴더 밖에 못 쓰는 성질을 경계로 삼아 작업 폴더를 고정했습니다.
- 도구 제한이 없던 코인 회고는 해시 가드로 막았습니다. 보호 파일이 바뀌면 자동 원복하고, 루트에 생긴 새 파일은 격리합니다.
실제로 코인 회고 AI가 임시 스크립트를 만들었을 때 가드가 격리했습니다." (ADR-03)

**꼬리 질문 대비**
- "작업 폴더 밖에 못 쓰는 건 일부러 설계한 건가요?" → 아니다. 처음엔 이 성질 때문에 저장이 전부 막혀서 버그로 겪었고, 그 뒤 경계로 활용했다.
</details>

### Q10. 사람은 어디에 개입하나요?
<details><summary>30초 답변</summary>

"세 번 바꿨습니다.
1. 8월에는 회고 AI가 전략을 바로 반영했습니다.
2. 9/7에 분석은 제안만 하게 하면서 모든 변경을 승인받게 했는데, 승인 대기로 적용이 하루 밀렸습니다.
3. 그래서 기준을 '되돌릴 수 있는가'로 바꿨습니다.
지금은 되돌릴 수 있는 전략·프롬프트 개선은 이전본을 남기고 자동 적용 후 보고합니다.
돈, 영상 삭제, 실전 매매처럼 되돌릴 수 없는 결정은 사람이 A/B/C/D 선택지 중에서 고릅니다." (ADR-07)

**꼬리 질문 대비**
- "되돌릴 수 없는 걸 겪은 적이 있나요?" → 품질 문제로 올린 영상을 지우고 다시 올렸더니 유튜브가 중복으로 보고 노출을 거의 안 줬다(16시간 2회). 이후 품질은 업로드 전에만 잡는다.
</details>

### Q11. 에이전트가 무한 반복하거나 폭주하면요?
<details><summary>30초 답변</summary>

"실제로 겪었습니다.
- 대본 제목의 시리즈 번호를 AI에게 쓰게 하고 AI로 검사했더니 루프가 생겼습니다. 빠지면 예비 대본으로 넘어가고, 번호가 멈춘 채 같은 요구가 반복됐습니다.
  그래서 저녁 자가테스트 시리즈가 사흘 동안 빠지고 예비 대본으로 대체됐습니다. 이후 그런 고정 문자열은 코드가 붙이게 바꿨습니다.
- 반복 횟수에도 상한을 뒀습니다. 대본은 2번 연속 차단되면 재생성을 멈춥니다.
- 매매 사이클은 파일 락으로 겹쳐 돌지 않게 했습니다.
- 처리 안 된 제안이 있으면 새 제안을 만들지 않고 건너뜁니다." (ADR-04)

**꼬리 질문 대비**
- "동시 실행 문제는요?" → 무인 AI 작업 두 개가 동시에 돌면 한쪽이 죽는 것으로 의심되는 현상이 두 번 재현됐다. 원인은 확정 못 했고, 예약 시간이 겹치지 않게 했다.
</details>

## D. 비용·평가·운영

### Q12. 비용은 어떻게 관리했나요?
<details><summary>30초 답변</summary>

"모든 호출의 비용을 기록하고, 역할마다 모델을 다르게 썼습니다. 주간 분석은 상위 모델, 대본은 중간 모델, 검수와 팩트체크는 가장 싼 모델입니다.
실측 월 US$51에서 목표를 US$30으로 잡고 캐싱과 실행 빈도도 조정했습니다.
대본 생성은 기준 주에 주 US$3.72, 호출당 약 US$0.16이었습니다." (ADR-08)

**꼬리 질문 대비**
- "비용 줄이다 문제 생긴 적은?" → 출력 한도를 낮췄는데, 사고 토큰까지 한도에 들어가는 데다 출력 자체가 약 1.2만 토큰이라 회고가 본문 0자로 실패했다.
  한도를 올리고, 한도 초과를 명시적 오류로 잡고, 실패하면 바로 폰 알림이 오게 했다.
</details>

### Q13. 품질은 어떻게 평가하나요?
<details><summary>30초 답변 (솔직 버전)</summary>

"지금은 세 가지로 봅니다.
- 업로드 전 검수 게이트
- 회고 AI가 직전 전략을 스스로 채점하는 주간 회고
- 리포트와 원본 데이터를 대조하는 주간 감사
재생성률 같은 운영 지표도 봅니다. 기준 주에 재생성이 21%였는데, 3건 모두 검수 오탐이라 검수 기준을 고쳤습니다.
다만 정해진 평가셋으로 점수를 재는 체계는 아직 없어서, 다음 프로젝트에서는 평가셋부터 만들고 에이전트 1개와 여러 개를 같은 문제로 비교할 계획입니다."

> 약점을 먼저 말하고 해결 계획을 붙이는 게 신뢰를 줍니다. 2단계 평가를 끝내면 이 답을 실측 숫자로 바꿉니다.
</details>

### Q14. 실패 경험과 배운 점을 말해 주세요.
<details><summary>답변 뼈대 (하나 골라 쓰기)</summary>

- **예측이 틀린 경우 (코인봇)**
  - 손절이 -2%를 넘겨 체결되는 문제가 있었다. 15건 전부였고 평균 -2.94%였다. 점검 주기를 10분에서 5분으로 줄이면 나아질 거라 예측했다.
  - 다음 회고에서 천천히 빠지는 손절은 -2.59%로 나아졌지만, 전체 평균은 -3.97%로 오히려 나빠졌다.
  - 분석해 보니 손실의 78%가 매수 15분 안에 -6~-10%로 무너지는 급락이었다. 점검 주기로는 못 막는 종류였다.
  - 회고 데이터에서 120원 이상 코인 그룹은 3주 연속 플러스였다. 그래서 120원 미만 신규 매수를 막는 규칙을 2주 시험으로 걸었다.
  - 9/28 재평가에서 이 규칙은 해제했다. 해제 이유는 **확인 필요**.
  - **배운 점**: 원인을 확인하기 전에 처방부터 하지 않는다. 처방마다 검증 날짜를 걸어두면 안 맞는 규칙을 빨리 걷어낼 수 있다.
- **감사를 반박한 쪽이 틀린 경우**

  - **배운 점**: 감사도, 감사를 반박하는 쪽도 검증 대상이다.

  - 감사가 원인을 찾았고, 다음 회고가 "오진"이라고 스스로 정정했다. 실제로는 +44% 회복이었다 (ADR-04).

## E. 업계 이해

### Q16. Cognition은 "멀티 에이전트를 만들지 말라"고 했는데 어떻게 생각하나요?
<details><summary>30초 답변</summary>

"그 글의 핵심은 여러 에이전트가 맥락을 공유하지 못한 채 병렬로 '쓰면' 서로 다른 암묵적 결정 때문에 결과가 깨진다는 겁니다.
Cognition도 2026년 후속 글에서, 여러 에이전트가 검토나 조언으로 생각을 보태는 구조는 잘 되고 쓰기는 한 줄기로 유지하는 게 핵심이라고 정리했습니다.
제 시스템도 비슷합니다. 감사는 읽기 전용이고, 유튜브 대본은 작성 AI 하나가 쓰고 검수 AI는 지적만 합니다.
다만 AI데일리 검수나 회고 팩트체크처럼 앞 단계 결과를 순서대로 직접 고치는 두 번째 작성자도 있어서, 이 경우 원문과 수정본을 같이 남겨야 한다고 봅니다."
</details>

### Q17. LangGraph나 LangChain을 써봤나요?
<details><summary>지금의 솔직한 답 → 2단계 후 업데이트</summary>

**지금**: "운영 중인 시스템은 프레임워크 없이 파이썬과 클로드 API, 클로드 코드 헤드리스 실행으로 만들었습니다.
제가 설계하고 AI 코딩 도구와 함께 구현했고, 재시도 상한·사람 승인·이전본 보관을 운영 시스템에 넣어봤습니다.
최근에 그 구조를 흉내 낸 LangGraph 학습 예제를 돌려봤습니다. 검수 루프는 갈림길로, 승인은 interrupt와 체크포인터로, 병렬 처리는 Send로 옮겼습니다.
그러면서 interrupt로 재개하면 노드가 처음부터 다시 실행된다는 것처럼, 직접 짤 때와 다른 점도 확인했습니다.
다음 프로젝트는 LangGraph로 만들 계획입니다."

**2단계 후 채울 것**: LangGraph로 만든 프로젝트에서 직접 짠 방식보다 편했던 점과 과했던 점.
</details>

### Q18. MCP가 뭔가요? 써봤나요?
<details><summary>30초 답변</summary>

"AI가 외부 도구와 데이터에 연결하는 표준 방식입니다. 도구마다 따로 연동 코드를 짜는 대신, MCP 서버 하나로 여러 AI 클라이언트에 붙일 수 있습니다.
저는 노션, 깃허브, 그리고 취몽 데일리 로그 제출을 MCP로 연결해 쓰고 있습니다. 게임 개발 에이전트용으로 유니티 편집기를 MCP로 조작하는 방식도 검토했습니다."

**꼬리 질문 대비**
- "MCP와 그냥 API 호출의 차이는?" → 도구 설명과 입력 형식을 표준으로 노출해서, AI가 어떤 도구가 있고 어떻게 부르는지 스스로 알 수 있다.
  레거시 시스템을 에이전트에 붙일 때도 MCP 서버로 감싸면 여러 에이전트가 같은 방식으로 쓴다 → [05 문서](05-레거시-시스템-연계.md).
</details>

### Q19. 다시 설계한다면 무엇을 바꾸겠나요?
<details><summary>답변 뼈대</summary>

1. **평가셋을 먼저 만든다.** 품질을 숫자로 재는 기준이 늦게 생겼다.
2. **데이터 출처를 처음부터 하나로 모은다.** 공유 DB(hub)를 나중에 만들어서, 9월 기준으로 리포트들이 아직 원본 파일을 따로 읽는다.
3. **사람 승인 기준을 처음부터 "되돌릴 수 있는가"로 정한다.** 자동 반영 → 전부 승인 → 선조치 후보고로, 이 기준에 오기까지 두 번 방향을 바꿨다.
4. **인증·한도 같은 외부 의존성을 시작 전에 점검한다.** 로그인 만료와 지출 한도 초과가 모두 "실행 중에" 발견됐다.
5. **두 번째 작성자를 두지 않거나, 둘 거면 수정 기록을 남긴다.** 검수 AI가 직접 고치면 누가 무엇을 바꿨는지 흐려진다.
</details>
