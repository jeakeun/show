**연습 방법**: 질문만 보고 30초 안에 소리 내어 답한 뒤, 접힌 모범 답과 비교합니다.
꼬리 질문까지 답할 수 있어야 "안다"고 봅니다. 근거는 [02-내-설계결정-기록.md](02-내-설계결정-기록.md)의 ADR 번호로 달았습니다.

## A. 기본기

### Q1. 멀티 에이전트가 뭔가요? 에이전트 하나와 무엇이 다른가요?
<details><summary>30초 답변</summary>

"각자 따로 맥락을 가진 AI 여러 개가 일을 나누고, 코드나 지휘 에이전트가 조율하는 구조입니다.
에이전트 하나는 한 대화 안에서 모든 걸 처리해서 맥락이 길어지고, 자기 결과를 스스로 검사하게 됩니다.
나누면 맥락 보호, 병렬 처리, 역할별 모델 선택, 만든 쪽과 검사하는 쪽의 분리가 가능합니다.
대신 토큰 비용이 크게 늘고 맥락이 끊기는 대가가 있습니다."

**꼬리 질문 대비**
- "같은 모델을 두 번 부르는 것도 멀티 에이전트인가요?" → 맥락이 분리돼 있으면 그렇다. 본질은 모델 종류가 아니라 맥락 분리.
- "비용이 얼마나 늘어나나요?" → Anthropic 측정으로 일반 채팅의 약 15배 토큰.
</details>

### Q2. 언제 멀티 에이전트를 쓰고, 언제 쓰지 말아야 하나요?
<details><summary>30초 답변</summary>

"읽기 중심이고 독립적으로 나눌 수 있는 일, 예를 들어 리서치나 감사는 병렬로 나누면 효과가 큽니다.
여럿이 같은 결과물을 쓰는 일은 각자 다른 암묵적 결정을 내려서 합치면 깨지기 쉽습니다.
그래서 저는 '읽기는 나누고 쓰기는 한 곳으로'를 원칙으로 삼고, 에이전트 하나로 먼저 해본 뒤
실패 원인이 나누기로 해결되는 종류일 때만 늘립니다."

**꼬리 질문 대비**
- "근거가 있나요?" → Anthropic 리서치 시스템(읽기 중심, 병렬로 90.2% 향상)과 Cognition의 반론 및 2026년 후속 글(생각은 여럿, 쓰기는 하나).
</details>

### Q3. 5가지 기본 패턴을 아나요? 직접 쓴 건 무엇인가요?
<details><summary>30초 답변</summary>

"프롬프트 체이닝, 라우팅, 병렬화, 오케스트레이터-작업자, 평가자-최적화자입니다.
유튜브 파이프라인이 체이닝, 아침·저녁 슬롯별 대본 방식이 라우팅, 읽기 전용 감사 3기가 병렬화,
대본 작성 후 검수 AI가 채점해 재생성하는 게이트가 평가자-최적화자입니다."

**꼬리 질문 대비**
- "병렬화와 오케스트레이터 차이는?" → 칸이 미리 정해져 있나(병렬화), 지휘자가 그때그때 나누나(오케스트레이터).
- "오케스트레이터는 직접 짜봤나요?" → 감사 방법론과 클로드 코드 서브에이전트로 써봤고, 코드로 직접 짜는 건 진행 중 (2단계 2-3).
</details>

## B. 내 시스템 설명

### Q4. 직접 만든 시스템을 2분 안에 설명해 주세요.
<details><summary>답변 뼈대</summary>

1. **무엇**: 유튜브 채널 운영, AX 채용 수집, 코인 모의투자, 주간 자가감사를 사람 손 없이 매일 돌리는 자동화 묶음.
   2026-08부터 운영 중.
2. **구조**: 모든 구성요소를 수집·규칙·분석·실행 4칸 중 하나에 넣었다. 분석 AI는 제안만 쓰고, 실제 변경은 코드 한 곳에서만 일어난다 (ADR-03).
3. **에이전트**
   - 대본 작성 AI ↔ 검수 AI (ADR-01)
   - 회고 AI ↔ 팩트체크 AI (ADR-05)
   - 읽기 전용 감사 에이전트 병렬 (ADR-06)
4. **경계**: 판단 없는 단계는 코드 (ADR-02), 숫자는 코드가 계산 (ADR-04).
5. **운영**
   - 사람 승인은 되돌릴 수 없는 결정에만 둔다 (ADR-07).
   - 역할별 모델을 쓰고 비용을 호출마다 기록한다 (ADR-08).
   - 실패하면 폰으로 알린다 (ADR-09).
</details>

### Q5. 왜 그 부분은 에이전트를 나눴나요?
<details><summary>30초 답변</summary>

"만든 AI가 자기 결과를 검사하면 관대해집니다. 그래서 대본과 회고는 다른 AI가 기준표로 채점하거나 반박하게 나눴습니다.
감사는 프로젝트별로 독립적인 읽기 작업이라 병렬로 나눠도 충돌이 없어서 나눴습니다."

**꼬리 질문 대비**
- "검수 AI도 틀리면요?" → 코드 사후검사(제목·의료 단어)를 항상 같이 두고, 주간 감사가 결과를 다시 대조한다. 감사 결과도 검증 대상 (ADR-06 교훈).
</details>

### Q6. 반대로 에이전트로 만들지 않은 부분은 어디고, 왜인가요?
<details><summary>30초 답변</summary>

"음성 합성, 렌더링, 업로드 같은 판단 없는 공정은 코드로 뒀습니다.
'부서별 에이전트 + 감독 에이전트' 안도 검토했지만, 판단이 없는 곳에 AI를 두면 비용과 실패 지점만 늘어서 기각했습니다.
코인 매매도 AI 판단 없이 코드 규칙으로만 돌고, AI는 주간 회고에서 제안만 합니다." (ADR-02)
</details>

### Q7. 에이전트끼리 정보는 어떻게 주고받나요?
<details><summary>30초 답변</summary>

"대부분 파일로 주고받습니다. 회고 AI는 제안 파일을 쓰고, 적용 코드가 그걸 읽습니다.
수집 결과는 구조화된 기록 파일과 공유 데이터베이스에 쌓입니다.
실시간은 아니지만 모든 전달 내용이 파일로 남아서 추적하고 다시 돌려보기 쉽습니다."

**꼬리 질문 대비**
- "실시간 협업은요?" → 지휘자가 하위 에이전트를 직접 부르고 요약을 받는 구조는 2단계에서 직접 구현 중.
  넘길 때는 전체 대화가 아니라 필요한 요약만 넘기는 게 핵심(맥락 보호).
</details>

## C. 신뢰성·안전

### Q8. 환각(지어내기)은 어떻게 막나요?
<details><summary>30초 답변</summary>

"세 겹으로 막습니다.
첫째, 숫자와 카운터는 AI가 세지 않고 코드가 계산해서 넘깁니다.
둘째, 결과물은 별도 검수 AI와 코드 검사를 통과해야 나갑니다.
셋째, 매주 읽기 전용 감사 에이전트가 리포트의 주장을 원본 데이터와 대조합니다.
실제로 첫 감사에서 AI데일리의 없는 회차 기록과 코인봇 수수료 계산 오류를 찾았습니다." (ADR-04·01·06)
</details>

### Q9. 에이전트에게 권한을 얼마나 주나요?
<details><summary>30초 답변</summary>

"필요한 만큼만 줍니다.
- 분석 AI는 리포트와 제안 파일만 씁니다.
- 보호 파일은 해시를 찍어 두고, 바뀌면 자동 원복하고 폰으로 알립니다. 루트에 생긴 새 파일은 격리합니다.
- 무인 실행하는 AI는 쓸 수 있는 도구 목록을 제한하고, 작업 폴더 밖에는 쓸 수 없게 했습니다.
실제로 코인 회고 AI가 임시 스크립트를 만들었을 때 가드가 격리했습니다." (ADR-03)
</details>

### Q10. 사람은 어디에 개입하나요?
<details><summary>30초 답변</summary>

"처음엔 모든 변경을 승인받게 했는데, 승인 대기 때문에 적용이 하루 밀리는 일이 생겼습니다.
그래서 기준을 '되돌릴 수 있는가'로 바꿨습니다.
되돌릴 수 있는 전략·프롬프트 개선은 자동 적용 후 보고하고, 이전본을 보관합니다.
돈, 영상 삭제, 실전 매매 같은 되돌릴 수 없는 결정은 사람이 A/B/C/D 선택지 중에서 고릅니다." (ADR-07)

**꼬리 질문 대비**
- "되돌릴 수 없는 걸 겪은 적이 있나요?" → 품질 문제로 올린 영상을 지우고 다시 올렸더니 유튜브가 중복으로 보고 노출을 거의 안 줬다(16시간 2회). 이후 품질은 업로드 전에만 잡는다.
</details>

### Q11. 에이전트가 무한 반복하거나 폭주하면요?
<details><summary>30초 답변</summary>

"반복 횟수에 상한을 뒀습니다. 대본은 2번 연속 차단되면 재생성을 멈추고 예비 대본을 씁니다.
- 매매 사이클은 파일 락으로 겹쳐 돌지 않게 했습니다.
- 처리 안 된 제안이 있으면 새 제안을 만들지 않고 건너뜁니다.
- 무인 AI 두 개가 동시에 돌면 하나가 죽는 걸 두 번 겪고 나서, 예약 시간이 겹치지 않게 짰습니다."
</details>

## D. 비용·평가·운영

### Q12. 비용은 어떻게 관리했나요?
<details><summary>30초 답변</summary>

"모든 호출의 비용을 기록하고, 역할마다 모델을 다르게 썼습니다.
주간 분석은 상위 모델, 대본은 중간 모델, 검수와 팩트체크는 가장 싼 모델입니다.
실측 월 US$51에서 목표를 US$30으로 잡고 캐싱과 실행 빈도도 조정했습니다." (ADR-08)

**꼬리 질문 대비**
- "비용 줄이다 문제 생긴 적은?" → 출력 한도를 낮췄더니 사고 토큰이 한도를 다 써서 회고가 본문 0자로 실패했다.
  한도 상향, 사고 강도 조정, 한도 초과 명시적 오류 처리, 실패 알림을 추가했다. 이후 비용과 실패율을 같이 본다.
</details>

### Q13. 품질은 어떻게 평가하나요?
<details><summary>30초 답변 (솔직 버전)</summary>

"지금은 세 가지로 봅니다.
- 업로드 전 검수 게이트
- 회고 AI가 직전 전략을 스스로 채점하는 주간 회고
- 리포트와 원본 데이터를 대조하는 주간 감사
다만 정해진 평가셋으로 점수를 재는 체계는 아직 약해서, 지금 만드는 프로젝트에서는 평가셋부터 만들고
에이전트 1개와 여러 개를 같은 문제로 비교해 숫자로 보려고 합니다."

> 약점을 먼저 말하고 해결 계획을 붙이는 게 신뢰를 줍니다. 2단계 2-5를 끝내면 이 답을 실측 숫자로 바꿉니다.
</details>

### Q14. 실패 경험과 배운 점을 말해 주세요.
<details><summary>답변 뼈대 (하나 골라 쓰기)</summary>

- **예측 실패를 인정한 경우 (코인봇)**
  - 손절이 -2%를 넘겨 체결되는 문제가 있었다. 15건 전부였고 평균 -2.94%였다. 점검 주기를 10분에서 5분으로 줄이면 나아질 거라 예측했다.
  - 다음 회고에서 평균은 -3.97%로 오히려 나빠졌다.
  - 분석해 보니 손실의 78%는 매수 15분 안에 -6~-10%로 무너지는 급락이었다. 점검 주기로는 못 막는 종류였다.
  - 그래서 원인 쪽인 저가 코인 진입을 막는 규칙(120원 미만 매수 금지)으로 바꿨다. 이것도 2주 시험으로 걸었다.
  - **배운 점**: 원인을 확인하기 전에 처방부터 하지 않는다. 처방마다 검증 날짜를 걸어둔다.
- **내 판단이 틀린 경우 (감사)**: 감사 에이전트의 지적 하나를 오탐이라고 반박했다가, 로그를 다시 보고 정정했다.
  - **배운 점**: 감사 결과도, 그걸 반박하는 나도 검증 대상이다.
</details>

### Q15. 장애 대응 경험이 있나요?
<details><summary>답변 뼈대</summary>

- **구독 로그인 만료 (9/8)**
  - 무인 AI 작업이 전부 멈췄다.
  - 원인을 확인하고 재로그인을 안내했다. 복구를 감시하다 빠진 작업을 자동으로 다시 돌렸다.
  - 후속으로 시작 전에 로그인 상태를 점검하는 기능을 제안했다.
- **이미지 API 월 지출 한도 초과 (8/26)**
  - 영상 2편이 대체 배경으로 조용히 발행됐다.
  - 이후 품질 저하 발행도 바탕화면 경고와 폰 알림으로 먼저 알리게 했다.
- **배운 점**: 실패보다 무서운 건 조용한 실패다. 성공은 AI의 "완료" 문구가 아니라 결과물로 판정한다 (ADR-09).
</details>

## E. 업계 이해

### Q16. Cognition은 "멀티 에이전트를 만들지 말라"고 했는데 어떻게 생각하나요?
<details><summary>30초 답변</summary>

"그 글의 핵심은 여러 에이전트가 맥락을 공유하지 못한 채 병렬로 '쓰면' 서로 다른 암묵적 결정 때문에 결과가 깨진다는 겁니다.
Cognition도 2026년 후속 글에서 여러 에이전트가 검토나 조언으로 '생각을 보태는' 구조는 잘 되고,
쓰기는 한 줄기로 유지하는 게 핵심이라고 정리했습니다.
제 시스템도 같은 결론입니다. 검수·팩트체크·감사는 여럿이지만, 실제로 결과물이나 설정을 바꾸는 건 한 곳뿐입니다."
</details>

### Q17. LangGraph나 CrewAI 같은 프레임워크를 써봤나요?
<details><summary>지금의 솔직한 답 → 3단계 후 업데이트</summary>

**지금**: "운영 중인 시스템은 프레임워크 없이 파이썬 코드와 클로드 API, 클로드 코드 헤드리스 실행으로 만들었습니다.
에이전트 루프와 상태 전달을 직접 짜보면서 구조를 이해하는 게 먼저라고 판단했고,
지금 같은 시스템을 LangGraph로도 만들어 비교하고 있습니다."

**3단계 후 채울 것**: 직접 짠 버전 대비 LangGraph가 편했던 점(상태 저장·재시작, 그래프 시각화 등)과
과했던 점을 실제 경험으로.
</details>

### Q18. MCP가 뭔가요? 써봤나요?
<details><summary>30초 답변</summary>

"AI가 외부 도구와 데이터에 연결하는 표준 방식입니다. 도구마다 따로 연동 코드를 짜는 대신 MCP 서버 하나로 여러 AI 클라이언트에 붙일 수 있습니다.
저는 노션, 깃허브, 그리고 취몽 데일리 로그 제출을 MCP로 연결해 쓰고 있고,
게임 개발 에이전트용으로 유니티 편집기를 MCP로 조작하는 방식도 검토했습니다."

**꼬리 질문 대비**
- "MCP와 그냥 API 호출의 차이는?" → 도구 설명·입력 형식을 표준으로 노출해서, AI가 어떤 도구가 있고 어떻게 부르는지 스스로 알 수 있다.
</details>

### Q19. 다시 설계한다면 무엇을 바꾸겠나요?
<details><summary>답변 뼈대</summary>

1. **평가셋을 먼저 만든다.** 품질을 숫자로 재는 기준이 늦게 생겼다.
2. **데이터 출처를 처음부터 하나로 모은다.** 공유 DB(hub)를 나중에 만들어서, 9월 기준으로 리포트들이 아직 원본 파일을 따로 읽는다.
3. **사람 승인 기준을 처음부터 "되돌릴 수 있는가"로 정한다.** 전부 승인 → 선조치 후보고로 돌아오는 데 2주 걸렸다.
4. **인증·한도 같은 외부 의존성을 시작 전에 점검한다.** 로그인 만료와 지출 한도 초과가 모두 "실행 중에" 발견됐다.
</details>
