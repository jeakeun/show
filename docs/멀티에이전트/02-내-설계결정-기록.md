# 1단계 · 내 설계 결정 기록 (Architecture Decision Records)

운영 중인 자동화에서 내가 실제로 내린 설계 결정 10개입니다.
각 결정은 **상황 → 대안 → 결정 → 이유 → 대가 → 결과 → 업계 원칙과 연결 → 면접 한 줄** 순서로 적었습니다.
면접 답변 형식(상황·과제·행동·결과)으로 바로 옮길 수 있습니다.

읽는 법:
- 숫자·날짜는 메모리와 운영 기록에 남은 것만 썼습니다. 2026-10-22 검토 에이전트가 문제 27개를 찾아 고친 판입니다.
- **"대안"은 돌이켜 정리한 것**입니다. 기록에는 결론만 남은 경우가 많아서, 면접에서는 "돌아보면 이런 선택지가 있었고"라고 말합니다.
- **"확인 필요"** 는 메인 PC 최신 로그로 채울 곳입니다.
- 여기서 "나"는 운영자(주인)와, 주인의 지시로 일한 클로드 세션을 합쳐 말합니다. 실제로 누가 무엇을 했는지 구분해야 하는 곳은 따로 적었습니다.

## ADR-01. 만드는 AI와 검사하는 AI를 나눈다

**날짜**: 2026-08-27 · **프로젝트**: 유튜브 대본 검수 게이트(`scriptgen.critique_script`)

- **상황**: 대본에 의료 조언 같은 정책 위험 표현이 섞이거나 구독 멘트가 빠질 수 있었다. 업로드는 무인 자동이라 사람이 보지 못한다.
- **대안 (돌이켜 정리)**
  - A. 작성 지시문에 규칙을 더 넣는다
  - B. 같은 AI에게 "다시 검토해"라고 한다
  - C. 별도 검수 AI가 기준표로 채점한다
  - D. 사람이 검토한다
- **결정**: C에 코드 사후검사(제목·의료 단어 검사)를 함께 둔다.
  - 차단급(정책 위험, 구독 멘트 누락)이면 재생성하고, 2번 연속이면 예비 대본으로 바꾼다.
  - 정책 위험이 아니고 예비 대본도 없으면, 등급을 낮춰 그대로 진행한다.
  - 경고급(모호한 훅 등)은 2건 이상일 때만 1회 재생성한다.
  - 검수 API가 장애면 **통과시킨다(fail-open)**. 코드 사후검사는 그대로 유지된다.
- **이유**: 작성 과정을 함께 겪은 AI는 자기 글에 관대해지기 쉽다. 검사 기준을 작성과 분리해야 기준이 흔들리지 않는다. 무인이라 D는 불가능하다.
- **대가**
  - 호출 비용과 시간이 늘어난다.
  - 검수 AI도 틀린다. 9/7~13에 재생성 3건이 있었는데 **3건 모두 검수 오탐**이었다.
    고전실험형 전용인 "훅" 기준을 저녁 리스트형 대본에도 적용한 탓이었다.
    9/14에 슬롯 정보를 검수 AI에 넘겨 기준을 나누는 것으로 고쳤다.
- **결과**: 도입 검증에서 정상 대본 3편은 지적 없이 통과했고, 의료 조언을 넣은 가짜 대본은 정확히 차단했다.
- **AI데일리는 구조가 다르다**: AI데일리의 2차 검수 AI는 문제를 **직접 고친다**. 검수자가 두 번째 작성자인 셈이다.
  순서대로 고치니 충돌은 없지만 "누가 무엇을 바꿨는지" 추적이 어렵다는 대가가 있다. 유튜브처럼 "지적만 하고 작성자가 다시 쓰는" 구조와 비교해 설명할 수 있다.
- **업계 연결**: 평가자-최적화자 패턴. Cognition 2026 후속 글의 리뷰 에이전트 사례와 같은 구조다.
- **면접 한 줄**: "작성 AI와 별개로 기준표를 가진 검수 AI를 붙였습니다.
  검수 AI도 오탐을 내서, 일주일 재생성 3건이 전부 오탐이었던 걸 찾아 슬롯별 기준으로 고쳤습니다."

## ADR-02. 판단 없는 단계는 에이전트로 만들지 않는다

**날짜**: 2026-08-27 · **프로젝트**: 유튜브 파이프라인

- **상황**: 파이프라인을 단계마다 "부서별 에이전트"로 나누는 안이 나왔다.
  - 기록에 남은 판단은 이렇다: "'부서별 에이전트 분리'는 이득 없다고 판단해 기각 (판단 없는 공정에 감독관 격)".
- **결정**: 에이전트로 쪼개지 않고, 판단이나 글쓰기가 필요한 칸에만 언어 모델(LLM)을 둔다.
  - **LLM이 하는 칸**: 대본 작성, 검수, 주간 회고, 팩트체크, 프롬프트 감사, 영어 현지화, 댓글 답글, 시청자 궁금증 정제
  - **코드가 하는 칸**: 슬롯·계열 결정, 렌더링, 업로드, 자막 맞추기
  - 음성(TTS)·이미지·음성인식 모델도 쓰지만 판단 없이 정해진 변환만 하는 부품이라, 에이전트가 아니라 코드에서 부르는 도구로 둔다.
- **이유**: 렌더나 업로드 같은 공정에 판단하는 AI를 두면 감독관만 늘어난 셈이라, 비용과 실패 지점만 늘어난다.
- **대가**: 겉보기에 덜 "에이전트스럽다". 데모의 화려함을 포기했다.
- **결과**: 8/04부터 하루 2편 돌던 코드 파이프라인을 쪼개지 않고 유지했다.
- **업계 연결**: Anthropic "가장 단순한 방법으로 시작하고, 필요할 때만 복잡도를 더하라". 직함 기준 분할을 피했다.
- **면접 한 줄**: "멀티 에이전트를 안 쓰는 결정도 설계입니다.
  판단이 없는 단계까지 에이전트로 만들면 비용과 실패 지점만 늘어서, LLM은 글을 쓰거나 판단하는 칸에만 뒀습니다."

## ADR-03. 분석 AI가 운영 설정을 직접 고치지 못하게 한다

**날짜**: 2026-08-21 시작 → 08-27 가드 → 09-07 4칸 구조로 정리 · **프로젝트**: 코인에서 시작해 전체로

- **흐름**
  1. **8/21** 코인 주간 회고를 만들 때부터 "설정은 제안만, 직접 수정 금지" 규칙이었다. 첫 회고가 결함을 찾아 제안했다.
     트레일링 1.5%/1.5% 설정은 사실상 본전 청산 구조였다. 검토 후 2.0%/1.0%로 적용했다.
  2. **8/27** 감사에서 코인 회고 AI가 쓰기 권한이 열려 있어 임시 분석 스크립트(`_analyze.py`)를 만든 전례를 찾았다.
     그래서 회고 실행 스크립트에 가드를 넣었다.
     - 실행 전에 설정·소스 파일 해시를 백업해 두고, 바뀌면 자동 원복한다.
     - 루트에 새로 생긴 파일은 격리한다.
     - 성공 판정은 리포트 파일이 실제로 있는지로 한다.
  3. **9/6** 회고 AI가 또 임시 스크립트(`_wk.py`)를 만들었고, 가드가 격리했다. 가드가 작동하는 걸 확인했다.
  4. **9/7** 운영자가 Cloud Compass 구조도(읽기 전용 수집 → 고정 규칙 → AI 분석은 제안만 → 승인 → 실행)를 참고하자고 했다.
     이를 수집·규칙·분석·실행 4칸 원칙으로 문서화했다.
     유튜브에는 승인 게이트(`src.approve`)를, AI데일리에는 같은 가드를 넓혔다.
- **대안 (돌이켜 정리)**
  - A. 회고 AI가 직접 수정
  - B. 회고 AI는 제안만 쓰고 다른 경로가 적용
  - C. 사람만 수정
- **결정**: B + 가드. 분석 AI가 직접 고치는 길은 막았다. 적용하는 길은 프로젝트마다 다르다.
  - 유튜브는 `src.approve` 코드 한 곳으로 모았다. 이전본을 보관하고 승인 기록을 남긴다.
  - 코인은 자동 적용 장치가 없다. 운영자가 고른 안을 클로드 코딩 세션이 적용하고 보고한다.
  - 날짜 라벨 같은 기계적 정리는 코드(`promptlint`)가 자동으로 고치되, 실패하면 원복한다.
- **이유**: 분석이 틀려도 실행에 바로 번지지 않는다. 바뀐 건 기록이 남아 추적하고 되돌릴 수 있다.
- **대가**: 적용까지 한 단계가 늘어난다. 이 비용은 ADR-07에서 다시 조정했다.
- **업계 연결**: 권한 최소화. Cognition 2026 "생각은 여럿이 보태고, 쓰기는 한 줄기로".
- **면접 한 줄**: "회고 AI가 임시 파일을 만든 전례를 보고, 분석 AI는 제안만 쓰게 하고 보호 파일이 바뀌면 자동 원복하는 가드를 넣었습니다.
  열흘 뒤 같은 일이 생겼을 때 가드가 막았습니다."

## ADR-04. 숫자·고정 문자열은 코드가, 해석과 문장은 AI가

**날짜**: 2026-08-27 ~ 09-07 · **프로젝트**: 유튜브 회고, 유튜브 검수, AI데일리

세 사건이 같은 교훈을 줬다.

1. **잘못된 집계 → 잘못된 해석 (8/26 → 8/27 발견)**
   - 유튜브 회고는 추적 중인 영상 50편의 합으로 일별 조회수를 계산했다. 옛 영상이 목록에서 밀리면 숫자가 떨어지는 착시가 생겼다.
   - 회고 AI가 이 숫자(-697회, "-76% 급락")로 원인 서사까지 지어냈다.
   - 8/27 감사가 원인을 찾았고, 8/30 회고가 "오진"이라고 스스로 정정했다(실제로는 +44% 회복).
   - 이후 50편 표본 합계 계산을 없앴다.
2. **AI에게 고정 문자열을 시키고 AI로 검사한 자기강화 루프 (8/27~29)**
   - 규칙은 "제목에 '뇌 자가테스트 #N' 필수"였고, 이 규칙을 검수가 검사했다.
   - 모델이 2번 빠뜨리자 예비 대본으로 넘어갔고, 회차 번호가 멈춘 채 다음 날도 같은 번호를 요구했다.
   - 그 결과 저녁 자가테스트가 사흘 동안 빠졌다. 8/30 감사가 발견했다.
   - 수정: 검사를 없애고, **회차 표기는 코드가 제목에 자동으로 붙인다.**
3. **AI가 손으로 센 카운터 부풀림 (9/6 발견 → 9/7 수정)**
   - AI데일리의 "연속 0건" 카운터가 실제(9일)보다 부풀어 있었다(12일). 증가한 날 리셋을 안 했다.
   - 9/7에 회차별 실측 기록(`tech_counts.jsonl`)을 남기고 `streaks.py` 가 계산하게 바꿨다.
- **대안 (돌이켜 정리)**: A. 지시문에 "정확히 세라"를 강화 / B. 코드가 계산하거나 붙여서 AI에게 넘김
- **결정**: B. 계산, 누적 상태, 정해진 형식의 문자열은 코드. 해석과 문장은 AI. 쉬운 설명(ELI5)에도 원문에 없는 숫자가 나오면 다시 쓰게 하는 검사를 둔다.
- **이유**: AI는 셈이나 누적 상태 유지에 약하고, 틀려도 그럴듯하다. 코드는 매번 같은 답을 낸다.
- **대가**: 데이터를 구조화해서 기록하는 일이 늘었다.
- **결과**: 카운터 계산 근거가 파일로 남아 감사할 수 있게 됐다. 전환 후 정확도는 **확인 필요** (9/7 기록에 "검증 필요"로 남음).
- **면접 한 줄**: "AI에게 맡길지 코드에게 맡길지는 '매번 같은 답이 나와야 하는가'로 나눴습니다.
  고정 문자열을 AI에게 쓰게 하고 AI로 검사했다가 사흘간 영상이 빠지는 루프를 겪은 뒤, 그런 건 코드가 붙이게 바꿨습니다."

## ADR-05. 회고는 다른 AI가 반박 검증한다

**날짜**: 2026-08-27 · **프로젝트**: 유튜브 주간 회고 팩트체크(`insights._factcheck`)

- **상황**: 주간 회고 AI가 쓴 전략(플레이북)이 다음 주 대본 방향이 된다. 출처 없는 주장, 표본이 적은 결론, 과한 목표가 섞이면 그대로 실행된다.
- **결정**: 별도 AI가 회고를 반박 검증한다.
  - 출처 없는 주장은 삭제하고, 표본 부족은 표시하고, 과한 목표는 낮춘다.
  - 리포트에 검증 노트를 붙인다.
  - 길이 가드를 둔다. 검증 AI가 리포트를 요약해 버리는 오작동을 막기 위해서다.
- **이유**: 회고 AI는 자기가 세운 가설에 유리하게 해석하기 쉽다. 반박 역할을 따로 둬야 균형이 맞는다.
- **대가와 시행착오**
  - 팩트체크 AI는 회고 결과를 **직접 고치는** 두 번째 작성자다. 순서대로 고치니 충돌은 없지만, 원문과 수정본을 둘 다 남겨야 추적된다.
  - 첫 실전에서 출력 한도에 걸려 잘렸다. 이때 통과(fail-open)가 정상 작동해 회고 자체는 나갔고, 이후 한도를 올렸다.
  - 비용 때문에 9/7에 검증 모델을 소넷에서 하이쿠로 내렸다.
- **결과**: 9/14 적용된 플레이북은 팩트체크 지적대로 목표치가 조정됐다.
- **관련 원칙**: 대화형 작업에서도 8/23부터 같은 원칙을 썼다. 클로드가 낸 전략 제안과 코드 변경을 검토 에이전트가 먼저 반박하게 했더니,
  첫 적용에서 과대 목표치·규칙 충돌·정책 위험·무인 실행 버그 6건을 잡았다.
- **면접 한 줄**: "회고 AI가 쓴 전략은 다른 AI가 반박부터 합니다. 출처 없는 주장은 지우고, 표본이 적으면 표시하고, 과한 목표는 낮춥니다."

## ADR-06. 감사는 읽기 전용으로

**날짜**: 2026-08-27 첫 전수 감사, 이후 매주 일요일 10:00 · **프로젝트**: 자가감사

- **상황**: 프로젝트가 늘면서 리포트가 실제 데이터와 맞는지 아무도 대조하지 않았다.
- **결정**
  - **8/27 첫 전수 감사**: 읽기 전용 감사 에이전트 3기를 병렬로 돌려, 리포트의 주장을 원본 데이터와 대조했다. 3기를 어떤 기준으로 나눴는지는 **확인 필요**.
  - **주간 자동 감사**: 헤드리스 클로드 1회 실행으로 같은 대조를 한다. 감사 중에도 보호 파일 해시 가드를 켠다.
    스케줄러 상태와 API 비용은 스크립트가 미리 뽑아 준다.
- **이유**: 감사는 넓게 퍼지는 읽기 작업이라 나눠도 서로 충돌할 쓰기가 없다. 읽기 전용이면 감사가 틀려도 시스템을 망가뜨리지 않는다.
- **결과**
  - 8/27 첫 감사: 노출된 API 키, 코인봇 수수료 계산 오류(20.5%), AI데일리의 없는 회차 기록(유령 데이터)을 찾았다.
    노출 파일은 지웠지만 키 재발급은 하지 않았다 (꼬리 질문 대비).
  - 1회차 주간 감사 시험(8/27): 8건을 발견했고, 검증 후 6건을 실제로 고쳤다.
  - 9/6 감사
    - 채널 전체 조회수 값이 9/2부터 사실상 멈춰 있었다(5일 +14회). 회고 추세가 왜곡될 상황이었다.
      그래서 영상별 증가분의 합으로 추세를 보고, "정지" 표시를 붙이게 고쳤다.
    - 손절 15건 모두 -2%를 넘겨 체결됐다(평균 -2.94%).
- **교훈**: 감사 지적 하나를 메인 클로드 세션이 "오탐"이라고 반박했다. 로그를 다시 보니 **감사가 맞았다**.
  2부작의 2부가 저녁 자가테스트 슬롯을 3일마다 잡아먹고 있었다. → 감사도, 감사를 반박하는 쪽도 검증 대상이다.
- **업계 연결**: Anthropic 리서치 시스템과 같은 "읽기 중심 병렬" 구조.
- **면접 한 줄**: "감사는 읽기 전용이라 병렬로 돌려도 충돌이 없습니다.
  첫 감사에서 노출된 API 키와 수수료 계산 오류를 찾았고, 감사를 반박한 쪽이 틀린 적도 있어서 반박도 검증 대상으로 둡니다."

## ADR-07. 사람 승인 위치는 "되돌릴 수 있는가"로 정한다

**날짜**: 8월 자동 반영 → 9/7 승인 게이트 → 9/21 선조치 후보고 · **프로젝트**: 유튜브 중심, 전체 원칙

- **흐름**
  1. **8월**: 회고 AI가 플레이북을 바로 반영했다.
  2. **9/7**: 분석은 제안만 하게 바꾸면서, 모든 회고 제안을 사람이 승인하게 했다.
  3. **9/20**: 플레이북이 승인 대기로 하루 묵어 9/21 적용 시작을 놓쳤다. 비개발자인 운영자에게 승인 판단도 부담이었다.
  4. **9/21**: 기준을 "되돌릴 수 있는가"로 바꿨다.
- **반대 방향의 교훈**: 품질 문제로 이미 올린 영상을 지우고 다시 올린 적이 있다. 유튜브가 중복으로 보고 노출을 거의 주지 않았다(16시간 조회 2회).
  밖으로 나간 것은 되돌릴 수 없었다.
- **결정**
  - 되돌릴 수 있는 플레이북·프롬프트 개선은 자동 적용한다(`auto_approve`).
  - 이전본을 보관하고, 프롬프트는 문법·스모크 테스트에 실패하면 자동 원복한다. 적용 후 폰과 바탕화면으로 보고한다.
  - 돈이 드는 결정, 영상 삭제·공개 전환, 실전 매매 전환은 계속 사람이 정한다. 리포트에 A/B/C/D 선택지로 올라온다(9/28~).
  - 품질은 업로드 **전** 게이트로만 잡고, 이미 나간 영상은 교체하지 않는다.
- **이유**: 승인의 가치는 되돌릴 수 없는 피해를 막는 데 있다. 되돌릴 수 있는 변경까지 막으면 속도만 잃는다.
- **결과**: 9/21부터 자동 적용 후 보고로 전환했다. 이후 실제 자동 적용 기록은 **확인 필요**.
- **업계 연결**: Human-in-the-loop 위치 설계. 비가역 행동 앞에 게이트를 둔다.
- **면접 한 줄**: "처음엔 자동 반영, 다음엔 전부 승인으로 갔다가 둘 다 문제를 겪었습니다.
  지금은 되돌릴 수 있는 건 이전본을 남기고 자동 적용 후 보고, 되돌릴 수 없는 건 사람이 고릅니다."

## ADR-08. 역할마다 모델을 다르게, 비용은 호출마다 기록

**날짜**: 2026-09-07 · **프로젝트**: 유튜브 (`src/apicost.py`)

- **상황**: 실측 월 US$51(앤트로픽) + 제미나이 약 ₩6천. 목표는 US$30 이하.
- **결정**
  - 판단 난이도에 맞춰 모델을 배정했다. 주간 분석은 상위 모델(Opus), 대본은 중간 모델(Sonnet), 검수·팩트체크는 하이쿠.
  - 대본 지시문은 프롬프트 캐싱으로 재사용했다.
  - 회고는 일요일에만 돌린다.
  - 모든 호출의 비용을 기록하고, 대시보드에 "매일 운영비"와 "주간 분석비"로 나눠 보여준다.
- **이유**: 측정하지 않으면 줄일 수 없다. 모든 칸에 상위 모델을 쓸 이유가 없다.
- **대가·실패 (9/13)**
  - 비용을 줄이려고 회고 출력 한도를 16,000 → 10,000 토큰으로 낮췄다. 그런데 두 가지를 놓쳤다.
    - 상위 모델은 사고(thinking) 토큰도 이 한도에 포함된다.
    - 리포트와 플레이북 출력만 해도 약 1.2만 토큰이라, 원래 10,000은 부족했다.
  - 결과는 본문 0자 실패였다. US$0.76이 낭비됐고 실패 알림도 없었다.
  - 수정 내용은 이렇다.
    - 한도를 24,000으로 올렸다.
    - 사고 강도를 중간으로 낮췄다.
    - 한도 초과로 멈추면 명시적 오류로 처리하게 했다.
    - 실패하면 폰으로 알린다.
- **결과 (실측)**
  - 9/7~13 기준선: 대본 생성 17회로 14편을 만들었다. 재생성은 3건(21%)이었다.
  - 대본 생성 비용은 주 US$3.72(호출당 약 US$0.16).
  - 하이쿠 검수 도입 검증 호출 1건은 US$0.0015.
  - 월 총액이 목표에 도달했는지는 **확인 필요**.
- **업계 연결**: 멀티 에이전트는 토큰을 많이 쓴다 (Anthropic 측정 약 15배). 그래서 역할별 모델 선택과 비용 측정이 필수다.
- **면접 한 줄**: "역할마다 모델을 다르게 쓰고, 모든 호출 비용을 기록합니다.
  비용을 줄이다 사고 토큰 때문에 회고가 실패한 적이 있어서, 지금은 한도 초과를 명시적 오류로 잡고 실패하면 바로 알림이 옵니다."

## ADR-09. 실패는 조용히 나지 않게, 성공은 결과물로 판정

**날짜**: 2026-08-23 ~ 09-08 · **프로젝트**: 전체 (폰 알림 `notify`)

- **상황**
  - AI 출력 문구로 성공을 판정하다 오판한 일이 반복됐다.
    - 8/23 AI데일리는 정상 리포트를 만들었는데 "완료:" 문구를 빼먹어 실패로 판정됐다.
    - 9/6 자가감사도 같은 일을 겪었다.
  - 8/26 제미나이 월 지출 한도 초과로 이미지·음성 생성이 막혔다. 영상 2편이 이모지 배경과 예비 음성으로 **조용히** 발행됐다.
  - 헤드리스 클로드의 로그인 만료로 무인 작업들이 멈췄다. 8/27이 처음이고 9/8에 다시 일어났다.
- **결정**
  - 성공 판정을 AI 출력 문구 대신 **결과물 파일 실존 + 종료 코드**로 바꿔 왔다.
    - AI데일리: 500바이트 초과 (8/23)
    - 코인 주간 회고: 리포트 실존 (8/27)
    - 자가감사: 800바이트 초과 (9/6)
    - 단, AI데일리 검수 단계는 아직 "검수완료:" 문구로 판정한다.
  - 자동화 실패와 품질 저하 발행은 바탕화면 경고 파일과 폰 푸시로 알린다. 알림이 실패해도 본 작업은 죽지 않게 했다.
- **이유**: 운영자가 "왜 안 올라갔지?"라고 묻기 전에 시스템이 먼저 알려야 한다. AI 출력 형식은 흔들리니 판정은 관측 가능한 결과물로 한다.
- **남은 과제**: 시작 전에 로그인 상태를 미리 점검하는 기능은 아직 제안 단계다. 같은 장애가 두 번 났으니 우선순위가 높다.
- **업계 연결**: 에이전트 관측성(observability).
- **면접 한 줄**: "AI가 '완료'라고 말하는 것과 실제로 완료된 것은 다릅니다. 그래서 성공은 결과물로 판정하고, 조용한 품질 저하도 알림으로 올라오게 했습니다."

## ADR-10. 법 규정 검사는 AI가 아니라 규칙 엔진으로

**날짜**: 2026-09 (개발 중) · **프로젝트**: market-compass

- **상황**: 마케팅 메시지가 정보통신망법이나 카카오 정책을 어기면 제재·과태료를 받는다. 틀리면 안 되고, 왜 막혔는지 설명할 수 있어야 한다.
- **결정**
  - 규정 검사(Guard)는 코드 규칙 R01~R12와 테스트로 만든다.
  - 사람이 두 번 승인한다.
  - 발송(Dispatch)은 한 경로에서만 한다.
  - 숫자는 코드만 계산한다.
  - 대상 판단(Radar)과 문구 생성 중 어디까지 AI가 맡는지는 **확인 필요**.
- **이유**: 법 규정 판정은 매번 같아야 하고, 규칙 번호로 이유를 설명할 수 있어야 한다. AI 판정은 그럴듯하지만 재현과 설명이 어렵다.
- **결과**: 9/7 기준 Guard 테스트 24/48 통과(2일차). 이후 진행은 **확인 필요**.
- **업계 연결**: 가드레일을 결정적 코드로 두는 설계.
- **면접 한 줄**: "자동보다 '안 걸리게'가 목표라, 규정 검사는 AI가 아니라 테스트가 붙은 규칙 엔진으로 만들고 발송 경로는 하나로 묶었습니다."

## 아직 약한 곳 (면접 전에 채울 것)

솔직하게 적어둡니다. 면접관이 파고들 지점입니다.

1. **체계적인 평가셋이 없다.** 검수 게이트 검증은 정상 대본 3편과 의료 조언 가짜 대본 수준이었다. → 2단계에서 평가셋을 만들고 실측한다.
2. **"에이전트 1개 vs 여러 개"를 직접 비교한 숫자가 없다.** → 2단계.
3. **프레임워크 실전 경험이 없다.** LangGraph는 검수 루프·승인·병렬 처리의 구조를 흉내 낸 학습 예제를 돌려본 수준이다 ([03 문서](03-LangChain-LangGraph-LangFlow.md)). → 2단계에서 LangGraph로 프로젝트를 만든다.
4. **RAG 경험이 없다.** → [04-RAG.md](04-RAG.md), 2단계 프로젝트에 넣는다.
5. **에이전트 사이 정보 전달이 대부분 파일 기반이다.** 단순하고 추적하기 쉽다는 장점은 있다.
   하지만 지휘자가 하위 에이전트를 직접 부르고 결과를 받는 구조를 코드로 짜본 적은 없다. → 2단계.
6. **두 번째 작성자 문제.** AI데일리 검수와 유튜브 팩트체크는 앞 단계 결과를 직접 고친다. "쓰기 단일화"를 말할 때 이 예외를 먼저 인정할 수 있어야 한다.
