## 왜 이 순서인가

1. **이미 운영 중인 것부터 설명한다.** 면접관이 가장 믿는 건 "실제로 돌려본 경험"입니다.
   새로 만드는 것보다, 지금 있는 걸 정확히 설명하는 게 먼저입니다.
2. **공고가 요구하는 도구(LangGraph·RAG·레거시 연계)로 프로젝트 하나를 끝까지 만든다.**
   운영하면서 손으로 짜본 경험(재시도 상한, 사람 승인, 병렬 감사)이 있어서,
   LangGraph의 각 기능이 어떤 문제를 푸는지 비교하며 배울 수 있습니다.
3. **평가 숫자를 만든다.** "에이전트를 여러 개로 나눴더니 정답률이 X% 올랐고 비용은 Y배 들었다"를 직접 잰 숫자로 말합니다.
4. **면접 질문으로 말해본다.** 아는 것과 말할 수 있는 것은 다릅니다.

### 2단계 프로젝트 제안: "운영 비서 에이전트"

내 자동화 시스템에 대해 물으면 문서와 데이터를 찾아 근거와 함께 답하고, 필요하면 조치를 제안합니다. 조치는 승인을 받은 뒤에만 실행합니다.
예: "지난주 저녁 쇼츠 조회수가 왜 떨어졌어?", "코인봇 손절 규칙을 왜 바꿨지?", "이번 주 API 비용은?"

```
질문 → [지휘자] 질문 종류 판단 (라우팅)
          ├─ [문서 검색 에이전트]  설계 기록·회고 리포트 RAG        ┐ 읽기라 병렬
          └─ [데이터 조회 에이전트] 레거시 DB·API 도구 (읽기 전용)   ┘
       → [작성자 1명] 출처를 붙여 답변
       → [검수자] 모든 문장에 근거가 있는지 검사 → 없으면 다시 쓰기
       → (조치가 필요하면) 쓰기 도구는 사람 승인 뒤에만 실행
```

| 공고 요구 | 이 프로젝트에서 |
|---|---|
| LangGraph | 지휘자·병렬·검수 루프·승인을 그래프로 |
| LangChain | 모델·도구·RAG 부품, 미들웨어 |
| LangFlow | 문서 검색 흐름을 LangFlow로도 만들어 코드와 비교 |
| RAG | 내 설계 기록·회고 리포트로 청킹·임베딩·하이브리드 검색, 평가셋 |
| 레거시 연계 | 공유 DB(hub)와 작은 Spring Boot API를 레거시 역할로 두고 도구로 연결 |

**왜 이 주제인가**
- 공고 요구 다섯 가지를 프로젝트 하나에 다 담습니다.
- 실제로 운영 중인 시스템의 데이터라 "진짜 이야기"가 됩니다.
- 운영자인 내가 매일 쓸 수 있습니다.

| # | 만드는 것 | 배우는 것 |

## 공부하는 방법

- 각 문서 끝의 **면접 질문**을 소리 내어 답해보고, 접힌 답과 비교합니다.
- 막히는 질문은 클로드에게 "이 질문 모의면접 해줘"라고 하면 꼬리 질문까지 이어서 연습합니다.
- 숫자는 **실제 운영 기록과 실제 실행 결과에서 온 것만** 씁니다. "확인 필요"는 메인 PC 최신 로그로 채웁니다.
- **아직 안 한 일을 "하고 있다"고 말하지 않습니다.** 검토 에이전트가 이런 표현을 여러 개 잡아내서 고쳤습니다.
