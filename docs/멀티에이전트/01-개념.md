# 0단계 · 개념 — 에이전트와 멀티 에이전트

## 1. 한 줄 정의

| 용어 | 정의 | 비유 |
|---|---|---|
| **에이전트** | AI 모델 + 도구 + 반복 루프. 목표를 받으면 "생각 → 도구 사용 → 결과 확인"을 스스로 반복하다가 끝났다고 판단하면 멈춤 | 일을 맡기면 알아서 처리해 오는 직원 |
| **멀티 에이전트** | **각자 따로 대화 맥락(context)을 가진** AI 여러 개가 일을 나눠 하고, 코드나 지휘 에이전트가 조율 | 팀 |
| **워크플로** | 순서는 코드가 정하고, 일부 칸만 AI가 하는 것 | 공장 라인 |

**핵심**: 멀티 에이전트의 본질은 "역할 이름이 여러 개"가 아니라 **"맥락이 분리돼 있다"** 는 점입니다.
같은 모델이라도 다른 대화창에서 다른 지시문과 자료만 보고 일하면 다른 에이전트입니다.
그래서 "왜 나눴나요?"라는 질문은 사실 **"왜 맥락을 분리했나요?"** 라는 질문입니다.

## 2. 왜 나누나 — 얻는 것 4가지

| 이유 | 설명 | 내 프로젝트 예 |
|---|---|---|
| **맥락 보호** | 한 대화에 다 넣으면 길어지고 산만해짐. 하위 에이전트가 자기 일만 보고 **요약만** 돌려줌 | 8/27 전수 감사: 감사 에이전트 3기가 각자 조사하고 발견만 보고 |
| **병렬** | 서로 독립적인 일을 동시에 | 8/27 감사 에이전트 3기 병렬 |
| **전문화** | 역할마다 지시문·도구·모델을 다르게 | 대본은 중간급 모델, 검수는 싼 하이쿠 |
| **견제** | 만든 쪽과 검사하는 쪽을 분리. 같은 맥락 안에서는 자기 결과에 관대해짐 | 대본 작성 AI ↔ 검수 AI, 회고 AI ↔ 팩트체크 AI |

Anthropic의 리서치 시스템이 대표 사례입니다.
지휘 에이전트(Claude Opus 4)가 계획을 세우고 하위 에이전트(Claude Sonnet 4) 여럿에게 조사를 나눠 맡겼더니,
Opus 4 혼자 할 때보다 **내부 리서치 평가에서 90.2% 더 좋은 결과**가 나왔습니다. (2025-06, 출처 1)

## 3. 대가 — 잃는 것 4가지

| 대가 | 설명 |
|---|---|
| **비용** | Anthropic 측정으로 멀티 에이전트는 일반 채팅의 **약 15배 토큰**을 씀 (출처 1). 같은 글에서 성능 차이의 상당 부분이 "토큰을 얼마나 썼나"로 설명된다고 함 → 성능 향상 중 일부는 "돈을 더 써서"라는 뜻 |
| **지연** | 에이전트끼리 주고받는 시간만큼 느려짐 |
| **오류 전파** | 앞 에이전트의 실수가 뒤로 그대로 넘어감 |
| **맥락 단절** | 각자 일부만 보니 서로 다른 "암묵적 결정"을 내림 → 합치면 어긋남 (출처 2) |

## 4. 5가지 기본 패턴 (Anthropic "Building effective agents", 2024-12, 출처 3)

| 패턴 | 어떻게 돌아가나 | 언제 쓰나 | 내 프로젝트 예 |
|---|---|---|---|
| **① 프롬프트 체이닝** | A의 결과를 B가 받고, B의 결과를 C가 받음. 중간에 코드 검사 가능 | 단계가 고정된 일 | 유튜브: 대본 → 사후검사 → 음성·자막 → 렌더 → 업로드 / 집가 M1~M6 |
| **② 라우팅** | 입력을 분류해서 맞는 처리로 보냄 | 종류마다 처리가 다를 때 | 정확한 사례 없음 (아래 주의) → 2단계에서 질문 종류별로 보내는 지휘자를 만듦 |
| **③ 병렬화** | 일을 쪼개 동시에(나누기) 또는 같은 일을 여러 번 해서 투표 | 독립적인 일이 여러 개일 때 | 8/27 읽기 전용 감사 에이전트 3기 |
| **④ 오케스트레이터-작업자** | 지휘자가 일을 **그때그때** 쪼개 맡기고 결과를 합침 | 몇 갈래로 나눌지 미리 모를 때 | 자가감사 방법론, 클로드 코드의 서브에이전트 |
| **⑤ 평가자-최적화자** | 만들기 → 평가 → 피드백 → 다시 만들기 반복 | 평가 기준이 분명할 때 | 유튜브 대본 검수 게이트(차단급이면 재생성) |

여기에 **자율 에이전트**(도구를 쓰며 스스로 경로를 정함)가 더해집니다. 예: AI데일리 채용 수집.

- ③과 ④의 차이: ③은 **나눌 칸이 미리 정해져 있고**, ④는 **지휘자가 상황을 보고 나눕니다**.
- **라우팅 주의**: 유튜브는 아침·저녁 슬롯마다 대본 방식이 다르지만, 이건 입력을 분류하는 게 아니라 **시간표 코드가 정하는 것**이라 라우팅이 아닙니다.
  면접에서 라우팅 예로 들면 반박당하기 쉽습니다.
- **AI데일리 검수는 ⑤가 아닙니다**: 검수 AI가 지적해서 작성 AI가 다시 쓰는 반복이 아니라, 검수 AI가 **직접 고치는** 2단 체이닝(①)입니다.

## 5. 업계 논쟁 — 언제 쓰고 언제 안 쓰나

이 부분이 면접에서 실력이 드러나는 곳입니다.

**Anthropic (2025-06, 출처 1)**
- 넓게 퍼져서 찾는 일(리서치처럼 **읽기 중심**)에 멀티 에이전트가 강하다.
- 모든 에이전트가 같은 맥락을 공유해야 하거나 서로 의존이 많은 일에는 아직 잘 안 맞는다.

**Cognition, Devin 개발사 (2025-06 "Don't Build Multi-Agents", 출처 2)**
- 원칙 1: **맥락을 공유하라.** 각 행동은 다른 부분이 내린 결정을 모두 알고 해야 한다.
- 원칙 2: **행동에는 암묵적 결정이 담긴다.** 코드를 병렬로 나눠 쓰게 하면 각자 다른 스타일·가정을 택해서 합치면 깨진다.

**Cognition 후속 (2026-04 "Multi-Agents: What's Actually Working", 출처 4)**
- 병렬로 여럿이 **쓰는** 구조는 여전히 잘 안 된다.
- 여러 에이전트가 **생각(검토·조언)을 보태고, 쓰기는 한 줄기로 유지하는** 구조는 잘 된다.
  예: 별도 리뷰 에이전트가 코드를 검토 (외부 요약 기준, 정확한 수치는 원문 확인 필요).

**정리하면**

> **읽기는 나눠도 되고, 쓰기는 한 곳으로 모은다.**

더 정확히 말하면 문제는 **같은 결과물을 동시에 여럿이 쓰는 것**입니다.
앞 단계 결과를 다음 단계가 순서대로 고치는 건 충돌이 없지만, 누가 무엇을 바꿨는지 기록을 남겨야 합니다.

내 설계와 연결하면:
- 8/27 감사 에이전트 3기를 병렬로 돌려도 안전했던 이유: **읽기 전용**이라 서로 충돌할 쓰기가 없음.
- 분석 AI가 운영 설정을 직접 고치는 길은 막았다. 유튜브는 적용을 `src.approve` 코드 한 곳으로 모았고, 코인은 운영자가 고른 안을 클로드 코딩 세션이 적용한다.
- 유튜브 대본: 검수 AI는 지적만 하고, 대본을 쓰는 건 작성 AI 하나뿐.
- 예외도 안다: AI데일리 검수 AI와 유튜브 팩트체크 AI는 앞 단계 결과를 **직접 고치는 두 번째 작성자**다. 순차라 충돌은 없지만 추적이 어려워지는 대가가 있다.

## 6. 에이전트를 늘리기 전에 묻는 5가지

1. **에이전트 하나로 먼저 해봤나?** 처음부터 여럿으로 시작하지 않는다.
2. **어디서 실패하나?** 맥락이 넘치나, 느린가, 검증이 안 되나. 실패 원인이 "나누기"로 해결되는 종류인가.
3. **나누는 기준이 "맥락"인가 "직함"인가?** "기획 담당·개발 담당·테스트 담당"처럼 직함으로 나누면
   넘길 때마다 맥락이 끊긴다. 같은 자료를 쓰는 일은 한 에이전트에 묶는다.
4. **쓰기는 한 곳인가?** 여럿이 같은 결과물을 동시에 고치지 않는가.
5. **늘어난 비용만큼 좋아졌는지 쟀나?** 재지 않았다면 아직 모르는 것이다.

## 7. 면접에서 이렇게 말하기 (30초)

> "멀티 에이전트는 따로 맥락을 가진 AI 여러 개가 일을 나누는 구조입니다.
> 맥락 보호, 병렬 처리, 역할별 모델 선택, 그리고 만든 쪽과 검사하는 쪽의 분리가 장점이지만,
> 토큰 비용이 크게 늘고 맥락이 끊기는 대가가 있습니다.
> 그래서 저는 읽기 작업은 병렬로 나누고, 실제로 무언가를 바꾸는 쓰기는 한 곳으로 모으는 원칙으로 설계했습니다.
> 예를 들어 제 유튜브 자동화에서 회고 AI는 제안 파일만 쓰고, 실제 전략 변경은 코드 한 곳에서만 일어납니다."

## 8. 스스로 점검 질문

<details><summary>Q1. 같은 모델을 두 번 부르면 멀티 에이전트인가?</summary>

맥락이 분리돼 있다면 그렇다. 핵심은 모델 종류가 아니라 각자 다른 지시문·자료·대화 기록을 가지는지다.
대본 작성과 검수가 둘 다 클로드여도, 검수는 작성 과정의 대화를 모른 채 결과물과 기준표만 본다.
</details>

<details><summary>Q2. 멀티 에이전트가 Anthropic 실험에서 90.2% 좋았다면 항상 쓰는 게 낫지 않나?</summary>

아니다. 그 실험은 읽기 중심 리서치였고, 같은 글에서 토큰을 약 15배 썼다고 밝힌다.
성능 향상의 상당 부분이 "더 많이 썼기 때문"이다. 쓰기 중심 작업은 Cognition이 지적한 맥락 단절 문제가 크다.
작업 성격과 비용 대비 효과를 보고 정한다.
</details>

<details><summary>Q3. 병렬화와 오케스트레이터-작업자의 차이는?</summary>

병렬화는 나눌 칸이 미리 정해져 있다 (예: 8/27 감사관 3기).
오케스트레이터는 지휘자가 입력을 보고 몇 개로 어떻게 나눌지 그때그때 정한다.
</details>

<details><summary>Q4. 내 프로젝트에서 "쓰기 단일화"를 지킨 예와 그 이유는?</summary>

4칸 구조. 분석 AI는 리포트와 제안 파일만 쓰고, 운영 설정을 직접 고치지 못한다.
- 유튜브는 적용을 `src.approve` 코드 한 곳으로 모았다. 이전본을 보관하고 기록을 남긴다.
- 보호 파일을 AI가 바꾸면 가드가 원복하고 폰으로 알린다. 실제로 9/6 코인 회고 AI가 만든 임시 스크립트를 가드가 격리했다.
- 예외: AI데일리 검수와 유튜브 팩트체크는 앞 단계 결과를 직접 고치는 순차적 두 번째 작성자다.
</details>

<details><summary>Q5. "기획 에이전트·개발 에이전트·QA 에이전트"로 나누는 설계의 위험은?</summary>

직함 기준 분할이라 넘길 때마다 맥락이 끊기고, 각자 다른 암묵적 결정을 내린다.
같은 자료를 쓰는 일은 묶고, 쓰기는 한 에이전트에 모으고, 다른 에이전트는 검토·조언만 하게 바꾸는 게 안전하다.
</details>
