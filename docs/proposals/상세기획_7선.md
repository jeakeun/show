### 팀 규칙
1. **M5(채점기) 담당자만 채점 코드를 수정**한다. 나머지 5명은 읽기만.
2. **M1(데이터) 담당자가 W0에 원본을 파일로 떠서 공유.** 6명이 각자 API를 부르지 않는다.
3. 모듈 경계는 **파일(parquet/jsonl)** 로 자른다. 함수 호출로 엮지 않는다 → 각자 독립 실행 가능.
4. 모듈마다 **입출력 테스트 5개를 사람이 직접 작성**. 이건 AI에게 안 맡긴다.
5. 매주 금요일 **성능표 셀 1개 이상 갱신**. 못 채우면 그 주는 실패로 기록.

### 공통 폴더 규약
```
data/raw/         원본 (건드리지 않음)
data/interim/     모듈별 중간 산출물
data/processed/   학습·평가용 최종본
schemas/          JSON 스키마 6개 (W1에 동결)
modules/m1..m6/   각자 작업 폴더
eval/             채점기 (M5 전용)
reports/          주차별 성능표
```

# 【A】 공공입찰 낙찰 예측 · 적격 자동판별 — 사업성 카드

## A-1. 제품 한 줄
> **"우리 회사가 딸 수 있는 공고만 골라주고, 얼마를 써야 하는지 알려준다."**

**타깃**: 조달 참여 중소기업 / 입찰 대행사 / 건설·용역 영업팀

## A-2. 문제를 숫자로

| 현재 상태 | 우리가 바꾸는 것 |
|---|---|
| 하루 공고 수백 건을 담당자가 눈으로 스캔 | **상위 N건으로 압축** → 검토 시간 절감률(%) |
| 투찰가를 과거 경험·감으로 결정 | **낙찰가 예측 MAPE(%)** 로 대체 |
| "넣어볼걸" / "괜히 넣었네"를 사후에 앎 | **과거 데이터로 우리 전략 백테스트** → 낙찰 적중률 |

**발표용 핵심 문장**: *"최근 12개월 공고 N건에 우리 전략대로 참여했다면, 실제 검토량은 X% 줄고 낙찰 적중률은 Y%였다."*

## A-3. 데이터 (확인됨)

| 데이터 | 출처 | 쓰는 이유 |
|---|---|---|
| 입찰공고정보서비스 | data.go.kr/data/15129394 | 물품·용역·공사·외자 공고, 추정가격, **면허제한·지역제한**, 공고 변경이력 |
| 낙찰정보서비스 | data.go.kr/data/15129397 | **개찰결과, 최종 낙찰자, 개찰 순위, 복수예비가격**, 유찰·재공고 |
| 공공데이터개방표준서비스 | data.go.kr/data/15058815 | 입찰·낙찰·계약을 공고일/개찰일/계약일 기준으로 표준 제공 |

**W0에 반드시 확인할 것**
- [ ] API 키 발급 소요시간 (당일 승인 여부)
- [ ] **공고 ↔ 낙찰 매칭키가 실제로 붙는가** ← 이 프로젝트 최대 리스크. 공고번호+차수 조합 확인
- [ ] 최근 12개월 공고·낙찰 각 5,000건 이상 수집 가능한가
- [ ] 복수예비가격 필드가 실제로 채워져 있는 비율

## A-4. 정답 라벨 설계
| 예측 대상 | 라벨 출처 |
|---|---|
| 낙찰가(또는 낙찰률 = 낙찰가/추정가격) | 낙찰정보서비스 최종 낙찰금액 |
| 우리 회사 적격 여부 | 공고문의 면허·지역·실적 제한 vs 가상 회사 프로필 → **규칙으로 정답 생성 후 표본 100건 사람 검수** |
| 낙찰 성공 여부 | 개찰 순위 1위 여부 |

> **시점 분리 필수**: 학습은 ~2025년, 평가는 2026년 공고. 미래 정보가 피처에 들어가면 성능이 가짜가 됩니다.

## A-5. 아키텍처
```
M1 공고수집 ─┐
             ├─→ M3 요건추출(LLM) ─→ M4 적격판별 ─┐
M2 낙찰수집 ─┘                                    ├─→ M6 대시보드
                └──────────→ M5 예측·백테스트 ────┘
```

## A-6. 6개 모듈 상세

### M1 — 공고 수집
- **책임**: 입찰공고 API 수집, 정규화, 중복 제거
- **출력** `data/processed/notices.parquet`
```json
{"notice_id":"20260901-00123-00","posted_at":"2026-09-01","category":"용역",
 "title":"...","org":"○○구청","est_price":142000000,"region_limit":["서울"],
 "license_req":["정보통신공사업"],"bid_method":"제한경쟁","close_at":"2026-09-10",
 "raw_text":"공고문 전문"}
```
- **완료 정의(DoD)**: 12개월치 5,000건 이상, 결측률 리포트 첨부

### M2 — 낙찰 이력 수집 · 매칭
- **책임**: 개찰결과 수집 + **공고와 매칭** (이 프로젝트의 핵심 난관)
- **출력** `data/processed/awards.parquet`
```json
{"notice_id":"20260901-00123-00","opened_at":"2026-09-12","winner":"○○㈜",
 "award_price":128500000,"award_rate":0.9049,"n_bidders":37,"rank_list":[...],
 "reserve_prices":[...]}
```
- **DoD**: **매칭률 ≥ 90%**, 미매칭 사유 분류표

### M3 — 공고문 요건 추출 (LLM)
- **책임**: 공고문 원문 → 구조화된 참가자격 (여기가 AI 파트 1)
- **출력**
```json
{"notice_id":"...","required_licenses":["정보통신공사업"],"region":["서울","경기"],
 "min_experience":{"amount":50000000,"years":3},"sme_only":true,
 "disqualifiers":["직접생산확인증명서 미보유"],"confidence":0.86}
```
- **DoD**: 사람 검수 100건 기준 **필드 정확도 ≥ 85%**

### M4 — 적격 판별기
- **책임**: 회사 프로필 ↔ 요건 매칭, 부적격 사유 설명 생성
- **출력**: `{"notice_id":..., "eligible":true, "score":0.91, "reasons":["면허 충족","지역 충족"], "blockers":[]}`
- **DoD**: 규칙 기반 정답 대비 **F1 ≥ 0.80**

### M5 — 예측 모델 + 백테스트 (채점기 겸임)
- **책임**: ① 낙찰률 회귀 ② 낙찰 확률 분류 ③ **시점 분리 백테스트**
- 모델: 그래디언트 부스팅(수치·범주) + 공고문 임베딩 피처 결합
- **출력**: `reports/backtest_YYYYMMDD.json` (MAPE, 적중률, 리프트, 기간별 안정성)
- **DoD**: 단순 베이스라인(평균 낙찰률) 대비 개선폭 명시

### M6 — 대시보드
- 화면 3개: ① 오늘의 추천 공고 랭킹 ② 공고 상세(요건 충족 체크리스트 + 권장 투찰가 + 신뢰구간) ③ 백테스트 성적표
- **DoD**: 실제 데이터로 3화면 동작, 클릭 3번 안에 근거까지 도달

## A-7. 성과 지표

| 지표 | 베이스라인 | 목표 |
|---|---|---|
| 낙찰률 예측 MAPE | 전체 평균값 예측 | **≤ 3%p** |
| 적격 판별 F1 | 키워드 매칭 | **≥ 0.80** |
| 검토 공고 수 감축 | 전량 | **≥ 90%** |
| 상위 10% 추천의 낙찰 리프트 | 1.0배 | **≥ 2.5배** |
| 요건 추출 정확도 | – | **≥ 85%** |

## A-8. 리스크
| 리스크 | 대응 |
|---|---|
| 공고-낙찰 매칭 실패 | **W0에서 판정.** 안 붙으면 표준서비스(15058815)로 전환 |
| 복수예비가격 추첨의 무작위성 | 낙찰가 점추정 대신 **구간 예측**으로 목표 변경, "예측 불가 영역"을 정직하게 보고 |
| 업종별 편차 | 1개 업종(예: 정보통신 용역)으로 좁혀 깊게 |

# 【B】 계약서 독소조항 대조 탐지 — 사업성 카드

## B-1. 제품 한 줄
> **"받은 계약서를 표준계약서와 나란히 놓고, 나에게 불리하게 바뀐 조항만 빨갛게 표시한다."**

**타깃**: 프리랜서 / 소상공인 / 초기 스타트업 / 예술·콘텐츠 창작자

## B-2. 문제를 숫자로
"계약서를 요약해주는" 서비스는 많습니다. 하지만 **불리한지 여부는 표준과 비교해야만 알 수 있습니다.**

| 지표 | 의미 |
|---|---|
| 조항 정렬 정확도 | 표준 제5조 ↔ 대상 계약서 제6조를 올바르게 짝지었는가 |
| 독소조항 탐지 재현율 | 실제 불리한 조항 중 몇 %를 잡았는가 |
| 오탐률 | 멀쩡한 조항을 불리하다고 한 비율 |
| 검토 시간 | 사람이 전문 대조하는 시간 대비 절감 |

## B-3. 데이터
| 데이터 | 성격 |
|---|---|
| 공정거래위원회 **표준약관 / 표준계약서** | 기준선 (공개) |
| 부처별 표준계약서 (문체부 등 분야별) | 도메인 확장 |
| 법제처 API 관련 법령 (약관규제법 등) | 근거 조문 링크 |
| 공공기관 공개 계약서 양식 | 실제 문서 샘플 |

**W0 확인**: 표준계약서 20종 이상 텍스트 확보 / 조항 자동 분해(제N조 단위) 정확도 / 실제 계약서 샘플 30건 확보 경로

## B-4. 정답 라벨 설계 — **변형 주입(자동 생성)**
표준계약서에 **의도적으로 불리한 변형**을 주입해 정답을 만듭니다.

| 변형 유형 | 예시 | 심각도 |
|---|---|---|
| T1 권리 삭제 | 해지 통보 유예기간 조항 삭제 | 상 |
| T2 기한 단축 | 대금 지급 30일 → 90일 | 상 |
| T3 책임 전가 | 손해배상 전액 부담 신설 | 상 |
| T4 상한 신설 | 배상 한도 계약금 10%로 제한 | 중 |
| T5 일방 권한 | 발주자 임의 해지권 추가 | 상 |
| T6 무해 변경 | 문구 다듬기, 순서 변경 | **없음(오탐 테스트용)** |

> **T6이 결정적입니다.** 무해 변경을 섞어야 "다 빨갛게 칠하는" 모델을 걸러낼 수 있습니다.

## B-5. 6개 모듈

| 모듈 | 책임 | 출력 |
|---|---|---|
| **M1** 표준 수집 | 표준계약서 수집·조항 분해 | `standards.jsonl` `{"doc_id","clause_no","title","text"}` |
| **M2** 변형 엔진 | T1~T6 주입, 라벨 생성 | `pairs.jsonl` `{"pair_id","std_clause","mod_clause","label":"T2","severity":"상"}` |
| **M3** 조항 정렬 | 표준↔대상 조항 매칭 (임베딩+번호+제목 하이브리드) | `{"std_no":"제5조","tgt_no":"제6조","score":0.93,"status":"matched\|missing\|added"}` |
| **M4** 차이 판정 | 차이 추출 + **불리함 방향**·심각도 분류 | `{"pair_id","verdict":"unfavorable","severity":"상","type":"T2","evidence":"지급기한 30→90일","law_ref":"하도급법 제13조"}` |
| **M5** 채점기 | 정렬 정확도·재현율·오탐·심각도 정확도 | `reports/score.json` |
| **M6** UI | 나란히 비교 뷰, 위험도 색상, 근거 조문 링크, 협상 문구 제안 | 데모 |

## B-6. 성과 지표
| 지표 | 목표 |
|---|---|
| 조항 정렬 정확도 | **≥ 90%** |
| 독소조항 재현율 | **≥ 80%** |
| 오탐률 (T6 무해 변경 기준) | **≤ 15%** |
| 심각도 3단계 정확도 | ≥ 75% |
| 실제 계약서 30건 사람 검수 일치율 | ≥ 80% |

## B-7. 리스크
| 리스크 | 대응 |
|---|---|
| 합성 변형이 실제 계약서와 다름 | **실제 계약서 30건 별도 검증셋**을 반드시 둔다. 합성 성능만 보고하면 안 됨 |
| "불리함"의 주관성 | 판단 기준을 **법령 근거 유무 / 권리 방향 / 금액·기한 방향** 3축으로 고정 |
| 법률 자문 오해 | "참고용, 법률 자문 아님" 명시 + 근거 조문 항상 병기 |

# 【C】 아파트 관리비 이상탐지 — 사업성 카드

## C-1. 제품 한 줄
> **"같은 조건 단지들과 비교했을 때, 우리 아파트에서 비정상으로 비싼 항목과 그 금액."**

**타깃**: 입주자대표회의 / 개별 입주민 / 지자체 감사 / 관리업체 비교 서비스

## C-2. 문제를 숫자로
관리비는 항목별로 공개되지만 **비교 기준이 없어서** 숫자를 봐도 판단이 안 됩니다.

| 지표 | 의미 |
|---|---|
| 유사단지군 내 분산 감소율 | 매칭 품질 (얼마나 "같은 조건"끼리 묶었나) |
| 이상 판정 단지 비율 | 항목별 |
| **연간 초과 지출 추정액(원)** | **발표에서 가장 강한 숫자** |
| 소급검증 재현율 | 공개된 감사 적발 사례를 우리가 잡았나 |

## C-3. 데이터 (확인됨)

| 데이터 | 출처 |

# 【E】 RAG 답변 근거 형광펜 — 기술스택 정면승부

## E-1. 제품 한 줄
> **"AI 답변에서 근거 문서에 없는 문장에 빨간 줄을 긋는다. GPT-4보다 정확하고 100배 싸게."**

## E-2. 근거 수치 (공개 실측 — 재현 가능)
RAGTruth 벤치마크 (구간 주석 **18,000건** / 학습 15,090 · 평가 2,700), **응답 단위 F1**:

| 방식 | 크기 | F1 |
|---|---|---|
| GPT-4 프롬프트 | – | **63.4%** |
| Luna (기존 인코더 SOTA) | – | 65.4% |
| Llama-2-13B 파인튜닝 | 13B | 78.7% |
| **LettuceDetect (ModernBERT)** | **396M** | **79.22%** |
| Llama-3-8B 파인튜닝 | 8B | 83.9% |

→ **4억 파라미터가 130억을 이겼습니다.** 처리량 GPU 1장 **초당 30~60건**, 컨텍스트 8,192 토큰.

비용(MiniCheck, EMNLP 2024): 770M 모델이 LLM-AggreFact **74.7%** vs GPT-4 **75.3%** (차이 0.6%p)인데
**13,000건 검증 $0.24 vs $107 — 약 400배.**

한국어에는 **K-HALU**(ICLR 2025, 7개 도메인, 40% 복수정답), **K-FinHallu**(2026, 금융 멀티턴) 같은 **평가 벤치마크는 있지만 구간 단위 탐지 모델이 없습니다.**

## E-3. 4주·바이브코딩에 맞춘 현실적 범위
대형 학습은 하지 않습니다. **3방식 캐스케이드 비교**로 잡습니다.

```
답변 문장 → [1단 규칙] 숫자·날짜·고유명사가 근거에 있나 (0ms, 무료)
          → [2단 임베딩] 문장 ↔ 근거 청크 최대 유사도 (5ms, 거의 무료)
          → [3단 LLM] 애매한 것만 판정 (수백 ms, 유료)
```
**"몇 %를 1·2단에서 걸러 LLM 호출을 줄였는가"** 가 핵심 성과 숫자입니다.

## E-4. 데이터 · 라벨
| 단계 | 방법 |
|---|---|
| 근거 문서 | 법제처 API 조문 또는 공공기관 FAQ (한국어 확보 쉬움) |
| 답변 생성 | LLM으로 QA 3,000건 생성 |
| **오류 자동 주입** | 숫자 변조 / 조건 추가 / 존재하지 않는 조문 인용 / 근거 밖 일반지식 삽입 / 과일반화 — **5종, 구간 위치까지 라벨로 기록** |
| 평가셋 | 자동 라벨 + **사람 검수 300건**(κ 측정) |
| 외부 검증 | K-HALU로 교차 평가 |

## E-5. 6개 모듈

| 모듈 | 책임 | 출력 |

| **M1** 근거 코퍼스 | 문서 수집·청킹·색인 | `corpus.jsonl`, 벡터 인덱스 |

| **M4** 탐지기 B | LLM 판정 + 소형 분류기, **캐스케이드 라우터** | `pred_b.jsonl` + 라우팅 통계 |

# 【F】 한국어 Text-to-SQL — 기술스택 정면승부 (채점 논쟁 0)

## F-1. 제품 한 줄
> **"한국어로 물으면 SQL이 나온다. 정답 여부는 DB가 직접 채점한다."**

## F-2. 왜 이 카드가 강한가
**실행정확도(Execution Accuracy)** = 생성한 SQL을 실제로 돌려 결과가 정답 SQL과 같은지 비교.
**LLM 심판도, 사람 채점도 필요 없습니다.** "이 점수 믿을 수 있냐"는 질문이 원천 봉쇄됩니다.

## F-3. 근거 수치 (BIRD 벤치마크)
**12,751 질문-SQL 쌍 / 95개 DB / 37개 전문 도메인**

| 주체 | 실행정확도 |
|---|---|
| **인간** | **92.96%** |
| Gemini-SQL2 (1위) | **80.04%** (인간과 **12.92%p 격차**) |
| Claude Opus 4.6 / AWS Q-SQL | 약 70.1% |

→ **프론티어 모델도 못 푼 문제이고, 이 숫자는 전부 영어 기준입니다.**

## F-4. 우리가 채우는 빈칸 — 한국식 스키마
| 한국 특유 난점 | 예시 |
|---|---|
| 한글 컬럼·테이블명 | `주민등록인구`, `자치구코드` |

## F-5. 데이터
공공데이터포털의 **관계형으로 구성 가능한 데이터 3~5종**을 실제 DB(SQLite/PostgreSQL)로 구축.
예: 인구·행정구역 / 상가업소 / 아파트 실거래 / 공공기관 예산·집행 / 교통 카드 통계.
질의는 팀이 작성하되 **난이도 3단계**(단순 집계 / 조인·중첩 / 다중 조인+윈도우 함수)로 층화.

## F-6. 6개 모듈

| 모듈 | 책임 | 출력 |
|---|---|---|
| **M1** DB 구축 | 공공데이터 → 정규화 스키마 3~5개 DB, 한글 스키마 문서 | `db/*.sqlite` + `schema.json` |
| **M2** 평가셋 | 질의 500~800개 + 정답 SQL, 난이도 태깅 | `queries.jsonl` `{"q_id","db_id","question","gold_sql","difficulty"}` |
| **M3** 채점 하네스 | **샌드박스 실행, 결과 집합 비교, 타임아웃·오류 분류** | `eval/runner.py` + `score.json` |
| **M4** 스키마 링킹 | 질문 → 관련 테이블·컬럼 후보 축소 (임베딩 + 값 매칭) | `linked.jsonl` |
| **M5** 생성 + 자기수정 | SQL 생성 → 실행 → 오류/빈결과면 재작성 (최대 3회) | `pred.jsonl` + 수정 로그 |
| **M6** 분석·UI | 오류 유형 분해, 질의 콘솔 데모 | 리포트 + 데모 |

# 【G】 AI 에이전트 툴콜 신뢰성 진단 — 기술스택 정면승부

## G-1. 제품 한 줄
> **"에이전트가 도구를 5번 연속 부르면 왜 무너지는가. 원인을 유형별로 해부하고 고친다."**

## G-2. 근거 수치 (BFCL v4, Berkeley)
- **멀티턴 점수는 단일턴 대비 모든 모델에서 5~10점 하락**
- **5회 이상 연속 호출 시 유효 정확도는 멀티턴 점수가 복리로 곱해짐** (헤드라인 점수가 아님)
- 멀티턴 4개 하위셋: base / long-context / **missing-function** / **missing-parameter**
- 프론티어 API와 최상위 오픈웨이트 격차는 **3~4%p**까지 축소

> **복리 감쇠**가 핵심입니다. 멀티턴 정확도 90%라도 5연속이면 0.9⁵ ≈ 59%. **이 계산 하나가 발표의 훅이 됩니다.**

## G-3. 우리가 채우는 빈칸
공개 벤치마크는 영어·해외 API 기준입니다. **한국 공공 API 스키마(공공데이터포털 계열)와 한국어 대화로 만든 멀티턴 툴콜 평가셋은 없습니다.**

## G-4. 6개 모듈

| 모듈 | 책임 | 출력 |
|---|---|---|
| **M1** 툴 스키마 | 공공 API 20~30개를 함수 스키마로 정의 (+의도적 결함 버전) | `tools.json` |
| **M2** 시나리오 | 한국어 멀티턴 시나리오 300건, 정답 호출 시퀀스 포함 | `scenarios.jsonl` `{"id","turns":[...],"gold_calls":[{"name","args"}],"trap":"missing_param"}` |
| **M3** 실행 하네스 | 모의 API 서버 + 에이전트 루프 실행·기록 | `traces.jsonl` |
| **M4** 실패 분류기 | 트레이스 → 실패 유형 자동 태깅 | `{"trace_id","fail_type":"wrong_function","turn":3}` |
| **M5** 수리 A/B | 스키마 재작성 / 인자 검증 레이어 / 재시도 정책 / 상태 요약 주입 — **각각 효과 측정** | `reports/ablation.json` |
| **M6** 리포트 UI | 감쇠 곡선, 유형 분포, 수리 전후 비교 | 데모 |

### 실패 유형 정의 (M4가 자동 태깅)
| 코드 | 의미 |
|---|---|
| F1 | 함수 선택 오류 (잘못된 도구) |
| F2 | 파라미터 타입/형식 오류 |
| F3 | **누락 파라미터를 되묻지 않고 지어냄** |
| F4 | 이전 턴 결과 추적 실패 (상태 소실) |
| F5 | 없는 함수를 호출 (환각 도구) |
| F6 | 장문 컨텍스트에서 초반 지시 망각 |
| F7 | 무한 재시도 / 루프 |

## G-5. 성과 지표

| 지표 | 베이스라인 | 목표 |
|---|---|---|
| 멀티턴 성공률 | 무보정 에이전트 | **+15%p** |
| 실패 유형 분포표 | – | **7종 비율 제시 (핵심 산출물)** |
