## 0-2. 비용을 3~10배 줄이는 API 기능 4개 (반드시 씀)

### ① Batch API — **비용 50%**
평가셋 생성, 대량 태깅처럼 **실시간이 아닌 작업은 전부 배치로**.
```python
batch = client.messages.batches.create(requests=[
    {"custom_id": f"item-{i}", "params": {...}} for i in range(3000)
])
# processing_status가 "ended"가 될 때까지 폴링 → results() 스트리밍
# 결과는 순서가 보장되지 않음 → 반드시 custom_id로 키를 잡을 것
```

### ② Prompt Caching — 반복되는 긴 컨텍스트 비용 절감
법령 조문, DB 스키마, 표준계약서처럼 **매 요청마다 똑같이 들어가는 앞부분**에 캐시 지점을 겁니다.
- 렌더 순서는 `tools` → `system` → `messages`. **안 변하는 것을 앞에, 매번 바뀌는 것(질문·타임스탬프)을 뒤에.**
- 앞부분이 1바이트라도 바뀌면 그 뒤 캐시가 전부 무효화됩니다.
- **검증**: 응답의 `usage.cache_read_input_tokens`가 0이면 캐시가 안 걸린 것. 반복 호출에서 이 값을 반드시 확인.

### ③ Structured Outputs — JSON 파싱 실패를 0으로
추출·분류 모듈은 전부 이걸로. 자유 텍스트 파싱은 금지합니다.
```python
# 응답 형식 고정
client.messages.create(..., output_config={"format": {...}})
# 또는 스키마 검증까지 한 번에
client.messages.parse(...)
# 툴 인자를 스키마대로 강제하려면 툴 정의에 최상위 필드로 strict: true
# (input_schema에 additionalProperties: false + required 필요)
```

### ④ Citations — **인용 위치를 API가 직접 돌려줌**
문서 블록에 `citations: {"enabled": true}`를 켜면, 응답이 여러 `text` 블록으로 쪼개지고
인용된 블록에 **`cited_text` + `char_location`(start_char_index / end_char_index)** 이 붙습니다.
→ **프로젝트 E(근거 형광펜)의 핵심 기능이 API 기본 제공**입니다. 직접 구현할 필요가 없습니다.
(주의: `output_config.format`과 같이 못 씁니다 — 400 에러)

## 0-3. thinking / effort — 품질과 비용 조절 다이얼

```python
client.messages.create(
    model="claude-opus-5",
    thinking={"type": "adaptive"},          # 현행 방식. budget_tokens는 Opus 5에서 400 에러
    output_config={"effort": "medium"},     # low / medium / high(기본) / xhigh / max
    max_tokens=16000,
    messages=[...],
)
```
- **판정 모듈**: `high` 또는 `xhigh`
- **대량 생성·태깅**: `low` ~ `medium` (여기서 비용이 크게 갈립니다)
- 긴 출력이나 큰 `max_tokens`는 **`.stream()` + `.get_final_message()`** 로 (타임아웃 방지)

## 0-4. 임베딩 · 검색 (LLM 아닌 AI 파트)

| 용도 | 1순위 | 대안 | 근거 |
|---|---|---|---|
| 한국어 문장/문단 임베딩 | **BGE-M3** | KURE | BGE-M3는 70개 이상 언어, 약 25만 토큰 어휘로 한국어 성능이 좋음. **KURE는 BGE-M3를 한국어로 추가 파인튜닝**한 고려대 모델이며 MTEB-ko-retrieval 리더보드와 함께 공개 |
| 재순위(reranking) | bge-reranker-v2-m3 계열 | Cross-encoder 직접 학습 | W0에 후보 2~3종 비교 후 고정 |
| 키워드 검색 | BM25 (`rank_bm25`) + 한국어 형태소 분석기(`kiwipiepy`) | Elasticsearch | 한국어는 형태소 분석 없이 BM25를 쓰면 성능이 크게 떨어짐 |
| 벡터 저장 | FAISS (로컬) | pgvector / Qdrant | 4주 프로젝트엔 FAISS가 가장 빠름 |

> **하이브리드 검색이 기본입니다.** 임베딩만 쓰면 고유명사·조문번호를 놓치고, BM25만 쓰면 의미를 놓칩니다.
> 두 점수를 **RRF(Reciprocal Rank Fusion)** 로 합치는 게 구현이 가장 간단하고 효과가 큽니다.

## 0-5. 전통 ML · 통계 (LLM으로 하면 안 되는 것)

| 용도 | 라이브러리 |
|---|---|
| 표 형태 예측(회귀/분류) | LightGBM, XGBoost, CatBoost |
| 생존분석(폐업까지 걸린 시간) | `lifelines` (CoxPH), `scikit-survival` (Random Survival Forest) |
| 이상탐지 | robust z-score(중앙값·MAD), IsolationForest |
| 변화점 탐지 | `ruptures` (PELT) |
| 최적 매칭 | `scipy.optimize.linear_sum_assignment` (헝가리안 알고리즘) |
| 공간 인덱싱 | `scipy.spatial.cKDTree`, H3 |
| 설명 | SHAP |

> **숫자 예측을 LLM에게 시키지 마세요.** 낙찰가·폐업확률·관리비 이상치는 전부 전통 ML이 정확하고 싸고 빠릅니다.
> LLM은 **텍스트를 구조로 바꾸는 자리**와 **판단 근거를 설명하는 자리**에만 씁니다.

## 【A】 공공입찰 낙찰 예측 · 적격 판별

### 모듈별 AI 기술 매핑

| 모듈 | AI 기술 | 구체적으로 |
|---|---|---|
| M1 공고 수집 | — | AI 없음. 순수 데이터 파이프라인 |
| M2 낙찰 매칭 | (선택) 퍼지 매칭 | 문자열 유사도 + 규칙. LLM 불필요 |
| **M3 요건 추출** | **LLM 구조화 추출** | Claude **Sonnet 5** + `strict: true` 툴 스키마. 공고문 원문 → 면허/지역/실적/제외사유 JSON |
| **M4 적격 판별** | **규칙 + 임베딩 매칭** | 면허명 표기 흔들림("정보통신공사업" vs "정보통신공사")을 BGE-M3 임베딩 유사도로 흡수. 판정 자체는 규칙 |
| **M5 예측** | **LightGBM 분위수 회귀 + 임베딩 피처** | 낙찰률 점추정이 아니라 **구간 추정**(10/50/90 분위수). 공고문 임베딩을 차원축소해 피처로 추가 |
| M6 대시보드 | (선택) LLM 설명 생성 | 추천 이유 문장화 — Haiku |

### 왜 이 선택인가
- **낙찰가를 LLM에게 물으면 안 됩니다.** 복수예비가격 추첨 구조 때문에 근본적으로 확률적이며, 표 형태 회귀가 정확합니다.
- **분위수 회귀**를 쓰는 이유: "1억 2,850만 원"이라는 점추정보다 **"1억 2,600만~1억 3,100만 원 사이일 확률 80%"** 가 실무에서 쓸모 있고, 평가도 정직합니다.
- 요건 추출은 텍스트→구조 변환이라 LLM이 압도적입니다. 정규식으로는 공고문 문체 편차를 못 이깁니다.

### 예상 LLM 비용
공고 5,000건 × (입력 4K + 출력 500 토큰), Sonnet 5, **Batch API 50% 적용**:
`5,000×4K = 20M 입력 × $2 = $40` / `5,000×0.5K = 2.5M 출력 × $10 = $25` → 합 $65 → **배치로 약 $33**
프롬프트 캐싱으로 지시문 부분을 캐시하면 더 내려갑니다.

### GPU 필요 여부
**불필요.** 임베딩은 CPU로도 되고(느리면 Colab 무료 T4), LightGBM은 CPU 학습.

## 【B】 계약서 독소조항 대조 탐지

### 모듈별 AI 기술 매핑

| 모듈 | AI 기술 | 구체적으로 |
|---|---|---|
| M1 표준 수집 | 문서 파싱 | `pdfplumber`/`python-docx` + 조항 분해 정규식(제N조/제N항) |
| **M2 변형 엔진** | **LLM 생성 (Haiku)** | T1~T6 변형 주입. "이 조항의 지급기한을 30일→90일로 바꿔 자연스럽게 다시 써라" |
| **M3 조항 정렬** | **임베딩 + 헝가리안 알고리즘** | BGE-M3로 조항 임베딩 → 유사도 행렬 → `linear_sum_assignment`로 **전역 최적 1:1 매칭**. 그리디 매칭보다 확실히 좋음 |
| **M4 차이 판정** | **LLM 판정 (Opus 5)** | 표준 조항 + 대상 조항 → `{불리함 여부, 방향, 심각도, 근거 문장, 관련 법령}` 구조화 출력 |
| **M5 채점기** | 지표 계산 | 정렬 정확도, 재현율, 오탐률 — AI 아님 |
| M6 UI | (선택) 협상 문구 생성 | Sonnet |

### 왜 이 선택인가
- **조항 정렬에 헝가리안 알고리즘을 쓰는 게 이 프로젝트의 기술 포인트입니다.** 계약서는 조항 순서가 바뀌고 번호가 어긋나므로, 한 쌍씩 그리디로 붙이면 연쇄적으로 밀립니다. 전역 최적 할당이 정답입니다.
- 판정은 **법적 함의 추론**이라 Opus 5가 필요한 자리입니다. 여기서 모델을 낮추면 지표가 무너집니다.
- 변형 주입은 창의성이 필요 없는 기계적 작업이라 Haiku로 충분합니다.

### 핵심 프롬프트 설계
판정 프롬프트에 **"불리하지 않음"을 고르는 것도 정답이라고 명시**해야 합니다. 안 그러면 모델이 전부 불리하다고 답합니다(오탐 폭증). T6 무해 변경 샘플로 이걸 검증합니다.

### 예상 LLM 비용
- 변형 생성: 조항 1,000개 × 6유형 = 6,000건, Haiku, 배치 → **약 $10 이하**
- 판정: 6,000쌍 × (입력 3K + 출력 400), Opus 5, 배치
  `18M × $5 = $90` + `2.4M × $25 = $60` → $150 → **배치 약 $75**
  → 캐싱 + 1차 필터(임베딩 유사도 0.98 이상이면 "동일"로 스킵)로 **절반 이하로 줄일 것**

### GPU 필요 여부
**불필요** (임베딩만).

## 【C】 아파트 관리비 이상탐지

### 모듈별 AI 기술 매핑

| 모듈 | AI 기술 | 구체적으로 |
|---|---|---|
| M1/M2 수집 | — | 데이터 파이프라인 |
| **M3 유사단지 매칭** | **표현학습 + KNN** | 통제변수(세대수·연식·난방방식·복도유형·지역·승강기)를 정규화 → **거리학습 또는 오토인코더 임베딩** → cKDTree로 K-최근접 |
| **M4 이상탐지** | **로버스트 통계 + 변화점 탐지** | 항목별 중앙값·MAD 기반 z-score(평균·표준편차는 이상치에 오염됨) + `ruptures` PELT로 시계열 급변 시점 탐지 |
| M5 검증 | 지표 계산 | 분산 감소율, 소급검증 재현율 |
| **M6 설명 생성** | **LLM (Sonnet)** | "이 단지의 경비비는 유사 단지 평균보다 38% 높으며, 2025년 7월부터 급등했습니다" 자연어 생성 |

### 왜 이 선택인가
- **이 프로젝트의 AI는 '예측'이 아니라 '비교군 생성'에 있습니다.** 유사단지 매칭을 학습 기반으로 하는 것이 단순 필터링과의 차이이자, "통계 과제 아니냐"는 지적을 막는 지점입니다.
- **평균 대신 중앙값·MAD**: 관리비 데이터는 극단값이 많아 평균 기반 z-score는 이상치가 이상치를 가려버립니다.
- 변화점 탐지를 넣는 이유: "원래 비쌌다"와 "갑자기 비싸졌다"는 완전히 다른 문제이고, 후자가 훨씬 강한 신호입니다.

### 매칭 품질을 어떻게 증명하나 (중요)
> **비교군 내 관리비 분산이 전국 분산 대비 얼마나 줄었는가.**
> 40% 이상 줄면 "비슷한 단지끼리 잘 묶었다"의 정량적 증거입니다. 이 숫자 하나로 M3의 가치를 방어합니다.

### 예상 LLM 비용
설명 생성만 씁니다. 이상 판정 단지 3,000건 × (입력 1K + 출력 300), Sonnet, 배치 → **약 $5**

### GPU 필요 여부
**불필요.**

## 【D】 폐업 위험 조기경보

### 모듈별 AI 기술 매핑

| 모듈 | AI 기술 | 구체적으로 |
|---|---|---|
| M1 이력 재구성 | — | 인허가일자·폐업일자로 업소별 생애 이력 구성 |
| **M2 상권 피처** | **공간 집계** | cKDTree/H3로 반경 300m 동종업 수, **최근 12개월 순증감**, 신규 유입 |
| **M3 데이터셋** | **시점 분리 설계** | 관측시점 T0 고정, T0 이후 정보 전면 차단. 누수 점검 스크립트 포함 |
| **M4 모델** | **3단 비교** | ① 로지스틱 회귀(베이스라인) ② LightGBM ③ **생존분석**(CoxPH `lifelines` / Random Survival Forest `scikit-survival`) |
| **M5 평가** | **AUROC + C-index + 캘리브레이션** | 예측 20%가 실제 20%인지(Brier score, calibration curve) |
| **M6 설명** | **SHAP → LLM 문장화** | SHAP 기여도 상위 3개를 Haiku가 한 문장으로 |

### 왜 생존분석까지 가는가
단순 이진 분류는 **"6개월 안에 망하나"** 만 답합니다. 생존분석은 **"언제쯤 망하나 + 지금까지 버틴 게 정보다"** 를 씁니다.
- 아직 영업 중인 가게는 **중도절단(censored) 데이터**입니다. 이걸 "폐업 안 함=0"으로 처리하면 정보를 버립니다.
- 생존분석은 이걸 제대로 다루고, **C-index**라는 별도 지표가 생겨 발표 내용이 두꺼워집니다.
- **이게 일반 상권분석 과제와 갈리는 지점입니다.**

### 캘리브레이션을 반드시 넣는 이유
"폐업 확률 70%"라고 말하려면 **실제로 70%가 망해야** 합니다. AUROC가 높아도 확률값이 엉터리인 모델은 서비스로 못 씁니다. 이 검증을 넣으면 완성도가 확 올라갑니다.

### 예상 LLM 비용
설명 문장화만. **$5 미만.**

### GPU 필요 여부
**불필요.** 이 프로젝트는 사실상 LLM 비중이 가장 낮고 전통 ML 비중이 가장 높습니다. → **"AI 필수" 요건을 맞추려면 M6 설명 생성과 M2 피처 엔지니어링을 발표에서 분명히 드러내야 합니다.**

## 【E】 RAG 근거 형광펜

**7개 중 AI 기술 밀도가 가장 높은 프로젝트입니다.**

### 모듈별 AI 기술 매핑

| 모듈 | AI 기술 | 구체적으로 |
|---|---|---|
| M1 코퍼스 | **청킹 + 하이브리드 색인** | 조문 단위 청킹, BGE-M3 임베딩 + BM25(kiwipiepy 형태소) + **RRF 융합** |
| **M2 데이터 생성** | **LLM 생성 + 오류 주입 (Haiku, 배치)** | QA 3,000건 + 5종 오류(숫자 변조/조건 추가/없는 조문 인용/근거 밖 지식/과일반화) **+ 구간 위치 라벨** |
| **M3 탐지기 A** | **규칙 + 임베딩** | ① 숫자·날짜·조문번호를 근거에서 문자열 대조 ② 문장별 최대 코사인 유사도 → 임계값 |
| **M4 탐지기 B** | **Claude Citations + LLM 판정 + 캐스케이드** | **Citations API의 `char_location`으로 인용 구간을 직접 획득** → 인용 안 된 구간을 후보로. 애매한 것만 Opus 5 판정 |
| **M5 채점기** | **구간 F1 + AUROC + 비용·지연 동시 측정** | 구간 겹침 기준(IoU) 정의 필수 |
| M6 UI | 렌더링 | 형광펜 하이라이트 + 근거 조문 링크 |

### 이 프로젝트의 핵심 기술 카드 3개

**① Citations API가 곧 구간 탐지기입니다**
문서 블록에 `citations: {"enabled": true}`를 켜면 응답이 `text` 블록으로 쪼개지고, 인용된 블록에 `cited_text`와 **`char_location`(start_char_index / end_char_index)** 이 붙습니다.
→ **"어느 문장이 어느 근거에서 나왔는가"를 모델이 직접 표시**합니다. 반대로 **인용이 안 붙은 구간이 곧 근거 없는 구간 후보**입니다.
→ 직접 span tagger를 학습할 필요 없이 4주 안에 구간 단위 결과를 냅니다.
(제약: `output_config.format`과 동시 사용 불가 — 400. 형식이 필요하면 후처리로 분리)

**② 3단 캐스케이드 — 비용 곡선을 직접 그린다**
```
문장 → [1단 규칙]   숫자·조문번호 불일치 → 즉시 '근거없음'      (0ms, $0)
      → [2단 임베딩] 유사도 > 0.85 → 즉시 '근거있음'            (~5ms, ≈$0)
      → [3단 LLM]   나머지만 Opus 5 판정                        (수백 ms, 유료)
```
**성과 숫자 = "LLM 호출을 100% → 30%로 줄이면서 F1을 유지했다."**
1·2단 임계값을 움직이며 **비용-정확도 파레토 곡선**을 그리는 게 이 프로젝트의 결과물입니다.

**③ 인용 수치 대비 벤치마킹**
| 비교 대상 | 공개 수치 |
|---|---|
| GPT-4 프롬프트 (RAGTruth, 응답 F1) | 63.4% |
| LettuceDetect (ModernBERT 396M) | 79.22% |
| MiniCheck 770M vs GPT-4 (LLM-AggreFact) | 74.7% vs 75.3%, **비용 $0.24 vs $107 = 400배** |

→ 우리는 "한국어에서 이 격차를 재현했다"를 목표로 삼습니다.

### 예상 LLM 비용
- 데이터 생성 3,000건, Haiku, 배치 → **약 $7**
- 판정 베이스라인(전량 Opus 5) 3,000건 × (입력 4K + 출력 300): `12M×$5=$60` + `0.9M×$25=$22.5` = $82.5 → 배치 **약 $41**
- **캐스케이드 적용 시 30%만 호출 → 약 $12** ← **이 차이 자체가 발표 성과**

### GPU 필요 여부
**불필요**(임베딩 CPU 가능). 여유가 있으면 소형 분류기 파인튜닝을 추가 — Colab T4로 충분.

## 【F】 한국어 Text-to-SQL

### 모듈별 AI 기술 매핑

| 모듈 | AI 기술 | 구체적으로 |
|---|---|---|
| M1 DB 구축 | — | 공공데이터 → SQLite/PostgreSQL 정규화 |
| **M2 평가셋** | **LLM 보조 + 사람 검증** | Haiku로 질의 초안 생성 → 사람이 정답 SQL 작성·검증 (**정답은 반드시 사람이**) |
| **M3 채점 하네스** | **실행 기반 자동채점** | 샌드박스 실행 → 결과 집합 비교(정렬 무시·중복 처리 규칙 고정) → 타임아웃·오류 분류 |
| **M4 스키마 링킹** | **임베딩 검색 + 값 매칭** | 질문 ↔ 테이블·컬럼 설명 임베딩 유사도 + **컬럼 값 사전 매칭**("강남" → `자치구명` 컬럼) |
| **M5 생성 + 자기수정** | **LLM 루프 (Sonnet 5) + `sqlglot`** | 생성 → `sqlglot`로 문법·스키마 검증 → 실행 → 오류/빈결과면 **오류 메시지를 넣어 재생성** (최대 3회) |
| M6 분석 | 오류 유형 분류 | 스키마링킹/조인/집계/한글값/날짜 5종 |

### 왜 이 선택인가
- **스키마 링킹이 성능의 절반입니다.** 테이블 50개 스키마를 통째로 프롬프트에 넣으면 모델이 헤맵니다. 관련 테이블 3~5개로 좁혀주면 정확도가 크게 오릅니다. → 여기가 검색 AI 파트.
- **`sqlglot`** 로 실행 전에 파싱·검증하면 잘못된 SQL을 DB에 보내기 전에 걸러 재시도 비용을 줄입니다.
- **실행 피드백 자기수정 루프**가 이 프로젝트의 기술 포인트입니다. "오류 메시지를 다시 모델에 넣는다"는 단순한 아이디어인데 실제로 정확도가 붙고, **기여도를 분리 측정**할 수 있습니다(1회 생성 vs 3회 루프).

### 정확도 향상 기법 우선순위 (4주 안에 넣을 순서)
1. 스키마 링킹 (효과 가장 큼)
2. 실행 피드백 자기수정
3. Few-shot 예제 검색 (유사 질문의 정답 SQL을 프롬프트에 삽입)
4. 다중 후보 생성 후 실행 결과 다수결 (self-consistency) — 비용이 배로 드니 마지막

### 예상 LLM 비용
질의 800개 × 3회 루프 × (입력 5K + 출력 400), Sonnet 5:
`800×3×5K = 12M × $2 = $24` + `0.96M × $10 = $9.6` → **약 $34** (실험 반복 3회 가정 시 약 $100)

### GPU 필요 여부
**불필요.**

## 【G】 AI 에이전트 툴콜 신뢰성 진단

### 모듈별 AI 기술 매핑

| 모듈 | AI 기술 | 구체적으로 |
|---|---|---|
| M1 툴 스키마 | JSON Schema 설계 | 공공 API 20~30개를 함수 스키마로. **의도적 결함 버전**(설명 누락, 모호한 인자명)도 같이 |
| M2 시나리오 | 템플릿 생성 + 사람 정밀 작성 | 300건 중 30건은 손으로 |
| **M3 실행 하네스** | **에이전트 루프 직접 구현** | `stop_reason == "tool_use"` 수동 루프. **툴 러너를 쓰지 않는 이유: 실패를 관찰하는 게 목적이라 루프를 우리가 통제해야 함** |
| **M4 실패 분류기** | **규칙 + LLM 분류** | 트레이스 → F1~F7 유형 자동 태깅. 명확한 건 규칙(없는 함수 호출 등), 애매한 건 Haiku |
| **M5 수리 A/B** | **4가지 개입의 절제 실험** | ① 스키마 설명 재작성 ② `strict: true` 인자 검증 ③ 재시도 정책 ④ 상태 요약 주입 |
| M6 리포트 | 시각화 | 감쇠 곡선, 유형 분포, 전후 비교 |

### 실패 유형 (M4가 자동 태깅)
| 코드 | 의미 | 대응 기법 |
|---|---|---|
| F1 | 함수 선택 오류 | 스키마 설명 재작성 |
| F2 | 파라미터 타입/형식 오류 | **`strict: true`** (툴 정의 최상위 필드, `additionalProperties: false` + `required` 필요) |
| F3 | 누락 파라미터를 되묻지 않고 지어냄 | 프롬프트 지시 + 검증 레이어 |
| F4 | 이전 턴 결과 추적 실패 | 상태 요약 주입 |
| F5 | 없는 함수 호출 | 화이트리스트 검증 |
| F6 | 장문 컨텍스트에서 초반 지시 망각 | 컨텍스트 편집 / 재주입 |
| F7 | 무한 재시도 | 루프 상한 |

### 발표 훅
> **멀티턴 정확도 90%도 5연속 호출이면 0.9⁵ ≈ 59%.**
> BFCL v4 기준 **멀티턴 점수는 단일턴 대비 모든 모델에서 5~10점 하락**하고, 5회 이상 연속이면 **복리로 곱해집니다.**

### 반드시 지킬 API 세부사항
- **병렬 툴 호출**: 한 응답에 여러 `tool_use` 블록이 올 수 있습니다. 결과를 **하나의 user 메시지에 모든 `tool_result`를 담아** 돌려줘야 합니다. 나눠 보내면 모델이 병렬 호출을 멈추도록 학습됩니다.
- **실패한 툴도 `tool_result`에 `is_error: true`로 반드시 돌려줍니다.** 빠뜨리면 루프가 깨집니다.
- **툴 인자는 반드시 `json.loads()`로 파싱.** 문자열 매칭 금지(이스케이프 차이로 깨짐).

### 예상 LLM 비용
300 시나리오 × 5턴 × 3모델 비교 × (입력 6K + 출력 300), Sonnet 5:
`300×5×3×6K = 27M × $2 = $54` + `1.35M × $10 = $13.5` → **약 $68** (실험 반복 포함 $150 예상)
→ **API 비용이 7개 중 가장 큽니다.** 모의 서버로 실제 API 호출 비용은 0이지만 LLM 호출은 많습니다.

### GPU 필요 여부
**불필요.**
