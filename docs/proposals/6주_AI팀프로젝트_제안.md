## 【1】 규제 변경 영향 자동추적기 ⭐ **종합 1순위**

> **"법이 바뀌었다. 우리 회사 문서 3,000개 중 지금 당장 고쳐야 하는 건 어느 것인가?"**

### 해결할 문제 (구체적으로)
법령·고시·표준약관은 계속 개정됩니다. 그런데 기업의 내규·약관·안내문·챗봇 답변은 **누가 언제 무엇을 고쳐야 하는지 아무도 모릅니다.** 지금은 법무·컴플라이언스 담당자가 개정문을 읽고 **눈으로 대조**합니다.

**수치화되는 문제**: 개정 1건당 검토 대상 문서 수 × 문서당 검토 시간. 우리 시스템은 이걸 **"고쳐야 할 확률 순으로 정렬된 상위 20건"** 으로 줄입니다.

### 검증 데이터 (실존 확인함)
- **법제처 국가법령정보 공동활용 OPEN API** — 조문 내용·조문번호·**시행일자·개정이력**·소관부처를 무료 XML 제공 (open.law.go.kr)
- 대상 문서: 금융감독원 표준약관, 지자체 자치법규, 공공기관 내규 등 **공개 문서**

### 왜 백테스트가 가능한가 (핵심)
과거 개정 이력이 있으니 **정답이 이미 존재**합니다.
`2024년 3월 A법 제○조 개정` → 그 시점 전후로 **실제로 바뀐 하위 문서·자치법규가 무엇인지 데이터에 남아 있음** → 우리 모델이 그 문서들을 상위에 올렸는지 채점.
**이게 이 주제의 최대 강점입니다. 사람이 라벨을 만들 필요가 없습니다.**

### 특별한 이유
챗봇·검색이 아니라 **"변경 전파(change propagation)"** 문제입니다. 아무도 안 만듭니다. 그런데 리걸테크·컴플라이언스에서는 실제로 돈 내고 사는 기능입니다.

### 6인 모듈 분해
| 모듈 | 담당 내용 | 산출물 |
|---|---|---|
| M1 수집 | 법령 API 수집, 개정 이력 파싱, 조문 단위 분해 | 조문 DB + 개정 타임라인 |
| M2 문서 | 대상 문서 수집·정규화·조항 분해 | 문서 DB |
| M3 연결 | 개정 조문 ↔ 문서 조항 후보 검색 (임베딩+BM25 하이브리드) | 후보 top-k |
| M4 판정 | LLM으로 "충돌/영향 있음/없음" 판정 + 근거 문장 추출 | 판정 결과 + 근거 |
| M5 채점 | **백테스트 하네스**: 과거 개정으로 Recall@20·MRR 자동 채점 | 성능 리포트 |
| M6 화면 | 대시보드: 개정 → 영향 문서 순위 → 근거 하이라이트 → 수정 제안 | 데모 |

### W0 사전검증 (3일)
1. OPEN API 키 발급 → **24시간 내** 조문 1,000건 + 개정 이력 100건 확보되는가
2. 과거 개정 1건을 손으로 추적 → **정답 문서를 찾을 수 있는가** (안 되면 주제 폐기)
3. 임베딩 검색으로 조문↔조항 top-20 뽑기 → 정답이 20위 안에 들어오는가

### 성과 지표 (전부 자동 채점)
| 지표 | 목표 |
|---|---|
| Recall@20 (영향 문서를 상위 20위 안에 포함) | **≥ 80%** |
| MRR (정답의 평균 순위 역수) | ≥ 0.5 |
| 오탐률 (영향 없는데 있다고 한 비율) | ≤ 20% |
| 검토 시간 절감 | 문서 N건 → 상위 20건, **절감률 %로 환산** |
| 근거 문장 정확도 | 사람 확인 100건 기준 ≥ 85% |

### 리스크
"영향 있음"의 기준이 모호할 수 있음 → **W0에서 판정 기준을 4단계(직접 인용 / 상위법 변경 / 용어 변경 / 무관)로 못 박고 시작.**

## 【2】 낡은 답변 탐지기 (Stale Answer Detector) ⭐ **기술 특별함 1위**

> **"우리 회사 AI 챗봇 답변 5,000개 중, 제도가 바뀌어서 지금은 틀린 답이 몇 개인가?"**

### 해결할 문제
RAG 챗봇·FAQ·블로그 글은 **만든 시점엔 맞았지만 시간이 지나 틀려집니다.** 세율, 지원금 요건, 법정 기한, 수수료… 아무도 이걸 주기적으로 검사하지 않습니다. **"환각"이 아니라 "유통기한 지난 정답"** 이라 기존 환각탐지기가 못 잡습니다.

**수치화**: 보유 답변 N개 중 낡은 답변 비율(%), 그리고 그것을 **탐지한 비율(재현율)** 과 **헛짚은 비율(오탐률)**.

### 검증 데이터 + 자동 라벨 생성 (여기가 핵심)
법제처 개정 이력이 있으므로 **라벨을 프로그램이 자동으로 만듭니다.**
```
개정 전 조문(t0)으로 답변 생성  →  개정 후 조문(t1) 기준으로 보면 그 답변은 '낡음' = 라벨 1
개정 없는 조문으로 만든 답변                                        = 라벨 0
```
→ **수천 건의 학습·평가 데이터를 사람 손 없이 생성**할 수 있습니다. 4주 프로젝트에서 이건 결정적 이점입니다.

### 특별한 이유
환각탐지는 이미 많습니다. **"시간이 지나 틀려짐"을 탐지하는 건 거의 없습니다.** 문제 정의 자체가 새로워서 발표에서 확실히 튑니다.

### 6인 모듈 분해
| 모듈 | 내용 |
|---|---|
| M1 | 법령 스냅샷 수집 (t0/t1 두 시점 조문) |
| M2 | 답변 코퍼스 자동 생성 (t0 기준 QA 3,000건) |
| M3 | 라벨러 (개정 diff → 낡음/유효 자동 태깅) |
| M4 | 탐지기 (임베딩 유사도 + 숫자·날짜 변화 규칙 + LLM 판정, 3방식 비교) |
| M5 | 채점 하네스 (AUROC, 재현율@오탐률 고정) |
| M6 | 대시보드 (낡은 답변 목록 + 원인 조문 + 수정안 자동 제안) |

### W0 사전검증
1. 같은 조문의 **과거 버전과 현재 버전을 API로 둘 다** 가져올 수 있는가 ← **이거 하나가 성패**
2. 개정 diff에서 숫자·기한 변경을 자동 추출 가능한가
3. 자동 라벨 50건을 사람이 검수 → **일치율 90% 이상**인가

### 성과 지표
| 지표 | 목표 |
|---|---|
| 낡은 답변 탐지 AUROC | **≥ 0.85** |
| 오탐률 5% 고정 시 재현율 | **≥ 70%** |
| 3방식(규칙 / 임베딩 / LLM) 비교표 | 비용·지연 포함 |
| 1만 건 검사 비용 | LLM 전량 대비 **1/10 이하** (규칙+임베딩 1차 필터링) |

### 리스크
과거 버전 조문 조회가 API로 안 되면 → **시행일자 기준 스냅샷을 W0에 미리 떠 두는 방식**으로 우회 (W0에서 반드시 확인).

## 【3】 공공입찰 낙찰가 예측 + 적격 자동판별

> **"우리 회사가 넣을 만한 공고는 무엇이고, 얼마를 써야 딸 수 있는가?"**

### 해결할 문제
나라장터에는 하루 수백 건의 공고가 뜹니다. 중소기업은 **읽을 시간이 없어서** 놓치고, 넣어도 **투찰가를 감으로** 씁니다.

**수치화**: 공고 N건 중 우리 회사 적격 공고를 얼마나 정확히 걸러내는가(정밀도/재현율), 낙찰가 예측 오차(MAPE), 그리고 **과거 데이터로 "우리 전략대로 넣었으면 몇 건 땄을지" 백테스트**.

### 검증 데이터 (실존 확인함, 공공데이터포털)
- **조달청_나라장터 입찰공고정보서비스** — 물품·용역·공사·외자 공고 목록, 추정가격, 면허제한, 지역제한, 공고 변경이력
- **조달청_나라장터 낙찰정보서비스** — **개찰결과, 최종 낙찰자, 개찰 순위, 복수예비가격**, 유찰·재공고 목록
- **공공데이터개방표준서비스** — 입찰·낙찰·계약 정보

→ **정답(누가 얼마에 땄는지)이 전량 공개**되어 있습니다. 백테스트 조건이 완벽합니다.

### 특별한 이유 / 주의
공모전 단골 소재이긴 합니다. 차별화하려면 **낙찰가 맞히기(회귀)에서 멈추지 말고**, ① 공고문 원문을 읽고 **자격요건 충족 여부를 판정**하는 문서이해 파트와 ② **복수예비가격 추첨 구조를 반영한 확률 모델**까지 가야 합니다. 거기까지 가면 흔하지 않습니다.

### 6인 모듈 분해
M1 공고 수집·정제 / M2 낙찰 이력 수집·매칭 / M3 공고문 요건 추출(LLM 구조화) / M4 적격 판별기 / M5 낙찰가·낙찰확률 모델 + 백테스트 / M6 대시보드(추천 공고 + 권장 투찰가 + 근거)

### W0 사전검증
API 키 발급 → 최근 3개월 공고·낙찰 각 5,000건 확보 / 공고-낙찰 **매칭키가 실제로 붙는지** (여기가 자주 깨짐) / 업종 1개로 단순 회귀 → MAPE 기준선 산출

### 성과 지표
적격 판별 F1 ≥ 0.8 / 낙찰가 MAPE **≤ 3%** / 백테스트 낙찰 적중률(상위 10% 추천 공고 기준) / 담당자 검토 공고 수 **90% 감축**

## 【4】 아파트 관리비 이상탐지 — "우리 아파트만 비싼가?"

> **"같은 규모·같은 지역·같은 난방방식 아파트 대비, 우리 단지 관리비 어느 항목이 비정상인가?"**

### 해결할 문제
관리비는 **48개 항목**으로 공개되지만, 일반 주민은 숫자를 봐도 **비교 기준이 없어서** 이상 여부를 모릅니다.

**수치화**: 항목별 유사단지 대비 편차(σ), 이상 판정 단지 수, 그리고 **"연간 초과 지출 추정액(원)"** — 발표에서 가장 강한 숫자입니다.

### 검증 데이터 (실존 확인함)
- **K-apt 공동주택관리정보시스템** (국토부 / 한국부동산원 위탁) — **관리비 등 48개 항목 공개**, 공용관리비·개별사용료·장기수선충당금 포함. **300세대 이상 의무관리대상**이 공개
- 공공데이터포털 **국토교통부_공동주택 기본 정보제공 서비스** (단지 기본정보), **공동주택 단지 면적 정보**
- API/파일 데이터로 JSON 제공

### 왜 검증이 되는가
① 동일 단지의 **과거 시계열**이 있어 급변 시점을 정답처럼 쓸 수 있고
② 관리비 부적정 **적발·감사 사례가 언론·지자체 감사보고서로 공개**되어 있어 **"우리 모델이 그 단지를 잡았는가"** 로 소급검증이 됩니다.

### 특별한 이유
"예측"이 아니라 **비교기준 생성(peer group matching)** 이 핵심입니다. 세대수·연식·난방방식·지역·복도형/계단형을 통제한 **유사단지 매칭**이 기술의 절반이고, 이걸 제대로 하는 서비스가 없습니다. 공익성도 커서 발표 반응이 좋습니다.

### 6인 모듈 분해
M1 관리비 수집(전국 다년치) / M2 단지 속성 수집·결합 / M3 **유사단지 매칭 모델** / M4 이상탐지(항목별 로버스트 z-score + 시계열 급변점) / M5 검증(소급검증·적발사례 대조) / M6 지도 대시보드 + 자연어 설명 생성

### W0 사전검증
데이터 다운로드 → **최소 3,000단지 × 12개월** 확보되는가 / 48개 항목 스키마 확인 / 결측·단위 오류 비율 측정

### 성과 지표
유사단지 매칭 품질(매칭군 내 분산 감소율 **≥ 40%**) / 소급검증 재현율 / 이상단지 비율 / **전국 초과지출 추정 총액(억 원)** / 설명 문장 정확도

### 리스크
**가장 쉬운 후보**라 기술 깊이가 얕아 보일 수 있음 → 유사단지 매칭에 학습 기반 임베딩을 쓰고, 이상 원인 설명을 LLM으로 생성해 **AI 비중을 확보**할 것.

## 【5】 폐업 위험 조기경보

> **"이 상권, 이 업종, 이 가게는 6개월 내 문 닫을 확률이 몇 %인가?"**

### 해결할 문제
창업 예정자와 프랜차이즈 본사, 상가 임대인은 **폐업 위험을 감으로** 판단합니다.

### 검증 데이터 (실존 확인함) — **라벨이 완벽한 게 최대 강점**
- **지방행정 인허가 데이터** (행안부) — 인허가 정보 **195종**(일반음식점·미용업·통신판매업 등), 전체분/월 변동분/일 변동분 제공. 컬럼에 **인허가일자·영업상태명·상세영업상태·폐업일자·휴업시작/종료일자·재개업일자**가 있어 "실제로 폐업했는가"가 정답 라벨로 그대로 존재. (LOCALDATA 포털은 2026-04-16 폐쇄되어 **공공데이터포털 data.go.kr로 이관**)
- **소상공인시장진흥공단 상가(상권)정보** — 상호·업종(대10/중75/소247)·주소·위경도

→ **미래 예측인데 정답이 이미 과거 데이터에 있습니다.** 2024년 시점 데이터로 예측 → 2025년 실제 폐업 여부로 채점. 완벽한 백테스트.

### 특별한 이유
상권분석 서비스는 많지만 대부분 **현황 통계**입니다. **개별 업소 단위 생존분석(survival analysis)** 은 드뭅니다. 여기에 **주변 경쟁 밀도 변화·신규 개업 유입** 같은 동적 피처를 넣으면 확실히 차별화됩니다.

### 6인 모듈 분해
M1 인허가 이력 수집(다년치) / M2 상권 피처 생성(반경 내 동종업 밀도·개폐업률·변화율) / M3 시점 분리 데이터셋 구축(**누수 차단이 핵심**) / M4 모델(생존분석 + 그래디언트 부스팅 + 시계열) / M5 평가(AUROC, C-index, 시점별 안정성) / M6 지도 대시보드 + 위험 원인 설명

### W0 사전검증
전체분 다운로드 크기·컬럼 확인 / **폐업일자 결측률** 측정 / 단순 로지스틱 회귀로 AUROC 기준선 산출

### 성과 지표
6개월 폐업 예측 **AUROC ≥ 0.75** / 상위 10% 위험군의 실제 폐업률(리프트 **3배 이상**) / 업종·지역별 성능 편차 / 피처 중요도 해석표

### 리스크
**데이터 누수**가 이 주제의 최대 함정(미래 정보가 피처에 섞임). M3 담당자가 시점 분리를 전담하고, 나머지 5명은 M3가 만든 데이터셋만 사용하도록 강제.

## 【6】 국회 의안 통과 예측 — "이 법, 통과될까?"

> **"발의된 법안 중 실제로 통과되는 건 소수다. 어떤 법안이, 왜 통과되는가?"**

### 해결할 문제
기업·협회·시민단체는 자기 사업에 영향 주는 법안을 추적해야 하는데, **발의안이 너무 많아** 무엇에 대응할지 모릅니다.

### 검증 데이터 (실존 확인함)
- **열린국회정보 OPEN API** (open.assembly.go.kr) — **의안정보 통합 API, 국회의원 발의법률안, 법률안 심사 및 처리(의안검색), 본회의 표결정보**
- 공공데이터포털 **국회사무처_국회의원 발의법률안**, **국회의원 정보 통합 API**

→ **과거 국회의 모든 의안과 그 처리결과(가결/부결/폐기/임기만료)가 전량 공개.** 완전 백테스트.

### 특별한 이유
**아무도 안 합니다.** 그런데 대외협력·정책·리걸테크 쪽에서 실제 수요가 있고, "AI가 정치 데이터를 읽는다"는 발표 소재가 강합니다. 텍스트(법안 제안이유·주요내용) + 구조(발의자 수·소속·상임위·발의 시점) + 네트워크(공동발의 그래프)를 **전부 써야 성능이 나오는 멀티모달 문제**라 기술적으로도 재밌습니다.

### 6인 모듈 분해
M1 의안·처리결과 수집 / M2 발의자·상임위·정당 메타 결합 / M3 **공동발의 네트워크 피처**(중심성 등) / M4 법안 본문 임베딩·주제 분류 / M5 모델 + 시점 분리 백테스트 / M6 대시보드(통과 확률 랭킹 + 근거 요인 + 유사 과거 법안)

### W0 사전검증
API 키 발급 → 최근 2개 국회분 의안 전량 수집되는가 / 처리결과 라벨 분포 확인 / 텍스트 없이 메타데이터만으로 AUROC 기준선

### 성과 지표
통과 예측 **AUROC ≥ 0.75** / 텍스트 추가 시 향상폭(**메타 대비 +몇 %p인가가 핵심 발견**) / 상임위별 성능 / 요인 중요도 (발의자 수? 여당 여부? 상임위? — **데이터로 답하는 것 자체가 결과물**)

### 주의
**정치적 중립**이 필수입니다. 특정 정당 유불리 해석을 결론으로 내지 말고, **"예측 정확도"와 "요인 기여도"까지만** 보고할 것. 이 원칙을 발표에 명시하면 오히려 완성도가 높아 보입니다.

## 【7】 보이스피싱 실시간 탐지 — "통화 중 몇 초 만에 잡는가"

> **"경고는 통화가 끝난 뒤에 오면 소용없다. 통화 시작 30초 안에 잡아야 한다."**

### 해결할 문제
기존 앱은 대부분 **번호 기반 차단**이라 신종 번호에 무력합니다. **대화 내용 기반 실시간 판정**이 필요합니다.

**수치화**: **탐지까지 걸린 시간(초)**, 오탐률(정상 통화를 사기로 오판), 온디바이스 처리 지연. "몇 초 만에 잡느냐"는 발표에서 가장 강렬한 숫자입니다.

### 검증 데이터 (실존 확인함 + **한계도 명시**)
- **금융감독원 보이스피싱지킴이** (phishing-keeper.fss.or.kr) — 2026년 4월 사기범 **7명의 실제 목소리 공개**. 2024년 제보 음성 **3,959건**을 국과수 성문 분석으로 걸러낸 것
- 금감원·경찰청의 **실제 피해 시나리오·수법 유형** 공개 자료

> ⚠️ **정직한 한계**: 공개된 **음성 파일 자체는 표본 수가 적습니다.** 그래서 이 프로젝트는
> ① 공개 수법·대본을 **텍스트 시나리오로 구조화**하고 ② TTS로 음성 증강하며 ③ 일반 통화(공개 한국어 음성 코퍼스)를 정상 클래스로 삼는 구성이 현실적입니다.
> **W0에서 확보 가능한 실제 음성 건수를 반드시 세어보고, 부족하면 "텍스트 단계 탐지"로 범위를 축소**하세요.

### 6인 모듈 분해
M1 시나리오·수법 데이터 구축 / M2 음성 데이터 생성·증강(TTS + 잡음·전화대역 시뮬레이션) / M3 스트리밍 STT(부분 전사) / M4 실시간 분류기(슬라이딩 윈도, 조기판정) / M5 평가(탐지 지연·오탐 곡선) / M6 앱 데모 UI(실시간 경고)

### W0 사전검증
공개 음성 실제 확보 건수 세기 / 스트리밍 STT 부분 전사 지연 측정 / **"몇 초 분량이면 판정 가능한가"** 예비 실험

### 성과 지표
**탐지 지연 중앙값 ≤ 20초** / 오탐률 ≤ 5% / 온디바이스 추론 지연 / 수법 유형별 탐지율

### 리스크
**난이도 상.** 음성이 붙으면 4주에 벅찹니다. **"텍스트(전사문) 기반 조기탐지"로 먼저 완성하고, 음성은 여유가 있으면 붙이는** 단계 설계를 권합니다.

## 【8】 계약서 독소조항 대조 탐지

> **"이 계약서, 표준약관 대비 무엇이 나에게 불리하게 바뀌었는가?"**

### 해결할 문제
프리랜서·소상공인·스타트업은 계약서를 받아도 **무엇이 불리한지 모릅니다.** "요약해주는" 서비스는 있지만, **표준과 대조해서 다른 지점을 짚어주는** 건 드뭅니다.

### 검증 데이터
- **공정거래위원회 표준약관 / 표준계약서**, 문화체육관광부 등 부처별 **표준계약서** (공개)
- 법제처 API의 관련 법령 조문 (약관규제법 등)
- 지자체·공공기관의 **공개 계약서 양식**

**라벨 생성**: 표준계약서에 **의도적으로 불리한 변형을 주입**해 정답을 자동 생성합니다(조항 삭제, 기한 단축, 배상 상한 신설, 일방 해지권 추가 등 유형화). 후보 2와 같은 "자동 라벨" 전략입니다.

### 특별한 이유
"요약"이 아니라 **조항 단위 정렬(alignment) + 차이 판정 + 불리함 방향 판단**의 3단 문제입니다. LLM에 그냥 던지면 안 되고 구조를 짜야 해서 기술 깊이가 나옵니다.

### 6인 모듈 분해
M1 표준계약서 수집·조항 분해 / M2 변형 주입 엔진(라벨 자동 생성) / M3 **조항 정렬 모델**(표준 ↔ 대상 매칭) / M4 차이 판정 + 불리함 방향·심각도 분류 / M5 채점 하네스 / M6 UI(나란히 비교 + 위험도 색상 + 근거 법령)

### W0 사전검증
표준계약서 20종 확보 / 조항 자동 분해 정확도 측정 / 변형 주입 50건 → 사람이 "불리함" 판정에 동의하는가

### 성과 지표
조항 정렬 정확도 ≥ 90% / 독소조항 탐지 재현율 ≥ 80% @ 오탐 ≤ 15% / 심각도 분류 정확도 / 검토 시간 절감

## 【9】 RAG 답변 근거 형광펜 (기술 카드)

> **"AI 답변에서 근거 문서에 없는 문장에 빨간 줄을 긋는다."**

### 근거 수치 (영어권 공개 실측 — 재현 가능)
RAGTruth 벤치마크(구간 주석 **18,000건**, 학습 15,090 / 평가 2,700) 응답 단위 F1:

| 방식 | 크기 | F1 |
|---|---|---|
| GPT-4 프롬프트 | – | **63.4%** |
| Llama-2-13B 파인튜닝 | 13B | 78.7% |
| **LettuceDetect (ModernBERT)** | **396M** | **79.22%** |

비용: MiniCheck(770M)이 LLM-AggreFact **74.7%** vs GPT-4 **75.3%** — 차이 0.6%p인데 **13,000건 검증에 $0.24 vs $107 (약 400배)**.

한국어에는 **K-HALU**(ICLR 2025, 7개 도메인, 40% 복수정답), **K-FinHallu**(2026, 금융 멀티턴) 같은 **평가 벤치마크는 있는데 구간 단위 탐지 모델은 없습니다.**

### 이 조건(4주·바이브코딩)에서의 현실적 범위
모델을 크게 학습하기보다 **① 공개 영어 모델 재현 → ② 한국어 이식 → ③ 규칙·임베딩·LLM 3방식 캐스케이드 비교**로 잡으세요.

### 6인 모듈
M1 한국어 RAG 데이터 생성 / M2 자동 오류 주입 / M3 탐지기 A(규칙+임베딩) / M4 탐지기 B(소형 모델/LLM) / M5 채점(F1·AUROC·비용·지연) / M6 형광펜 UI

### 성과 지표
한국어 구간 F1 / GPT-4 프롬프트 대비 **+8%p** / 1만 건 비용 **1/50 이하** / p95 지연 ≤ 150ms

## 【10】 한국어 Text-to-SQL (기술 카드, 채점 논쟁 0)

> **"DB가 직접 채점한다. SQL을 실행해서 결과가 같으면 정답."**

### 근거 수치 (BIRD 벤치마크)
**12,751 질문-SQL 쌍, 95개 DB, 37개 도메인.** 인간 **92.96%** vs 현재 1위 Gemini-SQL2 **80.04%** (**12.92%p 격차**), Claude Opus 4.6·AWS Q-SQL 약 70.1%.
→ **프론티어 모델도 못 푼 문제이고, 이 숫자는 전부 영어 기준입니다.**

### 빈칸

### 6인 모듈

### 성과 지표

## 【11】 AI 에이전트 툴콜 신뢰성 진단 (기술 카드)

> **"에이전트가 도구를 5번 연속 부르면 왜 무너지는가."**

### 근거 수치 (BFCL v4, Berkeley)
- **멀티턴 점수는 단일턴 대비 모든 모델에서 5~10점 하락**
- 5회 이상 연속 호출 시 **유효 정확도는 멀티턴 점수가 복리로 곱해짐**
- 멀티턴 4개 하위셋: base / long-context / **missing-function** / **missing-parameter**
- 프론티어 API와 최상위 오픈웨이트 격차는 **3~4%p**까지 축소

### 6인 모듈

### 성과 지표

## 【12】 의약품 병용·이상사례 신호 조기탐지

> **"이 약 두 개 같이 먹어도 되나? 그리고 아직 안 알려진 위험 신호가 있나?"**

### 검증 데이터 (**W0 확인 필수**)
- **식약처 공공데이터**: 의약품 허가·심사, **의약품개요정보(e약은요)** — 효능·사용법·주의사항·**상호작용·부작용** 항목 포함. data.go.kr / data.mfds.go.kr 에서 무료 제공
- 이상사례 보고는 **한국의약품안전관리원(KAERS)** 소관

> ⚠️ **정직한 한계**: **원시 이상사례 보고 데이터는 신청·제한이 있을 수 있습니다.** W0에서 **실제로 받아지는 범위**를 먼저 확인하고, 안 되면 **허가정보에 명시된 상호작용·금기 정보를 정답으로 삼는 "병용금기 판정" 문제로 범위를 좁히세요.**

### 검증 방법
**알려진 병용금기 목록을 정답으로 두고, 우리 시스템이 그것을 재발견하는지**로 채점합니다(소급검증). 재발견률이 높으면 **아직 목록에 없는 후보 신호**의 신뢰도도 올라갑니다.

### 6인 모듈
M1 의약품 데이터 수집·성분 정규화 / M2 병용금기 정답셋 구축 / M3 성분-성분 그래프 구축 / M4 신호 탐지 모델 / M5 소급검증 하네스 / M6 조회 UI(복용 목록 입력 → 위험 경고 + 근거)

### 성과 지표
알려진 금기 재발견률 **≥ 85%** / 오탐률 / 성분명 정규화 정확도 / 신규 후보 신호 상위 20건 + 문헌 대조

### 주의
**의료 조언이 아님을 명시**하고, 결과는 "확인 필요" 수준으로만 표기.

# 3. 추천 순위와 선택 가이드

| 상황 | 추천 |
|---|---|

| **데이터·라벨이 가장 확실해서 실패 확률 최저** | **【5】 폐업 예측** 또는 **【4】 관리비 이상탐지** |

| **AI 기술 스택을 정면으로 보여주고 싶다** | **【9】 근거 형광펜** 또는 **【10】 Text-to-SQL** |

### 제 1순위 추천: 【1】 + 【2】 결합
같은 데이터(법제처 개정 이력) 위에서 돌아가고, 모듈도 겹칩니다.
**"규제가 바뀌면 → 우리 문서 중 무엇이 낡았는지 찾아내고 → 무엇을 고쳐야 하는지 제안한다"** 하나의 제품이 됩니다.

- **사업성 카드**: 컴플라이언스·리걸테크 실수요, 절감 시간을 원 단위로 환산 가능
- **기술 카드**: 변경 전파 탐지, 자동 라벨 생성, 하이브리드 검색, 근거 추출 — AI 비중 충분
- **수치화 카드**: 과거 개정 이력으로 **사람 라벨 없이 백테스트** → Recall@20, AUROC, 절감률
- **바이브코딩 적합성**: 모듈 6개가 자연스럽게 갈라지고, GPU 대규모 학습이 필요 없음

# 4. 어떤 걸 고르든 지킬 규칙

1. **9/11(목)까지 W0 사전검증 끝낸다.** 데이터가 실제로 손에 안 들어오면 **그날 주제를 바꿉니다.** 12개를 준비한 이유입니다.
2. **W1 첫날 = JSON 스키마 6개 동결.** 코드보다 인터페이스가 먼저. 이후 스키마 변경은 전원 합의 필요.
3. **W1 안에 더미 데이터로 6모듈 전 구간 관통.** 통합을 마지막에 하면 반드시 터집니다.
4. **채점기는 1명 전담, 나머지는 수정 금지.** 성능 숫자의 신뢰가 여기서 나옵니다.
5. **베이스라인 먼저.** "우리 모델 F1 0.82"는 비교 대상이 없으면 의미가 없습니다. 반드시 단순 방법(규칙·랜덤·기존 도구) 숫자를 먼저 만듭니다.
6. **매주 금요일 숫자 1개 갱신.** 성능표의 셀이 매주 최소 1개 채워져야 합니다.
7. **10/13 기능 동결.** 이후엔 코드 안 건드리고 발표만 준비합니다.
8. **인용한 숫자는 W0에 원문 대조.** 이 문서의 수치도 예외 없습니다.
