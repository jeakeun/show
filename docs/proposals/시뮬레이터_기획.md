# 시뮬레이터 프로젝트 주제 10개 + AI 기술 + 기술 스택 (쉬운 설명판)

기간: 2026년 9월 9일 ~ 10월 20일 · 6명 · 실제 개발 4주

> **시뮬레이터** = 값을 바꾸면 결과가 바뀌는 것. **"이렇게 하면 어떻게 될까?"** 를 직접 만져보는 도구.

---

# 0. 왜 시뮬레이터가 유리한가

| 그냥 예측 프로그램 | 시뮬레이터 |
|---|---|
| "이 지역 위험도 62%입니다" | **"시설 하나 없어지면 62% → 81%로 올라갑니다"** |
| 심사위원이 화면을 **본다** | 심사위원이 **직접 만진다** |
| 성능표를 설명해야 이해됨 | **슬라이더 한 번 당기면 바로 이해됨** |

---

# 1. 주제 고르는 기준 ① — 우산과 비

## 아무 예측 모델에 슬라이더를 붙이면 거짓말이 됩니다

> "우산 든 사람이 많으면 비가 온다"는 프로그램을 만들었습니다. **실제로 잘 맞습니다.**
>
> 그런데 시뮬레이터로 만들어서 **"우산 든 사람" 슬라이더를 0으로 내리면**
> 프로그램은 **"비가 안 옵니다"** 라고 답합니다.
>
> **말이 안 되죠.** 우산은 비의 **원인이 아니라 결과**니까요.

**예측 프로그램은 "같이 움직이는 것"을 배웁니다. "뭐가 뭘 만드는지"는 모릅니다.**

## 그래서 조절 항목은 이 두 가지를 다 만족해야 합니다

| 조건 | 좋은 예 | 나쁜 예 |
|---|---|---|
| ① **사람이 진짜 정하는 값인가** | 충전기를 몇 대 놓을까 | 이 동네 인구가 늘면 |
| ② **그 값이 결과를 직접 만드는가** | 병원이 없으면 그 병원엔 못 감 | 경쟁 가게가 줄면 장사가 잘 될까 |

**이 문서의 10개는 전부 이 조건을 통과합니다.**

---

# 2. 주제 고르는 기준 ② — AI가 장식이면 안 됩니다 ⭐

## 흔한 실수: AI를 맨 끝에 붙이기

```
❌ 나쁜 구조
   데이터 → 공식으로 계산 → 결과 → 마지막에 AI가 결과를 문장으로 읊음
                                        └── 이게 "장식"입니다

   "이 AI 뭐 하는 건가요?" → "결과를 말로 설명해줍니다" → 심사에서 무너집니다
```

```
✅ 좋은 구조
   데이터 → AI가 핵심 값을 예측 → 그 값으로 시뮬레이션 → 결과
                └── AI가 빠지면 시뮬레이터가 아예 안 돌아감
```

> **판정 기준은 딱 하나입니다.**
> **"AI를 빼면 이 시뮬레이터가 돌아가나요?"**
> 돌아가면 그 AI는 장식입니다.

## 우리 주제로 예를 들면

| 시뮬레이터 | AI를 빼면? | 판정 |
|---|---|---|
| 충전소 대기시간 | **"몇 대가 올지"를 모르면 대기시간 계산 자체가 불가능** | ✅ AI가 엔진 |
| 산불 피해 예측 | **"얼마나 번질지"가 곧 AI의 출력** | ✅ AI가 엔진 |
| 응급실 접근성 | 최단거리만 계산해도 돌아감 (**단, 정확도가 크게 떨어짐**) | ⚠️ 보강 필요 |

> **⚠️ 이게 이번 추천에서 순위가 바뀐 이유입니다.**
> 앞서 응급실을 1위로 했는데, **AI가 필수 조건**이라면
> **충전소와 산불이 더 안전합니다.** 응급실은 아래 3-1에 적은 AI 3종을 반드시 넣어야 합니다.

# 【1위】 전기차 충전소 입지 시뮬레이터 ⭐ AI 조건까지 고려한 1등

## 한 줄로

> **"여기에 충전기 3대를 놓으면, 줄 서는 시간이 얼마나 줄어들까?"**

**누가 쓰나**: 충전 사업자, 지자체, 아파트 관리사무소, 대형마트·주유소

## 화면

```
┌───────────────────────────────────────────────┐
│  [지도] 📍 강남구 역삼동 ○○                    │
│                                               │
│  급속 충전기  ◀━━●━━━━━▶   2 대               │
│  완속 충전기  ◀━━━━●━━━▶   4 대               │
│                                               │
│  ┌─────────────────────────────────────┐      │
│  │ 평균 대기시간   18분 → 4분            │      │
│  │ 충전기 이용률   94% → 61%            │      │
│  │ 헛걸음 비율     31% → 6%             │      │
│  │ 하루 처리 대수  47대 → 112대          │      │
│  └─────────────────────────────────────┘      │
│                                               │
│  💰 1대 더 놓으면 4분 → 2분                   │
│     (효과가 꺾이는 지점입니다)                  │
└───────────────────────────────────────────────┘
```

## AI가 어디에 들어가나 (★ = 엔진)

| 순서 | 하는 일 | 기술 | AI인가 |
|---|---|---|---|
| ① | 주변 환경 파악 (아파트/사무실/상가 수) | 공간 집계 | ✗ |
| ② | **★ 시간대별로 몇 대가 올지 예측** | **머신러닝 (LightGBM)** | **✅ 엔진** |
| ③ | 그 수요로 줄 서기를 재현 | **가상 시간 시뮬레이션 (SimPy)** | 수학·시뮬레이션 |
| ④ | 최적 대수 찾기 | 반복 실행 + 탐색 | 부분적 |
| ⑤ | 결과 설명 문장 | Claude | 장식 (있으면 좋음) |

> **②가 빠지면 아무것도 안 돌아갑니다.**
> "몇 대가 올지"를 모르면 대기시간을 계산할 수가 없습니다.
> **AI가 뼈대에 확실히 박혀 있습니다.**

### ② 수요 예측 모델이 배우는 것
```
입력: 요일, 시간대, 공휴일 여부, 날씨, 주변 아파트 수,
      주변 사무실 수, 주변 상가 수, 근처 다른 충전소까지 거리,
      최근 4주 평균 이용량
출력: 이 시간대에 올 차량 대수
```

## 데이터 (직접 확인함)

| 뭘 받나 | 어디서 | 뭐가 들어있나 |
|---|---|---|
| 전기자동차 충전소 정보 | data.go.kr/data/15076352 (한국환경공단) | 충전소 ID, **충전기 타입**, 주소, **위도·경도**, 운영기관 |
| **서울시 충전소 충전량** | data.seoul.go.kr (OA-22249) | **충전량, 충전시간, 날짜, 최대용량** ← 실제 사용 기록 |

> **"충전시간"과 "날짜"가 있는 게 결정적입니다.** 언제 얼마나 오래 충전했는지를 알면 **줄이 얼마나 길었을지 역산**됩니다.

## 채점 방법

> **충전기가 새로 늘어난 충전소를 찾습니다.**
> 늘기 전 데이터로 "이만큼 늘리면 대기가 이렇게 될 것"이라 예측하고,
> **실제 늘어난 뒤 데이터와 비교**합니다.

## 6명 분업

| 담당 | 하는 일 | AI |
|---|---|---|
| 1번 | 전국 충전소 데이터 수집·정리 | – |
| 2번 | 충전 기록 → **시간대별 수요 곡선** 만들기 | – |
| 3번 | 주변 환경 정보 결합 (아파트·사무실·상가) | – |
| **4번** | **수요 예측 모델** | **핵심** |
| **5번** | **줄 서기 시뮬레이션 + 채점** | 시뮬레이션 |
| 6번 | 지도 화면 + 슬라이더 | – |

## 목표 숫자

| 뭘 재나 | 목표 |
|---|---|
| 수요 예측 오차 | **20% 이내** |
| 증설 사례 검증 오차 | **30% 이내** |
| 이용률 예측 정확도 | 실측 대비 15%p 이내 |

## ⚠️ AI를 반드시 3개 넣어야 합니다

> **그냥 만들면 "최단거리 계산기"가 됩니다.** AI 필수 조건을 못 통과합니다.
> **아래 3개를 반드시 넣으세요. 넣으면 AI 비중이 ★★★★로 올라갑니다.**

| 순서 | 하는 일 | 기술 | AI인가 |
|---|---|---|---|
| ① | 도로망 최단경로 | 그래프 알고리즘 | ✗ (기본기) |
| ② | **★ 실제 이송시간 보정 모델** | **머신러닝** | **✅ 반드시 넣기** |
| ③ | **★ 응급환자 발생 수요 예측** | **머신러닝** | **✅ 반드시 넣기** |
| ④ | **★ 최적 신설 위치 찾기** | **조합 최적화 (OR-Tools)** | **✅ 반드시 넣기** |
| ⑤ | 정책 브리핑 문서 생성 | Claude | 장식 |

### ② 이송시간 보정 모델이 필요한 이유
> **지도상 최단경로 시간과 실제 구급차 도착시간은 다릅니다.**
> 새벽 3시와 출근길 8시가 다르고, 산길과 고속도로가 다릅니다.
> **시간대·도로등급·계절로 보정하는 모델**을 학습시킵니다. 이게 정확도를 크게 올립니다.

### ③ 수요 예측이 필요한 이유
> **인구가 같아도 응급환자 수는 다릅니다.** 고령 인구가 많으면 훨씬 많습니다.
> **격자별 인구 구조로 "여기서 응급환자가 얼마나 나올지"를 예측**해서 가중치를 줍니다.
> 그래야 "몇 명이 위험한가"가 아니라 **"실제로 몇 건의 응급상황이 위험한가"** 가 됩니다.

### ④ 최적 입지 찾기가 왜 어려운가
> 후보 지점이 5,000곳이면 **하나씩 다 해볼 수가 없습니다.**
> "3곳을 고른다"면 경우의 수가 **200억 가지**가 넘습니다.
> **똑똑하게 좁혀가며 찾는 방법**이 필요하고, 그게 기술 포인트가 됩니다.

## 4-2. 시뮬레이터에만 쓰는 특별한 도구 4개

### ① SimPy — **가상의 시간을 흐르게 하는 도구** (시뮬레이터의 심장)

> 컴퓨터 안에서 **가짜 시계를 돌립니다.**
>
> ```
> 09:03  차 A 도착 → 충전기 비어있음 → 바로 충전 시작
> 09:07  차 B 도착 → 충전기 다 참 → 줄 섬 (대기 시작)
> 09:31  차 A 충전 완료 → 떠남 → 차 B 충전 시작 (24분 기다림)
> ```
>
> 이걸 하루치, 한 달치 돌려서 **"평균 몇 분 기다렸나"** 를 셉니다.
> **충전소·택시·대피소 시뮬레이터의 핵심**입니다.

### ② OSMnx + NetworkX — **내비게이션을 직접 만드는 도구**

> **OSMnx**: 전 세계 도로 지도를 무료로 받아옵니다.
> **NetworkX**: 도로를 **점과 선**으로 바꿔서 **가장 빠른 길**을 찾습니다.
>
> 쉽게 말하면 **티맵의 길찾기 엔진을 우리가 직접 만드는 것**입니다.
> **응급실·학교·대피소 시뮬레이터의 핵심**입니다.
>
> ⚠️ 전국을 한 번에 하면 너무 느립니다. **시군구 단위로 나눠서** 계산하세요.

### ③ OR-Tools — **수천 개 후보 중 최선의 조합을 찾는 도구** (구글이 만듦)

> **"응급실 3곳을 새로 짓는다면 어디?"**
> 후보가 5,000곳이면 3곳을 고르는 경우의 수가 **200억 가지**가 넘습니다.
> 하나씩 다 해보면 컴퓨터가 몇 년 돌아야 합니다.
>
> OR-Tools는 **똑똑하게 가지치기하면서** 좋은 답을 빠르게 찾습니다.
> 구글이 배달 경로 짤 때 쓰는 도구입니다.

### ④ folium / pydeck — **지도 위에 색칠하고 점 찍는 도구**

> **folium**: 간단한 지도. 만들기 쉬움. Streamlit과 잘 붙음
> **pydeck**: 화려한 지도. 격자 수만 개를 부드럽게 그림. **시연용으로 훨씬 예쁨**
>
> **추천**: 개발 중엔 folium으로 빠르게, **마지막 주에 pydeck으로 화려하게** 바꾸기

# 5. 최종 추천 (AI 필수 조건 반영)

| 상황 | 추천 | 왜 |
|---|---|---|
| **AI 조건을 가장 안전하게 통과** | **1번 충전소** | 수요 예측이 없으면 시뮬레이터가 아예 안 돌아감. 데이터도 가장 확실 |
| **시연이 가장 화려** | **2번 산불** | 예측 모델이 곧 시뮬레이터. 지도에 불이 번지면 시선 고정 |
| **사회적 임팩트 최고** | **3번 응급실** | 단, **AI 3종(이송시간 보정·수요 예측·최적 입지)을 반드시 넣을 것** |
| **데이터 품질 최고** | **4번 버스** | 노선×정류장×시간대가 전부 공개 |

## 하나만 고르라면: **1번 충전소**

1. **AI가 뼈대에 박혀 있습니다.** "몇 대가 올지" 예측이 없으면 대기시간 계산이 불가능합니다.
2. **데이터가 가장 확실합니다.** 충전 시작·종료 시각까지 있습니다.
3. **검증이 됩니다.** 충전기를 늘린 충전소의 전후 데이터로 맞춰볼 수 있습니다.
4. **"누가 씁니까?"에 바로 답이 됩니다.** 충전 사업자와 지자체가 실제로 하는 고민입니다.

## 가성비 조합: **3번 + 7번** (응급실 + 학교)

> 둘 다 **"시설이 없어지면 얼마나 멀어지나"** 라서 **계산 엔진이 똑같습니다.**
> 하나 만들어서 둘 다 보여줄 수 있습니다.

# 6. 팀이 빠지는 함정 3개

## 함정 1 — 껍데기에 시간을 다 쓴다
> 시뮬레이터는 **화면이 예뻐서 만드는 재미**가 있습니다.
> **예쁜 화면에 틀린 숫자가 나오면 그건 예쁜 거짓말입니다.**
>
> **막는 법**: 화면은 **4주차(10/3~10/9)에 시작.** 3주차까지 예측 정확도가 안 나오면 화면을 줄이고 모델에 집중.

## 함정 2 — 슬라이더를 너무 많이 만든다
> **5개를 넘으면 사용자가 뭘 만져야 할지 모릅니다. 3개면 충분합니다.**

## 함정 3 — 시뮬레이터 자체의 정확도를 안 잰다
> "슬라이더를 당기면 숫자가 바뀐다"만으로는 부족합니다.
> - 충전소: 증설 사례에서 예측이 실제와 얼마나 맞았나
> - 산불: 과거 산불의 실제 피해면적과 얼마나 맞았나
> - 응급실: 정부 지정 취약지를 몇 % 재현했나
>
> **이 검증을 넣는 팀은 거의 없습니다. 넣으면 확실히 차별화됩니다.**

**W0에 반드시 확인 (공통)**

- [ ] **예측 모델에 넣을 정답이 데이터에 있나** (충전량 / 피해면적 / 취약지 목록)
- [ ] **모델을 한 번이라도 학습시켜서 숫자가 나오나** ← AI 조건의 생사
- [ ] 핵심 계산(대기시간·이송시간)이 한 지역에서라도 돌아가나
