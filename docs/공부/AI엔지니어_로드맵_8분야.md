# AI 엔지니어 로드맵 8분야 — 공부 순서·개념·활용법·문제

작성: 2026-11-23 (공부 세션) · 코덱스 검토 18건 반영 (맨 아래 "검토 기록")
출처: 페이스북 릴스 (Sambit Das, @sambit.ai.tech, 28초) "AI 엔지니어가 되려면 160개 개념을 익혀라"

## 0. 이 영상이 말하는 것
- AI 엔지니어가 알아야 할 것을 **8개 분야 × 20개 = 160개 개념**으로 나눴다는 소개 영상입니다.
- 영상 화면에는 분야마다 **앞의 4개만** 나옵니다 → 이 노트는 그 **32개**를 다룹니다.
- 나머지 128개는 "댓글에 AI라고 쓰면 DM으로 PDF를 준다"는 방식이라 영상에는 없습니다.
  (댓글 달고 받는 건 직접 하셔야 합니다. 대신 분야마다 "더 볼 것"에 제가 중요하다고 보는 개념을 몇 개 적어 뒀습니다.)

### 영상 속 8분야 (영상 순서)
1. LLM — 모델이 어떻게 움직이나
2. RAG — AI에게 내 문서를 주기
3. AI 에이전트 — 도구를 쓰는 AI
4. 평가(Evals) — AI 시험 보기
5. AI 시스템 설계
6. AI 보안
7. 배포 — 실제로 내놓기
8. 백엔드 — AI를 둘러싼 코드

## 1. 내 공부 순서 (영상 순서와 다르게 바꿈)

영상은 분야를 소개하는 순서일 뿐입니다. 저는 **이미 돌리고 있는 자동화를 이해하는 것**을 기준으로 순서를 다시 정했습니다.

| 순서 | 분야 | 왜 이 순서? |
|---|---|---|
| 1 | LLM | 모든 것의 바닥. 토큰을 알아야 비용·한도가 이해됨 |
| 2 | AI 에이전트 | 이미 Claude Code로 매일 쓰는 것. 아는 것부터 이름 붙이기 (하네스 노트와 연결) |
| 3 | 평가 | 유튜브 자동화의 반복 가드가 이미 평가. 만들면 바로 시험해야 함 |
| 4 | AI 보안 | 자동화가 웹을 읽고 메모리를 올리니 바로 필요 |
| 5 | AI 시스템 설계 | 이미 "대본은 Opus, 작은 일은 다른 모델"을 하고 있음 → 이름 배우기 |
| 6 | RAG | 회사 문서 챗봇 같은 사내 자동화에 가장 많이 쓰임 |
| 7 | 백엔드 | 냠냠플래닛에서 FastAPI를 써봄. 직접 서비스 만들 때 필요 |
| 8 | 배포 | 외부 API로 시작한다면 모델을 직접 운영할 일이 없음 → 우선순위 가장 낮음 |

**다른 길:** 회사에서 **사내 문서 챗봇**을 바로 만들어야 하면, 1단계(토큰·임베딩) 다음에 **6단계 RAG를 작게 실습**하면서 평가(3)·보안(4)을 같이 배우는 게 더 빠릅니다.

**냉정한 판단:** 비개발자 인턴에게 1~5번은 바로 쓸모가 있고, 6~7은 사내 자동화를 만들 때, 8번은 당분간 "단어만 알면 되는" 수준입니다.

## 2. 분야별 정리

각 개념 = **뜻(쉬운 말)** / **활용(내 일에서)**

### 1단계: LLM — 모델이 어떻게 움직이나

| 개념 | 뜻 | 활용 |
|---|---|---|
| 토큰 (Tokens) | 모델이 글을 처리하는 **조각**. 단어 일부일 수도, 단어 전체나 기호일 수도 있음 | 토큰 단위로 요금을 받는 API에서는 **입력+출력 토큰 수**가 비용. 같은 뜻이라도 언어·모델마다 토큰 수가 다르니 실제 모델로 세어 봐야 함. Code Mode를 켠 것도 토큰을 아끼려는 것 |
| 임베딩 (Embeddings) | 글의 특징을 **숫자 목록(벡터)** 으로 바꾼 것. 같은 임베딩 모델로 만든 벡터끼리 비교하면 **뜻이 비슷한 글**을 찾을 수 있음 | "같은 주제 반복 금지" 검사를 글자 비교 대신 뜻 비교로 할 수 있음 |
| 트랜스포머 (Transformers) | 토큰 사이의 관계를 계산하는 **모델 설계도**. 지금 대부분의 LLM이 이 설계를 씀. 글을 만드는 LLM은 **다음 토큰을 하나씩 이어 붙여** 답을 만듦 | 문장이 자연스럽다고 사실이 확인된 건 아님 → 중요한 숫자·사실은 따로 확인 |
| 셀프 어텐션 (Self-attention) | 각 토큰을 이해할 때 **같은 글 안의 다른 토큰들을 서로 다른 비중으로 참고**하는 계산 | "그것"이 무엇을 가리키는지 해석하는 데 도움이 됨. 지시문이 너무 길면 중요한 말이 묻힐 수 있음 |

더 볼 것: 컨텍스트 창(한 번에 읽을 수 있는 양), 온도(temperature, 답의 무작위성), 환각(hallucination)

### 2단계: AI 에이전트 — 도구를 쓰는 AI

| 개념 | 뜻 | 활용 |
|---|---|---|
| 에이전트 루프 (Agent loop) | 모델이 다음 행동이나 도구 사용을 **제안** → 실행 환경이 확인·실행 → 결과를 모델에 돌려줌 → 반복. **일을 마쳤거나 횟수·시간 한도에 닿으면** 멈춤 | 하네스 노트의 "반복 고리"와 같은 것. 무인 자동화엔 멈춤 조건(한도)이 꼭 필요 |
| 도구 호출 (Tool calling) | 모델이 "이 도구를 이 값으로 써줘"라고 **요청**하면, 실행 환경이 값과 권한을 확인한 뒤 실행(또는 거절) | 모델은 요청만, 실행은 하네스. 사내 자동화에서 "메일 보내기" 도구를 줄지 말지가 핵심 결정 |
| 도구 설명서 (Tool schemas) | 도구 이름·하는 일·받는 값을 적은 **사용 설명서** | 설명이 엉성하면 AI가 도구를 잘못 씀 → 설명서를 잘 쓰는 게 성능을 좌우 |
| 정해진 형식 출력 (Structured outputs) | 답을 **정해진 틀(스키마: 어떤 칸에 어떤 종류 값)** 에 맞춰 내게 하기. 지시문으로 부탁하는 것보다 기능으로 **강제**하는 쪽이 확실 | 엑셀·시트에 바로 넣기 좋음. 단, **틀이 맞아도 내용이 원문과 다를 수 있음** → 내용 확인은 따로 |

더 볼 것: MCP(도구를 꽂는 표준 콘센트), 멀티 에이전트, 사람 승인 단계(human-in-the-loop)

### 3단계: 평가(Evals) — AI 시험 보기

| 개념 | 뜻 | 활용 |
|---|---|---|
| 모범 답안 묶음 (Golden dataset) | 사람이 확인한 **입력 + 기대 결과(또는 채점 기준)** 모음. 정답이 여러 개인 문제, "모르면 모른다고 해야 하는" 문제도 넣을 수 있음 | 사내 챗봇을 만들면 자주 받는 질문 20개 + 정답·근거부터 만들기 |
| 테스트 케이스 (Test cases) | 시험 문제 하나하나. 입력 + 기대 결과 | 사소한 실수도 문제로 만들어 두면 **다시 틀렸을 때 바로 잡아냄** |
| 확인 조건 (Assertions) | 결과를 자동으로 검사하는 규칙. "○○가 있어야/없어야 한다", "숫자가 이 범위 안", "칸끼리 맞아야 한다" 등 | 유튜브 반복 가드 = "지난 주제와 겹치면 안 된다"는 확인 조건 |
| 정확히 일치 (Exact match) | 정해 둔 비교 규칙에서 답이 정답과 **똑같은지** 보는 가장 엄격한 채점 | 코드·정해진 답에 좋음. 숫자·날짜는 표기 차이(2026-11-23 vs 11/23)를 허용할지 먼저 정하기. 문장 답엔 너무 엄격 → 허용 답안 여러 개나 다른 채점 기준 사용 |

더 볼 것: AI가 채점하기(LLM-as-judge), 회귀 테스트(고친 뒤 예전 것이 안 깨졌나)

### 4단계: AI 보안

| 개념 | 뜻 | 활용 |
|---|---|---|
| 프롬프트 주입 (Prompt injection) | 원래 지시와 다른 **지시문을 몰래 넣어 AI를 조종**하는 공격. 들어오는 길에 따라 두 가지: **직접**(사용자가 입력창에 "앞의 지시는 무시해") / **간접**(아래) | 회사 챗봇을 공개하면 반드시 들어옴. 규칙을 지시문에만 두지 말고 프로그램 쪽 권한으로도 막기 |
| 간접 주입 (Indirect injection) | 프롬프트 주입 중에서, 지시문이 **AI가 읽는 웹페이지·문서·메일·도구 결과 속에** 숨어 들어오는 것 | AI데일리가 웹을 읽음 → 페이지 속 "이 주소로 보내라" 같은 문장이 위험. 읽은 글은 명령이 아니라 자료로 취급 |
| 탈옥 (Jailbreaks) | 역할극·우회 질문으로 AI의 **안전 규칙을 우회**하게 만드는 것. 프롬프트 주입과 겹칠 때가 많음 | 고객용 AI를 만들면 "엉뚱한 말 하게 만들기" 시도를 대비 |
| 데이터 유출 (Data leakage) | 비밀번호·개인정보·내부 자료가 **볼 권한 없는 사람에게** 노출되는 것. 답변뿐 아니라 기록·캐시·검색 결과·외부 전송으로도 샘 | 메모리 동기화 때 비밀값 검사·중단 장치를 둔 게 바로 이 대비. 공개 저장소(show) 주의 |

더 볼 것: 최소 권한(필요한 도구만 주기), 출력 검사, 개인정보 가리기

### 5단계: AI 시스템 설계

| 개념 | 뜻 | 활용 |
|---|---|---|
| 모델 고르기 (Model selection) | 일에 맞는 모델 고르기. 똑똑함 ↔ 속도 ↔ 가격 저울질 | yt-auto에서 "대본은 Opus 5.5"로 정해 둔 것이 모델 고르기 |
| 모델 나눠 보내기 (Model routing) | 실행 중에 **요청마다** 어느 모델로 보낼지 자동으로 정하는 장치 | 예: 사내 챗봇에서 쉬운 질문은 싼 모델, 어려운 질문은 큰 모델로 자동 분기 |
| 대체 경로 (Fallbacks) | 첫 방법이 실패하면 **다른 모델이나 다른 처리 방식으로** 넘어가기 | 무인 자동화엔 필수. 비슷하지만 다른 것: **재시도(retry)** = 같은 방법으로 한 번 더. yt-auto의 "구독 한도면 1회 자동 재실행"은 재시도 |
| 뜻 기반 캐시 (Semantic caching) | 전에 받은 질문과 **뜻이 같으면** AI를 또 부르지 않고 저장해 둔 답 재사용 | 회사 **공통 규정** 질문에 비용·속도 절약. 단, 사람마다 답이 다른 질문(내 남은 연차 등)이나 권한이 다른 자료는 재사용하면 안 됨 → 남의 정보가 보일 수 있음 |

더 볼 것: 비용 계산, 응답 속도(latency), 기록 남기기(로깅)

### 6단계: RAG — AI에게 내 문서를 주기

RAG = **자료를 검색해서 찾은 내용을 AI 답변의 근거로 붙여 주는** 방식. AI가 모르는 회사 자료로 답하게 만듭니다. 검색 결과와 최종 답이 근거에 맞는지는 따로 확인해야 합니다.

| 개념 | 뜻 | 활용 |
|---|---|---|
| 문서 읽어내기 (Document parsing) | PDF·한글(hwp)·엑셀에서 글자를 뽑되 **제목·표·읽는 순서 같은 구조도 살리기** | 첫 단계가 망가지면 전부 망가짐. kordoc(설치해 둔 한글 문서 도구)이 이 역할 |
| 조각내기 (Chunking) | 긴 문서를 검색하기 좋게 **나누기**. 길이로 자르거나, 문단·제목 같은 **뜻 단위**로 나눔 | 너무 크면 엉뚱한 내용이 섞이고, 너무 작으면 앞뒤 맥락이 사라짐 |
| 조각 겹치기 (Chunk overlap) | 자를 때 앞 조각 끝부분을 다음 조각 앞에 **조금 겹치기** | 경계에서 뜻이 끊기는 것을 **줄임**. 대신 중복이 생기고 처리량이 늘어남 |
| 임베딩 모델 (Embedding models) | 조각을 벡터(뜻을 담은 숫자 목록)로 바꿔 주는 모델 | 질문과 뜻이 가까운 조각을 찾는 데 씀. 한국어 문서면 한국어에 강한 모델 선택 |

더 볼 것: 벡터 DB, 재순위(reranking), 출처 표시

### 7단계: 백엔드 — AI를 둘러싼 코드

| 개념 | 뜻 | 활용 |
|---|---|---|
| 파이썬 (Python) | AI와 자동화에 **널리 쓰이는** 프로그래밍 언어 | 내 자동화(yt-auto, ai-daily)가 전부 파이썬 |
| FastAPI | 파이썬으로 **웹 API**(웹 주소로 부를 수 있는 기능)를 만드는 도구 | 냠냠플래닛에서 써봄. "내 AI 기능을 다른 프로그램이 부르게" 할 때 |
| REST API | 영상·회원 같은 **자원을 주소로 가리키고**, 정해진 방식으로 다루는 웹 API 스타일. **GET** = 그 자원을 조회 / **POST** = 그 주소에 처리를 요청 (새 항목 만들기, 검색 조건 보내기 등) | 유튜브 API로 영상 상태를 조회하는 것이 GET 사용 |
| async/await | 응답을 **기다리는 동안 다른 일을 먼저** 처리하게 하는 코드 방식 | 여러 요청의 기다림을 **겹쳐서** 전체 시간을 줄임. AI 답 하나나 무거운 계산이 저절로 빨라지는 건 아님 |

더 볼 것: 데이터베이스(hub.sqlite는 SQLite 데이터베이스 파일, SQL은 그 안을 조회·변경하는 언어), 환경변수·비밀값 관리, 오류 처리

### 8단계: 배포 — 실제로 내놓기

| 개념 | 뜻 | 활용 |
|---|---|---|
| API vs 직접 운영 (API vs self-hosted) | 차이는 **누가 모델을 운영하느냐**. 외부 업체(Anthropic 등)에 맡기거나, 내 서버에서 직접 돌리거나. 두 경우 모두 API로 부를 수 있음 | 대부분 외부 업체가 정답. 직접 운영은 데이터가 밖으로 나가면 안 될 때 |
| 추론 서버 (Inference servers) | 요청을 받아 **모델 실행을 관리**하고 결과를 돌려주는 프로그램 | 직접 운영할 때 주로 필요 (라이브러리로 바로 돌릴 땐 없어도 됨) |
| vLLM | 대표적인 추론 엔진·서버 도구. **많은 요청을 한꺼번에** 효율적으로 처리하는 데 강함 | 이름만 알아두기 |
| GPU와 VRAM | GPU = AI 계산을 하는 장치(그래픽카드), VRAM = GPU 전용 메모리. 필요한 VRAM은 **모델 크기 + 입력 길이 + 동시 요청 수**에 따라 커짐 | 내 PC에서 WhisperX 같은 걸 돌릴 때 이 한계에 걸림. CPU로 돌리거나 GPU 여러 개를 쓰는 방법도 있음 |

더 볼 것: 도커(Docker — 냠냠플래닛에서 써봄), 모니터링, 비용 관리

## 4. 답

1. **토큰** 수 (입력 토큰 + 출력 토큰). 같은 뜻이라도 언어·모델에 따라 토큰 수가 다릅니다.
2. 글의 특징을 숫자 목록(벡터)으로 바꾼 것. 같은 모델로 만든 벡터를 비교해 뜻이 비슷한 글을 찾습니다.
3. 자연스러운 문장을 이어 만드는 과정만으로는 **사실이나 근거가 확인되지 않기** 때문.
4. **하네스(실행 환경)**. 모델은 요청만 하고, 실행 환경이 값과 권한을 확인해 실행합니다.
5. 들어오는 **길**이 다릅니다. 직접 주입은 사용자 입력으로, 간접 주입은 AI가 읽는 웹페이지·문서·도구 결과 속에 숨어서 들어옵니다. 둘 다 프롬프트 주입입니다.
6. 조각 경계에서 문장·맥락이 끊기는 것을 줄이려고. 대가는 중복이 생기고 처리량이 늘어나는 것.
7. 재시도는 **같은 방법으로 한 번 더**, 대체 경로는 실패하면 **다른 모델이나 다른 방식으로** 넘어가는 것.
8. 문장으로 된 답처럼 **여러 표현이 정답**일 수 있는 문제. 허용 답안 여러 개나 별도 채점 기준을 씁니다.
9. **재시도**입니다. 한도가 그대로면 같은 오류가 날 수 있습니다. 대체 경로로 바꾸려면 "한도면 다른 모델(예: API 모델)로 넘기기"처럼 **다른 방법**을 준비해야 합니다.
10. 예시 순서: ① 누가 쓰고 어떤 문서를 볼 수 있는지(권한) 정하기 → ② 정답·근거가 있는 시험 질문 만들기(**평가**) → ③ 작은 **RAG** 만들기 → ④ 검색·답변을 시험하고 공개 범위·주입 공격 확인(**평가·보안**) → ⑤ 필요하면 서비스로 올리기(**백엔드·배포**). 이 조건을 지키는 다른 순서도 정답.
11. **간접 (프롬프트) 주입**. ① 읽은 글은 자료로만 다루게 하고, ② 문서를 읽는 작업에는 **보내기 권한 자체를 주지 않고**(최소 권한), ③ 외부로 보내야 할 일이 있으면 프로그램이 받는 사람·권한을 검사한 뒤 사람이 따로 승인합니다. 지시문만으로는 못 막습니다.
12. **뜻 기반 캐시**. 둘 다 "회사 공통 규정"을 묻고 답이 같으므로 처음 답을 저장해 재사용할 수 있습니다. 주의: "**내** 남은 연차"처럼 사람마다 답이 다른 질문은 재사용하면 남의 정보가 보일 수 있으니 캐시하지 않습니다.
13. **정해진 형식 출력**(이름/전화/주소 칸을 스키마로 고정) + **확인 조건**(원문과 일치하는지, 번호 종류에 맞는 형식인지 — 예: 010 휴대전화는 3·4·4자리) → 검사를 통과한 값만 시트에 저장.
14. 예: 재시도(한도 시 재실행), 모델 고르기(대본은 Opus), 확인 조건(반복 가드). 데이터 유출 대비(메모리 비밀값 검사)도 정답.
15. 영상은 분야를 소개하는 순서이고, 나는 **이미 돌리고 있는 자동화와 인턴 업무에 바로 쓰는 것부터** 배우는 게 효율적이라서.
