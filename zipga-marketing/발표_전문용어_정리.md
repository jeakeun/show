## 3. 시스템을 단계로 설명하기

발표에서 도식 하나 띄우고 이 순서로 말하면 됩니다.

```
소재 생성  →  후처리  →  채널별 가공  →  발행  →  성과 수집
```

| 단계 | 전문용어 | 실제로 한 일 |
|---|---|---|
| 1 | **소재 생성 (asset generation)** | 로컬 생성형 AI로 영상 컷·배경음악 생성 |
| 2 | **미디어 후처리 (post-processing)** | 자막·워터마크·BGM 합성, 색보정, 인코딩 |
| 3 | **채널별 규격화 (channel adaptation)** | 9:16 / 16:9 산출, 용량 제약 대응, 채널별 문구 분리 작성 |
| 4 | **연동 발행 (API publishing)** | 각 플랫폼 API·예약 발행으로 배포 |
| 5 | **성과 수집 (analytics collection)** | 조회수·반응 지표 수집 후 리포트 생성 |

**중간에 강조할 포인트 한 줄**
> "각 단계가 파일 단위로 분리돼 있어서, 한 단계가 실패해도 나머지가 멈추지 않습니다."

## 4. 기술 스택 — 물어보면 이렇게 답하세요

| 영역 | 쓴 기술 | 한 줄 설명 |
|---|---|---|
| 언어 | **Python** | 파이프라인 전체 (약 3,700줄) |
| 영상 생성 | **ComfyUI + 확산 모델(diffusion model)** | 노드 기반 워크플로를 API로 호출 |
| 음악 생성 | **ACE-Step** | 가사 없는 연주곡 생성 |
| 영상 처리 | **FFmpeg** | 합성·인코딩·트랜스코딩 |
| 이미지 처리 | **Pillow (PIL)** | 자막·썸네일·배너 생성 |
| 발행 | **YouTube Data API / Threads API / Instagram Graph API** | 채널별 공식 API |
| 인증 | **OAuth 2.0, 액세스 토큰** | 장기 토큰 발급 후 재사용 |
| 예약 | **플랫폼 네이티브 예약 + Windows 작업 스케줄러** | API에 예약 기능이 없는 채널을 스케줄러로 보완 |

**모델 이름을 물어보면** — 영상은 MiniMax H3, 음악은 ACE-Step 3.5B를 로컬에서 돌렸습니다.

## 6. 예상 질문과 답변

**Q. AI API 비용이 얼마나 들었나요?**
> "영상·음악 생성은 전부 로컬 추론이라 호출 비용이 0원입니다. GPU가 있는 PC에서 직접 모델을 돌렸습니다."

**Q. 왜 채널마다 자동화 수준이 다른가요?**
> "플랫폼별 API 정책이 다릅니다. 쓰레드는 텍스트 발행이 바로 열려 있고, 인스타그램은 프로페셔널 계정과 비즈니스 포트폴리오 연결이 선행돼야 합니다. 티스토리는 Open API가 종료돼서 자동화가 불가능한 걸 확인했습니다."

**Q. 예약 발행은 어떻게 처리했나요?**
> "유튜브는 플랫폼 자체 예약 기능을 씁니다. 쓰레드와 인스타그램 API에는 예약 기능이 없어서, 로컬 작업 스케줄러로 발행 시각에 스크립트를 실행하는 방식으로 보완했습니다. 대신 그 시각에 PC가 켜져 있어야 하는 제약이 있습니다."

**Q. 같은 영상을 여러 계정에 올리면 안 되나요?**
> "영상 지문으로 중복이 감지돼서 계정이 묶일 수 있습니다. 계정마다 다른 소재를 생성하도록 설계했습니다."

**Q. 실패하면 어떻게 되나요?**
> "자동 재시도를 하지 않습니다. 재시도가 중복 발행을 만드는 게 더 위험하다고 판단했고, 실패는 로그에 남기고 사람이 확인합니다."

**Q. 가장 어려웠던 점은?**
> "AI가 한글을 제대로 렌더링하지 못한다는 점이었습니다. 그래서 AI는 배경과 분위기만 생성하고, 텍스트가 들어가는 화면은 전부 실촬영과 후처리로 얹는 구조로 바꿨습니다."
