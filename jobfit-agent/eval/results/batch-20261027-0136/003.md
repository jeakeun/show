## 회사 읽기 (AI 추정)
회사 유형: 사용자 플랫폼 (확신도 보통, AI 추정)
돈 버는 방식: 기업 고객(B2B SaaS)에게 올인원 AI 메신저·고객 상담 플랫폼을 구독형으로 제공하며, 고객사 사이트·앱에 SDK를 설치해 실시간 대화·데이터·AI 에이전트를 연결한다. 고객사가 늘고 오래 쓰며 사용량이 늘어야 매출이 커지는 구조라 대규모 트래픽 안정성과 고객사 활성화·리텐션이 핵심이다.
중요 지표: 매출·사용자 활성화·리텐션, 높은 트래픽·급격한 사용량 변화에서의 안정성(장애 격리, 가용성), 대용량 데이터 조회·실시간 상호작용 성능, SDK가 호스트 앱·웹의 성능·안정성에 주는 영향 최소화, 가설 검증 기반 제품 지표 개선, Feature 팀 개발 생산성·출시 속도
안 통하는 지표: 단순 모델 정확도·벤치마크 점수 같은 기술 자체 성과, 고객·비즈니스 지표와 연결되지 않은 구현 결과물 개수, 운영 책임 없는 단발성 신규 개발 실적
근거 문구: "고객사의 지속 가능한 성장을 돕는 올인원 AI 메신저를 만들며" / "고객이 체감하는 변화와 매출·사용자 활성화·리텐션 같은 비즈니스 결과를 책임지는" / "출시 후에는 고객 피드백과 제품 데이터로 가설을 검증하며 제품과 비즈니스 지표를 함께 개선합니다" / "높은 트래픽과 급격한 사용량 변화에도 안정적으로 동작할 수 있도록 확장성·장애 격리·관측 가능성을 갖춘 시스템을 설계하고" / "호스트 앱의 성능과 안정성에 영향을 주지 않으면서 실시간 기능을 제공하는 문제를 다룹니다" / "채팅·유저·채널·사용량·정산 등 공통 기능을 개발하고"

## 자기소개서

여러 자동화를 운영하면서 "실패는 조용히 나지 않게, 성공은 결과물로 판정한다"는 원칙을 전체 프로젝트에 적용했습니다 [E7][E21]. 자동화 실패와 품질 저하 발행은 바탕화면 경고 파일과 폰 푸시로 알리고, 알림이 실패하더라도 본 작업은 멈추지 않게 했습니다 [E7]. 폰 푸시로는 업로드 실패, 가드 발동, 수집 실패 같은 사건을 받습니다 [E6]. AI 출력 형식은 흔들리기 때문에, 성공 여부는 AI의 "완료" 보고가 아니라 관측 가능한 결과물로 판정했습니다 [E7]. 같은 장애가 두 번 났기 때문에 시작 전에 로그인 상태를 미리 점검하는 기능을 우선순위가 높은 과제로 두고 있으며, 이 기능은 아직 제안 단계입니다 [E7].

프로젝트가 늘어나자 리포트가 실제 데이터와 맞는지 아무도 대조하지 않는 문제가 생겼습니다 [E12]. 2026-08-27 첫 전수 감사에서는 읽기 전용 감사 에이전트 3기를 병렬로 돌려 리포트의 주장을 원본 데이터와 대조했습니다 [E12]. 감사를 읽기 전용으로 둔 이유는 감사가 틀리더라도 시스템을 망가뜨리지 않게 하기 위해서였습니다 [E12]. 이 감사에서 코인봇의 수수료 계산 오류(20.5%)와 AI데일리에 없는 회차가 기록된 유령 데이터를 찾았습니다 [E12]. 감사 과정에서 분석 AI가 쓰기 권한으로 임시 스크립트를 만든 전례도 찾았습니다 [E24]. 그래서 회고 실행 전에 설정·소스 파일 해시를 백업해 두고 바뀌면 자동으로 원복하며, 루트에 새로 생긴 파일은 격리하는 가드를 회고 실행 스크립트에 넣었습니다 [E24]. 9/6에 회고 AI가 다시 임시 스크립트를 만들었을 때, 가드가 그 파일을 격리하는 것을 확인했습니다 [E24]. 지금은 매주 일요일 10:00 자동 감사로 같은 대조를 반복합니다 [E12][E32]. 1회차 주간 감사 시험에서는 8건을 발견했고, 검증 후 6건을 실제로 고쳤습니다 [E12].

비용과 신뢰성 사이의 판단도 기록으로 남기며 일했습니다 [E4]. 유튜브 파이프라인을 단계마다 부서별 에이전트로 나누자는 안이 나왔을 때, 판단 없는 공정에 AI를 두면 비용과 실패 지점만 늘어난다고 보고 이 안을 기각했습니다 [E4]. 대본 작성·검수·팩트체크처럼 판단이나 글쓰기가 필요한 칸에만 LLM을 두고, 렌더링·업로드·자막 맞추기는 코드가 맡게 했습니다 [E4]. 그 대가로 데모의 화려함은 포기했습니다 [E4]. AI데일리에서도 "연속 0건" 같은 카운터는 AI가 손으로 세지 않고 코드가 데이터에서 계산하게 했습니다 [E5]. 생성이 끝나면 검수 에이전트가 형식·링크·한글 깨짐을 다시 검사합니다 [E5]. 학습 예제에서는 조회 도구는 승인 없이 바로 실행하고, 되돌리기 어려운 쓰기 도구는 사람 승인 뒤에 실행되도록 만들었습니다 [E31][E34]. 이 실행 순서는 시험용 가짜 모델로 확인했습니다 [E31].

## 이력서 강조

- 자동화 실패와 품질 저하 발행을 경고 파일·폰 푸시로 알리고, 알림 실패가 본 작업을 멈추지 않게 했으며, 성공은 관측 가능한 결과물로 판정했습니다 [E7].
- 읽기 전용 감사 에이전트 3기를 병렬로 돌려 리포트와 원본 데이터를 대조했고, 수수료 계산 오류(20.5%)와 유령 데이터를 찾았습니다 [E12].
- 주간 자동 감사 1회차 시험에서 8건을 발견했고, 검증 후 6건을 실제로 수정했습니다 [E12].
- 분석 AI 실행 전 파일 해시를 백업해 변경 시 자동 원복하고 새 파일을 격리하는 가드를 넣었으며, 재발 시 격리가 작동하는 것을 확인했습니다 [E24].
- 판단 없는 공정의 에이전트화를 비용과 실패 지점 증가를 이유로 기각하고, LLM은 판단·글쓰기 칸에만 두었습니다 [E4].
- 6인 팀 프로젝트 집가의 마케팅 파트를 혼자 자동화했으며, 영상 정규화부터 발행 큐까지 이어지는 M1~M6 파이프라인을 운영했습니다 [E27].

## 보강할 증거

- 운영 중인 자동화 개수와 운영 기간, 알림으로 잡아낸 장애 건수, 알림부터 복구까지 걸린 시간 (안정성·장애 대응 지표로 말하기 위함)
- 부서별 에이전트 분리안을 기각한 결정 전후의 API 비용 비교 숫자 (공유 저장소에 API 비용이 매일 모이니 여기서 뽑을 수 있음)
- 집가 티저·시연 쇼츠와 쓰레드 예약 게시의 조회수·클릭 같은 사용자 반응 숫자 (사용자 활성화 지표와 연결하기 위함)
- 주간 감사 회차별 발견·수정 건수 누적, 가드 발동 횟수, 첫 전수 감사에서 3기를 나눈 기준 (기준은 "확인 필요" 상태라 면접 전에 정리 필요)
