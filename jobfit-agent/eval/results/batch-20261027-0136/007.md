근거 문구: "인공지능 기술을 통해 의료의 한계를 뛰어넘을 수 있다면" / "AI가 실제 의료 현장에서 안정적이고 효율적으로 동작하도록 만드는" / "Latency / Throughput / GPU Memory를 고려한 추론 성능 최적화" / "GPU 자원의 효율적인 활용을 위한 Scheduling 및 Runtime 최적화" / "어떻게 하면 AI를 더 빠르고, 안정적이고, 확장 가능하게 제품화할 수 있을까?"

## 자기소개서

유튜브 자동화 파이프라인을 운영하면서, 단계마다 "부서별 에이전트"를 두자는 안을 기각했습니다 [E4]. 렌더링이나 업로드처럼 판단이 없는 공정에 판단하는 AI를 두면 비용과 실패 지점만 늘어난다고 판단했기 때문입니다 [E4]. 그래서 언어 모델은 대본 작성, 검수, 팩트체크처럼 판단이나 글쓰기가 필요한 칸에만 두고, 슬롯·계열 결정, 렌더링, 업로드, 자막 맞추기는 코드가 맡게 했습니다 [E4]. 음성(TTS)·이미지·음성인식 모델은 판단 없이 정해진 변환만 하는 부품이라, 에이전트가 아니라 코드에서 부르는 도구로 두었습니다 [E4]. 그 결과 8월 4일부터 하루 2편씩 돌던 코드 파이프라인을 쪼개지 않고 유지했습니다 [E5]. 제 운영 경험은 제가 설계하고 운영한 것이며, 구현은 클로드 코딩 에이전트가 맡았습니다 [E16].

운영할 때는 실패가 조용히 묻히지 않게 하는 데 집중했습니다 [E14]. 자동화 실패와 품질 저하 발행은 바탕화면 경고 파일과 폰 푸시로 알리고, 알림이 실패해도 본 작업은 멈추지 않게 했습니다 [E14]. AI 출력 형식은 흔들리기 때문에, 성공 여부는 AI의 응답이 아니라 관측 가능한 결과물로 판정했습니다 [E14]. 메인 PC에는 공용 도구 두 가지를 두고 있습니다 [E15]. 하나는 API 비용 등을 매일 23:50에 SQLite 공유 저장소 한곳에 모으는 도구로, 원본은 읽기만 합니다 [E15]. 다른 하나는 업로드 실패, 가드 발동, 수집 실패를 폰으로 알리는 알림 도구입니다 [E15]. 같은 장애가 두 번 났기 때문에, 시작 전에 로그인 상태를 미리 점검하는 기능을 우선순위가 높은 과제로 두고 있습니다 [E14]. 이 기능은 아직 제안 단계입니다 [E14].

에이전트 실행 과정의 상태 관리와 흐름 제어는 LangGraph 예제를 직접 실행하며 학습했습니다 [E1][E6]. 병렬 예제에서는 감사관 3개를 동시에 돌리고, 결과를 보고서 작성 노드 하나로 합쳤습니다 [E1]. 검수 루프 예제에서는 재시도 상한을 2회로 두고, 1차에 실패한 뒤 2차에 통과하는 것을 확인했습니다 [E6]. 레거시 연계 예제에서는 자유 SQL 대신 정해진 쿼리에 파라미터만 넣는 읽기 도구를 만들었습니다 [E3]. 같은 예제에서 읽기 도구는 바로 실행하고, 쓰기 도구는 사람이 승인하기 전까지 멈추게 했습니다 [E8]. 시험용 가짜 모델로 돌려 승인 전에는 DB 값이 바뀌지 않는 것도 확인했습니다 [E8]. 이 과정에서 재개할 때 노드가 처음부터 다시 실행되므로, `interrupt()` 앞에는 두 번 실행되면 안 되는 일을 두지 않아야 한다는 점을 배웠습니다 [E13]. 제 운영 시스템에는 중간에 죽었을 때 이어서 하는 기능과 병렬 처리가 코드로 없었습니다 [E19]. 이 부분은 LangGraph로 채워야 할 영역이라고 정리했습니다 [E19]. 지금은 공고 분석부터 병렬 근거 검색, 근거 검증, 사람 확정까지 잇는 jobfit-agent를 LangGraph·RAG로 개발하고 있습니다 [E15]. 첫 골격을 만들고 가짜 모델 테스트를 통과한 단계입니다 [E15].

## 이력서 강조

- 유튜브 파이프라인에서 판단 없는 단계까지 에이전트로 나누는 안을, 비용과 실패 지점이 늘어난다는 이유로 기각했습니다 [E4].
- LLM은 판단·글쓰기 칸에만 두고, 음성·이미지·음성인식 모델은 코드에서 부르는 도구로 두었습니다 [E4]. 8월 4일부터 하루 2편 돌던 파이프라인을 쪼개지 않고 유지했습니다 [E5].
- 자동화 실패와 품질 저하를 경고 파일과 폰 푸시로 알리게 했습니다 [E14]. 성공 여부는 관측 가능한 결과물로 판정했습니다 [E14].
- API 비용 등을 매일 23:50에 SQLite 공유 저장소로 모으는 수집 도구를 운영하고 있으며, 원본은 읽기만 합니다 [E15].
- (학습) LangGraph로 병렬 실행 후 단일 작성 노드로 합치기, 재시도 상한이 있는 검수 루프, 쓰기 도구에 사람 승인 걸기 예제를 실행해 확인했습니다 [E1][E6][E8].
- 6인 팀 프로젝트의 마케팅 파트를 혼자 자동화했습니다 [E7]. 이 과정에서 ComfyUI Desktop을 자동 연결해 로컬 GPU로 영상과 BGM을 생성하게 했습니다 [E7].

## 보강할 증거

- 에이전트 분할을 기각한 구조의 비용 효과: API 비용 기록에서 월 비용, LLM 호출 수, 1편당 비용을 뽑아 두면 "비용 절감"을 숫자로 말할 수 있습니다.
- 안정성 지표: 파이프라인 가동 기간의 실패 건수, 업로드 성공률, 알림 후 복구까지 걸린 시간을 모아 두면 서빙 안정성·Observability 질문에 답할 수 있습니다.
- 로컬 GPU 생성 작업의 성능 수치: 1건당 생성 시간과 VRAM 사용량, 이를 줄이려고 바꾼 설정이 있으면 Latency·GPU Memory 항목에 닿습니다.
- 필수 요건 공백: vLLM이나 PyTorch로 모델 하나를 직접 서빙하고, Latency·Throughput·GPU Memory를 측정한 기록이 필요합니다. 현재 근거에는 이 부분이 없습니다.
