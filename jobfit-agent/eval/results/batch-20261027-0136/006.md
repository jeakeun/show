## 회사 읽기 (AI 추정)
회사 유형: 사용자 플랫폼 (확신도 높음, AI 추정)
돈 버는 방식: 라이브 스트리밍 플랫폼(SOOP)으로 다수 유저를 모아 수익을 내며, 보유한 비디오·오디오·텍스트 데이터에 AI를 접목한 상용 AI 서비스로 새로운 콘텐츠 시장을 만들려 함. 이 자리는 그 AI 서비스를 대규모 유저에게 안정적으로 서빙하는 백엔드 역할.
중요 지표: 대용량 트래픽 처리량·동시 사용자 수 대응, AI 서빙 안정성(가용성·장애율), 서빙 지연시간·처리 효율 최적화, AI 서비스 사용자 수·이용률
안 통하는 지표: 모델 정확도·논문 수준 성능 개선, 신사업 단독 런칭 개수·속도, 판매량·매출 직접 성과
근거 문구: "최고의 Live Streaming 플랫폼에서 수많은 유저를 대상으로 뉴미디어 상용 AI 서비스를 경험할 수 있습니다." / "안정적인 AI 서비스 서빙 아키텍처 설계 및 개발" / "AI 서비스 백엔드 서버 개발 및 서빙 최적화" / "대용량 트래픽을 처리하는 서버 애플리케이션 개발 경험이 있으신 분"

## 자기소개서

AI 서비스를 운영할 때 제가 먼저 지키는 원칙은 "실패는 조용히 나지 않게, 성공은 결과물로 판정한다"입니다 [E3]. 이 원칙이 필요했던 사고가 있습니다 [E21]. 비용을 줄이려다 사고 토큰 때문에 회고 생성이 본문 0자로 실패했고, US$0.76이 낭비됐는데 실패 알림도 없었습니다 [E21]. 그래서 한도를 24,000으로 올리고 사고 강도를 중간으로 낮췄습니다 [E21]. 한도 초과로 멈추면 명시적 오류로 처리하고, 실패하면 폰으로 알림이 오도록 고쳤습니다 [E21]. 지금은 업로드 실패, 가드 발동, 수집 실패를 폰 푸시 알림으로 받습니다 [E6]. 자동 실행은 메인 PC에서만 돌려, 두 PC에서 같이 돌 때 생기는 이중 업로드와 이중 매매를 막습니다 [E9].

AI 호출은 역할마다 모델을 다르게 쓰고, 모든 호출의 비용을 기록합니다 [E21]. 9/7~13 기준선에서는 대본 생성 17회로 14편을 만들었고, 재생성은 3건(21%)이었습니다 [E21]. 같은 기간 대본 생성 비용은 주 US$3.72, 호출당 약 US$0.16이었습니다 [E21]. 하이쿠 검수를 도입하기 전 검증 호출 1건의 비용은 US$0.0015였습니다 [E21]. 작성 AI와 별개로 기준표를 가진 검수 AI도 붙였습니다 [E4]. 검수 AI도 오탐을 냈습니다 [E4]. 일주일 동안의 재생성 3건이 전부 오탐이었던 것을 찾아내 슬롯별 기준으로 고쳤습니다 [E4]. 매일 23:50에는 유튜브 통계, API 비용, 코인 매매, 채용 카운트를 SQLite 공유 저장소 한 곳에 모읍니다 [E6].

이 시스템들은 제가 설계하고 운영했으며, 구현은 클로드 코딩 에이전트와 함께 했습니다 [E17]. LangGraph 같은 프레임워크는 아직 실전 경험이 없습니다 [E22]. 검수 루프, 승인, 병렬 처리 구조를 흉내 낸 학습 예제를 돌려본 수준입니다 [E22]. 학습 예제에서는 조회 도구는 바로 실행하고, 쓰기 도구는 사람 승인 뒤에 실행하며, 도구 호출을 5회로 제한해 폭주를 막는 구조를 확인했습니다 [E19]. 제 운영 시스템은 중간에 죽으면 실패 알림을 받고 수동으로 재실행합니다 [E27]. 마지막 체크포인트부터 이어서 하기와 병렬 처리는 제 시스템에 코드로 없던 부분이라, 앞으로 채워야 할 영역으로 보고 있습니다 [E27].

- 규모 숫자: 하루 AI 호출 수, 하루 처리 작업 수, 동시에 도는 파이프라인 수. 플랫폼 회사는 처리량과 규모로 말하는데, 지금 근거에는 이 숫자가 없습니다.
- 안정성 수치: 알림 도입 전후의 실패 건수, 실패를 알아차리기까지 걸린 시간, 월간 수동 재실행 횟수, 파이프라인 정상 완료율.
- 지연시간: 대본 생성과 검수 호출의 응답 시간, 파이프라인 전체 소요 시간. "서빙 최적화"를 말하려면 시간 지표가 필요합니다.
