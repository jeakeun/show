## 회사 읽기 (AI 추정)
회사 유형: 기술 판매 (확신도 보통, AI 추정)
돈 버는 방식: 기업 고객사에 올인원 AI 메신저(고객 상담·CRM·마케팅·AI 에이전트·음성 통화) SaaS를 제공하고 사용량·구독으로 매출을 내는 B2B 플랫폼. 고객사 웹/앱에 SDK가 설치되어 대규모 실시간 트래픽을 처리함
중요 지표: 고객사 매출·사용자 활성화·리텐션 개선, 높은 트래픽·급격한 사용량 변화에서의 안정성(장애 격리, 가용성), 대용량 데이터 조회·실시간 처리 성능, SDK 경량화 및 호스트 앱 성능 영향 최소화, 개발 생산성·출시 속도 향상(공통 라이브러리, 아키텍처 개선), 가설 검증 기반 제품 지표 개선
안 통하는 지표: 일반 소비자 대상 다운로드·조회수 같은 B2C 노출 지표, 비즈니스 결과와 연결되지 않은 단순 기능 구현 개수, 운영·장애 대응 없는 일회성 프로토타입 성과

## 자기소개서

운영 중인 자동화의 설계 결정을 실제로 내려 왔습니다 [E5]. 여기서 '저'는 운영자인 저와, 제 지시로 일한 클로드 세션을 합친 말입니다 [E5]. 유튜브 자동화에서는 대본을 쓰는 AI와 별개로, 기준표를 가진 검수 AI를 붙였습니다 [E24]. 작성 과정을 함께 겪은 AI는 자기 글에 관대해지기 쉬워서 검사 기준을 작성과 분리했습니다 [E12]. 도입 검증에서 정상 대본 3편은 지적 없이 통과했고, 의료 조언을 넣은 가짜 대본은 정확히 차단했습니다 [E12]. 검수 AI도 틀렸습니다 [E12]. 9/7~13에 재생성이 3건 있었는데 모두 검수 오탐이었고, 고전실험형 전용인 '훅' 기준을 저녁 리스트형 대본에도 적용한 탓이었습니다 [E12]. 9/14에 슬롯 정보를 검수 AI에 넘겨 기준을 나누는 방식으로 고쳤습니다 [E12]. 고정 문자열을 AI에게 쓰게 하고 AI로 검사하다가 사흘간 영상이 빠지는 루프도 겪었습니다 [E35]. 이후 매번 같은 답이 나와야 하는 부분은 코드가 붙이도록 바꿨습니다 [E35].

실패가 조용히 묻히지 않는 구조를 만들었습니다 [E10]. 자동화 실패와 품질 저하 발행은 바탕화면 경고 파일과 폰 푸시로 알리고, 알림이 실패해도 본 작업은 죽지 않게 했습니다 [E10]. AI 출력 형식은 흔들리기 때문에 성공 여부는 관측 가능한 결과물로 판정합니다 [E10]. 검수 API가 장애이면 통과(fail-open)시키고, 코드 사후검사는 그대로 유지했습니다 [E12]. 회고 팩트체크 AI가 첫 실전에서 출력 한도에 걸려 잘렸을 때도 이 통과 처리가 정상 작동해 회고는 나갔고, 이후 한도를 올렸습니다 [E14]. 감사에서 코인 회고 AI가 쓰기 권한이 열린 상태로 임시 스크립트를 만든 전례를 찾았습니다 [E28]. 그래서 실행 전에 설정·소스 파일의 해시를 백업해 두고, 바뀌면 자동 원복하며, 새로 생긴 파일은 격리하는 가드를 넣었습니다 [E28]. 9/6에 회고 AI가 다시 임시 스크립트를 만들었을 때 가드가 이를 격리하는 것을 확인했습니다 [E28]. 9/7부터는 분석 AI가 제안만 하게 바꾸면서 모든 회고 제안을 사람이 승인하게 했습니다 [E29]. 그런데 9/20에 플레이북이 승인 대기로 하루 묵어 적용 시작을 놓쳤습니다 [E29]. 9/21부터는 기준을 '되돌릴 수 있는가'로 바꿨습니다 [E29]. 되돌릴 수 있는 개선은 이전본을 보관한 채 자동 적용한 뒤 보고하고, 돈이 드는 결정이나 영상 삭제·공개 전환은 계속 사람이 정합니다 [E4][E29].

파이프라인을 단계마다 부서별 에이전트로 나누자는 안이 있었지만, 판단 없는 공정에 감독관만 늘어 비용과 실패 지점만 많아진다고 보고 기각했습니다 [E6]. LLM은 대본 작성·검수·팩트체크처럼 판단이나 글쓰기가 필요한 칸에만 두고, 렌더링·업로드·자막 맞추기는 코드가 맡게 했습니다 [E6]. 그래서 8/04부터 하루 2편씩 돌던 코드 파이프라인을 쪼개지 않고 유지했습니다 [E44]. 9/7에는 비용 때문에 회고 검증 모델을 소넷에서 하이쿠로 내렸습니다 [E14]. 2026-10-01부터는 코드·설정·프롬프트 수정을 work 브랜치에서 하고, 검증과 테스트를 모두 통과해야 main에 병합합니다 [E18]. 예약 작업이 도는 중에는 병합을 거부하는 도구도 씁니다 [E18]. 8/27 1회차 주간 감사 시험에서는 8건을 발견했고, 검증을 거쳐 6건을 실제로 고쳤습니다 [E16].

## 이력서 강조

- 작성 AI와 별도로 기준표를 가진 검수 AI를 운영했습니다 [E24]. 도입 검증에서 정상 대본 3편은 통과시키고 의료 조언을 넣은 가짜 대본은 차단했습니다 [E12][E24]. 일주일간 재생성 3건이 모두 오탐임을 찾아 슬롯별 기준으로 고쳤습니다 [E12][E24].
- 자동화 실패와 품질 저하를 폰 푸시와 경고 파일로 알리고, 성공은 결과물로 판정하는 관측 구조를 운영했습니다 [E10]. 검수 장애 때는 fail-open으로 통과시키되 코드 사후검사는 유지했습니다 [E12].
- 분석 AI가 운영 설정을 직접 고치지 못하게 하는 가드를 넣었습니다(파일 해시 백업, 자동 원복, 새 파일 격리) [E28]. 9/6에 실제 격리가 작동하는 것을 확인했습니다 [E28].
- 읽기 전용 감사 에이전트 3기를 병렬로 돌려 전수 감사를 했고, 코인봇 수수료 계산 오류(20.5%)를 찾았습니다 [E16]. 주간 감사 시험에서는 8건을 발견해 6건을 고쳤습니다 [E16].
- 비용과 실패 지점이 늘지 않도록 LLM은 판단·글쓰기 칸에만 두고 나머지 공정은 코드로 유지했습니다 [E6][E44]. 비용 때문에 검증 모델을 소넷에서 하이쿠로 내렸습니다 [E14].
- 코드·설정·프롬프트 수정은 브랜치에서 하고, 테스트를 통과해야 main에 병합하는 작업 규칙을 운영합니다 [E18].
