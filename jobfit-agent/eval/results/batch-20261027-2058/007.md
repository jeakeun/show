## 회사 읽기 (AI 추정)
회사 유형: 기술 판매 (확신도 높음, AI 추정)
돈 버는 방식: 의료 AI 기업. 의료 현장에 AI 제품을 공급하며, 해당 팀은 모델을 빠르고 안정적으로 제품화하는 Serving/Runtime/Agent 플랫폼을 구축한다. 기술력(추론 성능·안정성·비용 효율)이 제품 경쟁력이다.
중요 지표: 추론 Latency 단축, Throughput 향상, GPU Memory·GPU 자원 활용 효율(비용 절감), 서비스 안정성·가용성, Research→Production 배포 시간 단축, 여러 제품에서 재사용 가능한 공통 플랫폼 확장성
안 통하는 지표: 사용자 수·재방문 등 트래픽 성장 지표, 판매량·조회수, 신규 사업 런칭 개수
근거 문구: "AI가 실제 의료 현장에서 안정적이고 효율적으로 동작하도록 만드는 엔지니어링을 담당합니다" / "Latency / Throughput / GPU Memory를 고려한 추론 성능 최적화" / "GPU 자원의 효율적인 활용을 위한 Scheduling 및 Runtime 최적화" / "“어떻게 하면 AI를 더 빠르고, 안정적이고, 확장 가능하게 제품화할 수 있을까?”" / "Research 단계의 기술을 실제 Production 환경으로 연결합니다"

## 자기소개서

유튜브 자동화 파이프라인을 운영할 때 실측 운영비는 월 US$51(앤트로픽)에 제미나이 약 ₩6천이었고, 목표를 US$30 이하로 잡았습니다 [E3]. 판단 난이도에 맞춰 모델을 나눴습니다 [E3]. 주간 분석은 상위 모델(Opus), 대본은 중간 모델(Sonnet), 검수·팩트체크는 하이쿠에 배정했고, 대본 지시문은 프롬프트 캐싱으로 재사용했습니다 [E3]. 모든 호출의 비용을 기록하고, 대시보드에서 "매일 운영비"와 "주간 분석비"로 나눠 보여주게 했습니다 [E3]. 회고를 반박 검증하는 모델도 비용 때문에 소넷에서 하이쿠로 내렸습니다 [E18]. 실패한 적도 있습니다 [E3]. 회고 출력 한도를 16,000에서 10,000 토큰으로 낮췄는데, 상위 모델은 사고(thinking) 토큰도 한도에 포함된다는 점을 놓쳤습니다 [E3]. 그 결과 본문 0자 실패로 US$0.76이 낭비됐고 실패 알림도 오지 않았습니다 [E3].

안정성은 결과물로 판정하는 원칙으로 다뤘습니다 [E14]. AI가 '완료'라고 말하는 것과 실제로 완료된 것은 다르기 때문입니다 [E14]. 자동화 실패와 품질 저하 발행은 바탕화면 경고 파일과 폰 푸시로 알리고, 알림이 실패해도 본 작업은 멈추지 않게 했습니다 [E14]. 되돌릴 수 있는 플레이북·프롬프트 개선은 자동 적용하되 이전본을 보관하고, 프롬프트는 문법·스모크 테스트에 실패하면 자동으로 원복하게 했습니다 [E13]. 팩트체크 AI가 첫 실전에서 출력 한도에 걸려 잘렸을 때는 통과(fail-open)가 정상 작동해 회고가 나갔고, 이후 한도를 올렸습니다 [E18]. 작성 AI와 별개로 기준표를 가진 검수 AI도 붙였습니다 [E7]. 일주일간 재생성 3건이 전부 오탐이었던 것을 찾아 슬롯별 기준으로 고쳤습니다 [E7].

복잡한 구조보다 단순한 구조를 골랐습니다 [E1]. 파이프라인을 부서별 에이전트로 나누는 안은 판단 없는 공정에 감독관만 늘리는 셈이라 기각했습니다 [E1]. 대신 대본 작성·검수·팩트체크처럼 판단이나 글쓰기가 필요한 칸에만 LLM을 뒀습니다 [E1]. 음성(TTS)·이미지·음성인식 모델은 정해진 변환만 하는 부품이므로, 에이전트가 아니라 코드에서 부르는 도구로 두었습니다 [E1]. 그래서 8/04부터 하루 2편씩 돌던 코드 파이프라인을 쪼개지 않고 유지했습니다 [E28]. 이 경험을 바탕으로 LangGraph를 학습했습니다 [E33]. 학습 예제로 검수 게이트를 그래프로 그려 보니 "작성 → 검수 → 통과/재작성/예비" 갈림길이 한눈에 드러났습니다 [E20]. 직접 만든 재시도 카운터, 승인 대기 파일, 이전본 폴더가 LangGraph의 상태 카운터, interrupt, 체크포인터에 각각 대응한다는 점도 비교해 정리했습니다 [E21]. 이 시스템들은 제가 설계·운영했고, 구현은 AI 코딩 도구와 함께 했습니다 [E33].

## 이력서 강조

- 실측 월 US$51(앤트로픽)이던 운영비를 US$30 이하로 낮추는 목표를 세우고, 판단 난이도별 모델 배정(Opus·Sonnet·Haiku), 프롬프트 캐싱, 호출별 비용 기록을 적용했습니다 [E3].
- 자동화 실패와 품질 저하 발행을 경고 파일과 폰 푸시로 알리고, 알림이 실패해도 본 작업은 멈추지 않는 구조로 운영했습니다 [E14].
- 프롬프트 개선은 이전본을 보관한 채 자동 적용하고, 문법·스모크 테스트에 실패하면 자동 원복하게 했습니다 [E13].
- LLM은 판단·글쓰기 칸에만 두고 TTS·이미지·음성인식 모델은 코드에서 부르는 도구로 둔 파이프라인을 설계했습니다 [E1]. 이 파이프라인을 8/04부터 하루 2편씩 운영했습니다 [E28].
- 검수 AI의 일주일 재생성 3건이 전부 오탐이었던 것을 찾아 슬롯별 기준으로 고쳤습니다 [E7].
- LangChain 1.4.7·LangGraph 1.2.16으로 검수 루프와 도구 호출 에이전트 예제를 시험용 가짜 모델로 실행하며 학습했습니다 [E33][E15].

## 보강할 증거

- 비용 최적화 후 실제 월 운영비(US$30 목표 달성 여부), 프롬프트 캐싱 전후의 호출당 토큰 수와 비용
- 파이프라인 단계별 처리 시간(대본 생성·TTS·렌더·업로드): Latency·Throughput 지표로 말하려면 필요함
- 운영 기간의 자동화 성공률, 장애 횟수, 알림으로 먼저 감지한 실패 건수: 안정성·가용성 지표로 말하려면 필요함
- 로컬 GPU(RTX 4080)에서 모델을 직접 띄워 추론해 본 사례와 GPU 메모리·처리 속도 수치(vLLM·PyTorch 실습 포함): 이 공고의 필수 요건인 서빙·GPU 경험이 현재 근거에 없음
