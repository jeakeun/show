## 회사 읽기 (AI 추정)
회사 유형: 사용자 플랫폼 (확신도 높음, AI 추정)
돈 버는 방식: 라이브 스트리밍 플랫폼(SOOP)으로 대규모 유저를 모아 수익을 내며, 보유한 비디오·오디오·텍스트 데이터에 AI를 접목해 플랫폼 내 상용 AI 서비스로 새 콘텐츠 가치를 만든다.
중요 지표: 대용량 트래픽 처리 능력(동시 접속·처리량), AI 서비스 서빙 안정성(가용성·장애율), 서빙 최적화(지연시간·인프라 비용), AI 기능 사용 유저 수·활용도
안 통하는 지표: 신규 사업 0→1 출시 속도·개수, 상품 판매량, 모델 학습 정확도 등 연구 성과 단독 수치
근거 문구: "최고의 Live Streaming 플랫폼에서 수많은 유저를 대상으로 뉴미디어 상용 AI 서비스를 경험할 수 있습니다." / "안정적인 AI 서비스 서빙 아키텍처 설계 및 개발" / "AI 서비스 백엔드 서버 개발 및 서빙 최적화" / "대용량 트래픽을 처리하는 서버 애플리케이션 개발 경험이 있으신 분"

## 자기소개서

저는 사람이 손대지 않아도 매일 아침·저녁 쇼츠가 올라가는 유튜브 자동화 파이프라인을 운영하고 있습니다 [E20]. 이 파이프라인에서는 판단이나 글쓰기가 필요한 칸에만 언어 모델을 두고, 렌더링·업로드처럼 판단이 없는 공정은 코드가 맡도록 결정했습니다 [E15]. 판단 없는 공정에 AI를 두면 비용과 실패 지점만 늘어난다고 봤기 때문입니다 [E15]. 실측 운영비는 앤트로픽 월 US$51에 제미나이 약 ₩6천이었고, 목표는 US$30 이하로 잡았습니다 [E19]. 판단 난이도에 맞춰 주간 분석에는 Opus, 대본에는 Sonnet, 검수·팩트체크에는 하이쿠를 배정했고, 대본 지시문은 프롬프트 캐싱으로 재사용했습니다 [E19]. 모든 호출의 비용을 기록해 대시보드에 매일 운영비와 주간 분석비로 나눠 보여주도록 했습니다 [E19]. 실측해 보니 대본 생성 비용은 주 US$3.72(호출당 약 US$0.16)였고, 하이쿠 검수 도입 검증 호출은 1건에 US$0.0015였습니다 [E31].

비용을 줄이려다 장애를 낸 적도 있습니다 [E19]. 회고 출력 한도를 16,000에서 10,000 토큰으로 낮췄는데, 상위 모델의 사고 토큰이 이 한도에 포함된다는 점을 놓쳐 본문 0자 실패가 났고 실패 알림도 오지 않았습니다 [E19]. 한도를 24,000으로 올리고 사고 강도를 중간으로 낮췄으며, 한도 초과로 멈추면 명시적 오류로 처리하고 폰으로 알리도록 고쳤습니다 [E31]. 자동화 실패와 품질 저하 발행은 바탕화면 경고 파일과 폰 푸시로 알리고, 알림이 실패해도 본 작업은 멈추지 않게 했습니다 [E36]. AI 출력 형식은 흔들리기 때문에 성공 여부는 관측 가능한 결과물로 판정합니다 [E36]. 작성 AI와 별개로 기준표를 가진 검수 AI를 붙였고, 검수 API에 장애가 나면 통과시키되 코드 사후검사는 그대로 유지하도록 했습니다 [E6][E22]. 검수 AI도 오탐을 냈습니다 [E22]. 9/7~13 재생성 3건이 모두 오탐이었던 것을 찾아, 9/14에 슬롯 정보를 검수 AI에 넘겨 기준을 나누는 방식으로 고쳤습니다 [E22]. 되돌릴 수 있는 프롬프트 개선은 자동 적용하되, 이전본을 보관하고 문법·스모크 테스트에 실패하면 자동으로 원복하도록 했습니다 [E9].

이 프로젝트들은 모두 클로드 코드와 함께 만들었고, 메인 PC의 윈도우 작업 스케줄러에서 매일 자동으로 돌아갑니다 [E27]. 파이썬 3.12 기반 저장소를 운영하면서, 두 PC에서 함께 돌리면 이중 업로드가 나기 때문에 자동 실행은 메인 PC에서만 하도록 정했습니다 [E14]. LangGraph를 학습하면서 중간에 죽었을 때 이어서 하기와 병렬 처리는 제 시스템에 코드로 없던 부분이라는 점도 정리했습니다 [E32].

## 이력서 강조

- 역할별 모델 배정(Opus·Sonnet·하이쿠)과 프롬프트 캐싱을 적용하고, 모든 호출 비용을 기록해 대시보드로 운영했습니다 [E19]. 대본 생성 비용은 주 US$3.72(호출당 약 US$0.16)로 실측했습니다 [E31].
- 토큰 한도 때문에 알림 없이 실패하던 문제를 명시적 오류 처리와 폰 알림으로 고쳤습니다 [E19][E31].
- 실패와 품질 저하 발행을 바탕화면 경고와 폰 푸시로 알리고, 알림이 실패해도 본 작업이 죽지 않게 설계했습니다 [E36].
- 검수 API 장애 시 fail-open으로 통과시키되 코드 사후검사는 유지했습니다 [E22]. 재생성 3건이 모두 검수 오탐이었던 것을 찾아 슬롯별 기준으로 수정했습니다 [E22].
- 프롬프트 자동 적용 시 이전본을 보관하고, 문법·스모크 테스트에 실패하면 자동 원복하도록 했습니다 [E9].
- 클로드 코드와 함께 만든 자동화 프로젝트들을 윈도우 작업 스케줄러로 매일 운영하고 있습니다 [E27].
