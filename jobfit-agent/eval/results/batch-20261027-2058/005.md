## 회사 읽기 (AI 추정)
회사 유형: 기타 (확신도 높음, AI 추정)
돈 버는 방식: 라프텔(애니메이션 스트리밍 플랫폼)의 사내 AX파트로, 외부 매출이 아니라 사내 업무 효율화가 목적인 자리. AI 에이전트로 반복·병목 업무를 자동화하고 흩어진 지식을 연결해 업무 속도·정확도를 높이고 비용을 줄이는 것이 성과다.
중요 지표: 업무 처리 시간 단축(속도), 결과물 정확도, 비용 절감(인력 공수·AI 운영 비용), AI 에이전트 도입·활용 구성원 수 및 확산 사례 수, PoC에서 실제 업무 적용까지의 속도
안 통하는 지표: 서비스 사용자 수·재방문 등 외부 고객 지표, 대규모 트래픽 처리, 모델 자체의 벤치마크 성능 향상, 판매량·조회수
근거 문구: "만들어낸 결과를 속도, 정확도, 비용 등으로 확인하고 지속적으로 개선해요." / "업무 속도와 정확도, 비용 절감 등 AX의 효과를 측정하고 이를 바탕으로 AI 에이전트와 업무 방식을 지속적으로 개선해요." / "AI 에이전트의 활용 현황과 비용, 성과를 지속적으로 살피며 더 효율적으로 운영할 수 있는 방법을 찾아요." / "효과가 검증된 사례를 정리하고 공유하여, 더 많은 구성원이 AI를 업무에 활용할 수 있도록 확산해요." / "정답을 오래 고민하기보다 빠르게 만들어보고 검증해요."

## 자기소개서

저는 유튜브 채널 운영, 취업 정보 수집, 코인 모의투자 같은 개인 자동화 프로젝트를 클로드 코드와 함께 만들었고, 이 프로젝트들은 윈도우 작업 스케줄러에서 매일 자동으로 돌아갑니다 [E34]. 유튜브 파이프라인을 부서별 에이전트로 나누자는 안이 나왔을 때, 저는 판단 없는 공정에 감독관을 두는 셈이라고 보고 기각했습니다 [E7]. 대신 대본 작성·검수·주간 회고처럼 판단이나 글쓰기가 필요한 칸에만 LLM을 두기로 결정했습니다 [E7]. 렌더링·업로드·자막 맞추기는 코드에 맡겨 비용과 실패 지점이 늘지 않게 했고, 8/04부터 하루 2편 돌던 코드 파이프라인은 쪼개지 않고 유지했습니다 [E7][E5]. 모든 호출 비용을 기록한 결과, 9/7~13 기준 대본 생성 비용은 주 US$3.72(호출당 약 US$0.16)였고 하이쿠 검수 도입 검증 호출 1건은 US$0.0015였습니다 [E14]. 대시보드에서는 API 비용을 매일 운영비와 주간 분석비로 나눠 보여 줍니다 [E35]. 비용을 줄이다가 사고 토큰 때문에 회고 본문이 0자로 실패한 적이 있습니다 [E14]. 이때 US$0.76이 낭비됐고 실패 알림도 오지 않았습니다 [E14]. 이후 한도를 24,000으로 올리고, 한도 초과는 명시적 오류로 처리하며, 실패하면 폰으로 알림이 오게 고쳤습니다 [E14].

정확도를 지키려고 만드는 AI와 검사하는 AI를 나눴습니다 [E25]. 업로드는 무인 자동이라 사람이 대본을 볼 수 없습니다 [E25]. 그래서 별도 검수 AI가 기준표로 채점하고, 코드가 제목과 의료 단어를 사후 검사하는 게이트를 두었습니다 [E25]. 도입 검증에서 정상 대본 3편은 지적 없이 통과했고, 의료 조언을 넣은 가짜 대본은 정확히 차단했습니다 [E27]. 그런데 9/7~13에 나온 재생성 3건(21%)은 모두 검수 AI의 오탐이었습니다 [E14][E27]. 고전실험형 전용인 "훅" 기준을 저녁 리스트형 대본에도 적용한 것이 원인이어서, 9/14에 슬롯 정보를 검수 AI에 넘겨 기준을 나눴습니다 [E27]. 매번 같은 답이 나와야 하는 일도 같은 방식으로 정리했습니다 [E11]. 고정 문자열을 AI가 쓰고 AI가 검사하게 했다가 사흘간 영상이 빠지는 루프를 겪었고, 그 뒤로 고정 문자열은 코드가 붙이게 바꿨습니다 [E11]. 리포트가 실제 데이터와 맞는지 확인하려고 읽기 전용 감사 에이전트 3기를 병렬로 돌려, 리포트의 주장을 원본 데이터와 대조했습니다 [E10]. 그 결과 노출된 API 키, 코인봇 수수료 계산 오류(20.5%), 없는 회차 기록을 찾았습니다 [E10]. 1회차 주간 감사 시험에서는 8건을 발견했고, 검증을 거쳐 6건을 실제로 고쳤습니다 [E10].

속도와 안전 사이의 균형도 직접 겪으며 조정했습니다 [E24]. 8월에는 회고 AI가 플레이북을 바로 반영했고, 9/7부터는 모든 회고 제안을 사람이 승인하게 했습니다 [E24]. 그러자 9/20에 플레이북이 승인 대기로 하루 묵어, 9/21 적용 시작을 놓쳤습니다 [E24]. 그래서 9/21부터 기준을 "되돌릴 수 있는가"로 바꿨습니다 [E24][E26]. 되돌릴 수 있는 플레이북·프롬프트 개선은 이전본을 보관한 채 자동 적용하고 나중에 보고하며, 돈이 드는 결정이나 영상 삭제처럼 되돌릴 수 없는 일만 사람이 고릅니다 [E24][E26]. 프레임워크는 학습 단계로, LangChain의 create_agent에 읽기 전용 도구를 붙인 에이전트를 시험용 가짜 모델로 실행해 도구 호출 루프를 확인했습니다 [E13]. RAG는 아직 운영 시스템에 없습니다 [E32]. 학습용으로 제 설계 문서에 청킹과 키워드 검색을 실험해, 분할기 설정 하나로 검색 결과가 바뀌는 것을 확인했습니다 [E32]. 제목 기준 분할기의 기본 설정이 섹션 제목을 본문에서 빼서 못 찾던 질문이, 제목을 본문에 남기자 정답을 1등으로 찾았습니다 [E39]. 다만 질문 하나로 한 실험이라 평가셋으로 다시 확인해야 합니다 [E39].
