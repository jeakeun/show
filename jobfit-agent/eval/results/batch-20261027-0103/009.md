## 자기소개서

사람이 손대지 않아도 매일 반복되는 업무가 돌아가도록 자동화를 설계하고 운영해 왔습니다 [E6]. 1분호기심 유튜브 채널은 트렌드 수집, 대본 작성, 렌더링, 업로드, 주간 회고까지 하루 2편을 자동으로 처리하며 2026-08-02부터 운영 중입니다 [E5][E19]. 파이프라인을 단계마다 부서별 에이전트로 나누자는 안이 나왔을 때, 판단이 없는 공정에 감독관만 늘어나는 셈이라 이득이 없다고 보고 기각했습니다 [E8]. 대본 작성·검수·팩트체크처럼 판단이 필요한 칸에만 LLM을 두고 렌더링·업로드는 코드에 맡겨, 하루 2편 돌던 파이프라인을 쪼개지 않고 유지했습니다 [E7][E8]. 6인 팀 프로젝트인 집가에서는 마케팅 파트를 혼자 맡아 영상 정규화부터 발행 큐까지 M1~M6 파이프라인으로 자동화했습니다 [E14]. 이 프로젝트들은 제가 설계·운영하고 클로드 코딩 에이전트가 구현하는 방식으로 만들었습니다 [E6][E10].

업로드가 무인 자동이라 사람이 결과를 볼 수 없었기 때문에, 콘텐츠를 만드는 AI와 검사하는 AI를 분리했습니다 [E26]. 별도 검수 AI가 기준표로 대본을 채점하고, 코드가 제목과 의료 관련 단어를 사후검사합니다 [E26]. 차단급 문제가 나오면 대본을 재생성하고, 2번 연속 걸리면 예비 대본으로 바꿉니다 [E26]. 검수 API에 장애가 나면 대본을 통과시키되 코드 사후검사는 유지하는 fail-open 방식을 택했습니다 [E26]. 실패나 품질 저하가 있는 상태로 발행되면 바탕화면 경고 파일과 폰 푸시로 알리고, 올린 영상이 채널에서 사라지면 한 번 알림을 보냅니다 [E23]. AX 채용공고와 AI 논문·뉴스를 매일 수집하는 AI데일리에서는 카운터를 AI가 세지 않고 코드가 데이터에서 계산합니다 [E24]. 생성이 끝나면 검수 에이전트가 형식·링크·한글 깨짐을 다시 검사합니다 [E24]. 코드·설정·프롬프트 수정은 work 브랜치에서 하고, 검증·테스트를 통과한 뒤에만 main에 병합합니다 [E12]. 예약 작업이 도는 중에는 병합을 거부하도록 해서 운영 중인 자동화를 보호합니다 [E12].

에이전트의 도구 정의와 RAG는 학습과 실험 단계입니다 [E10][E16]. LangChain으로 읽기 도구는 바로 실행하고 쓰기 도구는 사람 승인 뒤에 실행되도록 나눈 예제를 만들었습니다 [E2][E21]. 이 예제를 시험용 가짜 모델로 실행해, 승인 전에는 DB 값이 바뀌지 않는 것을 확인했습니다 [E2]. 같은 학습 예제에서 도구 설명문에 입력 형식과 한도를 적고, 자유 SQL 대신 정해진 쿼리에 파라미터만 넣도록 도구를 정의했습니다 [E21][E22]. RAG는 아직 운영 시스템에 적용하지 않았습니다 [E16]. 제 설계 문서로 청킹을 실험해 보니, 글자 수로만 자르면 41조각 중 31조각은 어느 섹션 내용인지 알 수 없었습니다 [E4]. 다음에는 실제 운영 문서로 평가셋을 만들고 정답 적중률로 설정을 비교할 계획입니다 [E16].

## 이력서 강조

- 하루 2편 무인 제작·업로드 파이프라인을 설계·운영 중이며(2026-08-02~), 판단이 필요한 칸에만 LLM을 두고 나머지는 코드로 처리했습니다 [E7][E8][E19].
- 생성 AI와 검수 AI를 분리하고 코드 사후검사를 더했으며, 재생성·예비 대본 전환·fail-open으로 예외를 처리합니다 [E26].
- 실패·품질 저하 발행 시 경고 파일과 폰 푸시를 보내고, 업로드한 영상이 사라지면 알림을 보내도록 모니터링을 구성했습니다 [E23].
- 매일 채용공고와 논문·뉴스를 수집·요약하는 AI데일리를 운영하며, 수치는 코드가 계산하고 결과는 검수 에이전트가 재검사합니다 [E24].
- Git 브랜치 작업 규칙을 운영합니다: 검증·테스트를 통과해야 병합하고, 예약 작업이 도는 중에는 병합을 거부합니다 [E12].
- (학습) LangChain 읽기/쓰기 도구 분리와 승인 미들웨어 예제를 실행했고, RAG 청킹 실험으로 분할 방식에 따른 차이를 확인했습니다 [E2][E4].
