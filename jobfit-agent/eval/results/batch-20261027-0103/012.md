돈 버는 방식: 채용 플랫폼 '원티드'의 매칭 데이터와 AI 매칭으로 수익을 내며, 자체 AI 솔루션 엔노이아 기반 AX 사업(기업용 AI 에이전트·운영 솔루션)으로 확장 중. 이 팀은 AI 기능을 서비스에 안정적으로 서빙·운영하는 역할로, AI 기술력이 제품 경쟁력이 되는 구조.

## 초안 (사람 확정 직전, 승인 안 함)
## 자기소개서

저는 LLM을 쓰는 자동화 파이프라인을 설계·운영하면서, 역할마다 모델을 다르게 두고 모든 호출의 비용을 기록해 왔습니다 [E11]. 여기서 운영 경험은 제가 설계·운영하고, 구현은 클로드 코딩 에이전트가 맡은 시스템을 말합니다 [E2]. 기록해 보니 대본 생성 비용은 주 US$3.72, 호출당 약 US$0.16이었고, 하이쿠로 검수를 도입하기 전에 돌린 검증 호출 1건은 US$0.0015였습니다 [E24]. 비용을 줄이던 중 사고 토큰 때문에 회고가 본문 0자로 실패해 US$0.76이 낭비됐고, 당시에는 실패 알림도 없었습니다 [E24]. 그래서 한도를 24,000으로 올리고 사고 강도를 중간으로 낮췄습니다. 또 한도 초과는 명시적 오류로 처리하고, 실패하면 폰으로 알림이 오게 바꿨습니다 [E24]. 지금은 매일 23:50에 API 비용과 유튜브 통계 등을 공유 저장소 한 곳에 모읍니다. 업로드 실패·가드 발동·수집 실패는 폰 푸시로 받습니다 [E6].

품질 쪽에서는 만드는 AI와 검사하는 AI를 나누는 결정을 내렸습니다 [E11]. 작성 AI와 별개로 기준표를 가진 검수 AI를 붙였습니다 [E10]. 그런데 검수 AI도 오탐을 냈습니다. 일주일 동안 재생성된 3건이 전부 오탐이었던 것을 찾아 슬롯별 기준으로 고쳤습니다 [E10]. 파이프라인을 부서별 에이전트로 나누자는 안도 나왔지만 기각했습니다. 판단 없는 공정에 감독관을 두면 비용과 실패 지점만 늘어난다고 봤기 때문입니다 [E16]. LLM은 대본 작성, 검수, 팩트체크처럼 판단이나 글쓰기가 필요한 칸에만 두었습니다. 렌더링·업로드·자막 맞추기는 코드가 맡게 했습니다 [E16]. 그 결과 8/04부터 돌던 코드 파이프라인을 쪼개지 않고 유지했습니다 [E17]. 사람 승인도 처음에는 모든 회고 제안에 받게 했습니다. 그러다 9/20에 플레이북이 승인 대기로 하루 묵어 적용 시작을 놓쳤고, 이후 승인 기준을 "되돌릴 수 있는가"로 바꿨습니다 [E26]. 이제 되돌릴 수 있는 플레이북·프롬프트 개선은 이전본을 보관한 채 자동 적용합니다. 프롬프트가 문법·스모크 테스트에 실패하면 자동으로 원복합니다 [E26].

Agent 프레임워크는 학습 단계이며, 2026-10-22에 예제를 직접 실행해 확인했습니다 [E2]. LangChain의 create_agent에 HumanInTheLoopMiddleware와 ToolCallLimitMiddleware를 붙여 시험용 가짜 모델로 실행해 봤습니다 [E1]. 조회 도구는 승인 없이 바로 실행됐습니다. 쓰기 도구는 호출 직전에 멈췄고, 승인한 뒤에야 DB 값이 0에서 1로 바뀌는 것을 확인했습니다 [E1]. 조회 도구는 자유 SQL 대신 정해진 쿼리와 파라미터만 쓰고, 합계는 도구가 계산하게 했습니다 [E21]. LangGraph로는 제 대본 검수 게이트의 갈림길 구조만 흉내 낸 학습 예제를 만들었습니다 [E30]. 이 검수 루프를 돌려 1차 실패 뒤 2차에 통과하는 최종 상태를 확인했습니다 [E28]. 지금은 LangGraph·RAG 기반의 jobfit-agent를 개발하고 있습니다. 공고 분석부터 경력 근거 검색, 적합도 계산, 근거 검증, 사람 확정까지 잇는 구조이며, 2026-10-23에 첫 골격이 가짜 모델 테스트를 통과한 단계입니다 [E6].

- (설계·운영) 역할마다 모델을 다르게 두고 모든 호출 비용을 기록했습니다 [E11]. 그 결과 대본 생성 비용이 주 US$3.72, 호출당 약 US$0.16임을 측정했습니다 [E24].
- (설계·운영) 사고 토큰 때문에 회고가 본문 0자로 실패한 사고(US$0.76 낭비, 알림 없음)를 고쳤습니다. 한도를 24,000으로 올리고, 사고 강도를 중간으로 낮추고, 한도 초과를 명시적 오류로 처리하고, 실패 시 폰 알림을 추가했습니다 [E24].
- (설계·운영) 작성 AI와 분리된, 기준표 기반 검수 AI를 붙였습니다. 일주일 재생성 3건이 전부 오탐인 것을 찾아 슬롯별 기준으로 고쳤습니다 [E10].
- (설계·운영) LLM은 판단·글쓰기 칸에만 두고 렌더링·업로드·자막 맞추기는 코드로 처리했습니다 [E16]. 이 구조로 8/04부터 돌던 파이프라인을 쪼개지 않고 유지했습니다 [E17].
- (설계·운영) 사람 승인 기준을 "되돌릴 수 있는가"로 정했습니다. 되돌릴 수 있는 개선은 이전본을 보관한 뒤 자동 적용하고, 프롬프트는 테스트에 실패하면 자동 원복합니다 [E26].
- (학습) LangChain create_agent에 HumanInTheLoopMiddleware·ToolCallLimitMiddleware를 붙인 예제를 실행했습니다. 읽기 도구는 즉시, 쓰기 도구는 승인 뒤에 실행되는 흐름을 확인했습니다 [E1].

## 보강할 증거

- 검수 기준을 슬롯별로 고친 뒤 오탐 건수와 재생성률이 어떻게 바뀌었는지 전후 숫자. 이 회사의 "AI 품질·정확도" 지표로 말할 수 있습니다.
- 역할별 모델 분리 전후의 월 총비용과 목표 도달 여부. 근거에 "확인 필요"로 남아 있으니 실제 청구 내역으로 채우세요.
- 대본 생성·검수 호출의 응답 시간 기록. 지연시간 지표가 근거에 하나도 없습니다.
- 실패 알림과 명시적 오류 처리를 넣은 뒤의 장애 감지·복구 시간, 파이프라인이 끊기지 않고 돈 날짜 수. 서비스 안정성 지표로 쓸 수 있습니다.
