## 자기소개서

에이전트를 설계할 때 저는 판단하는 AI를 어느 칸에 둘지부터 정합니다 [E7]. 유튜브 파이프라인을 단계마다 "부서별 에이전트"로 나누자는 안이 나왔을 때, 판단 없는 공정에 감독관을 두는 격이라 이득이 없다고 보고 기각했습니다 [E7]. 대신 대본 작성, 검수, 팩트체크처럼 판단이나 글쓰기가 필요한 칸에만 LLM을 두고, 렌더링·업로드·자막 맞추기는 코드가 맡게 했습니다 [E7]. 판단이 필요 없는 공정에까지 AI를 두면 비용과 실패 지점만 늘어나기 때문입니다 [E7]. 그 결과 8/04부터 돌던 코드 파이프라인을 쪼개지 않고 유지했습니다 [E8]. 사람 승인 위치는 "되돌릴 수 있는가"를 기준으로 정했습니다 [E13]. 처음에는 전부 자동 반영했고 다음에는 전부 승인을 받게 했는데, 두 방식 모두 문제를 겪었습니다 [E13]. 그래서 되돌릴 수 있는 변경은 이전본을 남긴 뒤 자동 적용하고 보고합니다 [E13]. 돈이 드는 결정, 영상 삭제·공개 전환, 실전 매매 전환처럼 되돌릴 수 없는 일은 지금도 사람이 A/B/C/D 선택지 중에서 고릅니다 [E13].

에이전트가 기업 업무 시스템을 조작하는 일은 "어떤 도구를, 어떤 권한으로, 어떤 안전장치와 함께 주는가"를 설계하는 일로 보고 학습했습니다 [E21]. 예제에서는 조회 도구가 자유 SQL 대신 미리 정한 쿼리에 파라미터만 넣어 실행되게 했습니다 [E3]. 쓰기 도구는 HumanInTheLoopMiddleware로 호출 직전에 멈추게 했고, 폭주를 막기 위해 ToolCallLimitMiddleware로 호출 횟수를 제한했습니다 [E25]. 시험용 가짜 모델로 실행해 보니, 승인 전에는 DB 값이 바뀌지 않았고 승인 후에만 바뀌었습니다 [E25]. 여러 에이전트가 같은 시스템을 쓸 때 도구를 MCP 서버 하나에 모으면 연동 코드를 에이전트마다 다시 짤 필요가 없다는 점도 정리했습니다 [E6]. 같은 구조에서는 권한·로그·호출 제한을 한 곳에서 관리할 수 있다는 점도 함께 정리했습니다 [E6]. 노션·깃허브 등은 MCP로 연결해 보았습니다 [E4]. 공식 API가 없는 티스토리는 비공식 방법이 언제 깨질지 모르고 계정 제재 위험도 있어 자동화하지 않았고, 사람이 마지막 클릭을 하는 보조 모드로 두었습니다 [E4].

운영 쪽에서는 매일 23:50에 유튜브 통계·API 비용·코인 매매·채용 카운트를 SQLite 공유 저장소 한 곳에 모으는 수집 스크립트를 돌리며, 원본은 읽기만 하게 했습니다 [E14]. 매주 일요일 10:00에는 코드 원본과 로그를 대조해 이상 징후를 보고하는 자체 감사 리포트가 작성됩니다 [E15]. 업로드 실패, 가드 발동, 수집 실패는 폰 푸시 알림으로 받습니다 [E15]. LangChain·LangGraph는 버전부터 확인하는 습관을 들이며 학습했고, 1.0에서 `create_react_agent` 대신 `create_agent`를 쓰는 변화도 정리했습니다 [E11]. 순서가 고정된 단순 파이프라인에는 LangGraph를 쓰지 않는다는 기준도 함께 세웠습니다 [E11]. RAG는 질문·정답·정답 위치를 30~50개 묶은 평가셋을 먼저 만들고, 청킹 크기·임베딩 모델·k값·하이브리드 여부를 하나씩 바꿔 비교하는 평가 방법을 학습했습니다 [E16]. 지금은 공고 분석, 경력 근거 병렬 검색, 근거 검증, 사람 확정으로 이어지는 LangGraph·RAG 기반 jobfit-agent를 개발하고 있으며, 가짜 모델 테스트를 통과한 첫 골격 단계입니다 [E14].

## 이력서 강조

- 판단 없는 단계는 에이전트로 만들지 않는 기준을 세워 LLM을 판단·글쓰기 칸에만 두었고, 코드 파이프라인을 쪼개지 않고 유지했습니다 [E8].
- 사람 승인 위치를 "되돌릴 수 있는가"로 정해, 되돌릴 수 있는 변경은 이전본 보관 후 자동 적용·보고하고 되돌릴 수 없는 결정은 사람이 고르게 했습니다 [E13].
- 읽기 도구는 바로 실행하고 쓰기 도구는 승인 뒤에 실행하며 호출 횟수를 제한하는 에이전트를 예제로 만들어, 승인 전에는 DB가 바뀌지 않는 것을 가짜 모델로 확인했습니다 [E25].
- 유튜브 통계·API 비용·코인 매매·채용 카운트를 매일 SQLite 한 곳에 모으고 원본은 읽기만 하는 수집 스크립트를 운영하고 있습니다 [E14].
- LangGraph `Send` 예제로 감사 노드 3개를 동시에 실행하고, 결과를 보고서 작성 노드 하나로 합쳐 보았습니다 [E20].
- LangGraph·RAG 기반 맞춤 지원서 에이전트(jobfit-agent)를 개발하고 있으며, 첫 골격이 가짜 모델 테스트를 통과했습니다 [E14].

## 보강할 증거

- 비용·실패 지점 숫자: LLM을 판단 칸에만 둬서 아낀 API 비용이나 파이프라인 실패율을 hub에 쌓인 API 비용 데이터에서 뽑아 두면, "비용과 실패 지점을 줄였다"를 숫자로 말할 수 있습니다.
- MCP 서버 직접 개발 사례: 지금은 MCP로 "연결해 본" 경험뿐이라 78종+ 어댑터 업무에 대한 질문에 약합니다. 계획대로 작은 Spring Boot API를 레거시 역할로 두고 MCP 서버나 도구로 감싼 결과물이 있으면 좋습니다.
- RAG 검색 정확도: jobfit-agent에서 평가셋을 만들어 top-k 적중률, 근거 충실도를 실제로 잰 숫자가 필요합니다. 하이브리드 검색과 리랭킹 적용 전후 비교가 있으면 더 좋습니다.
- 자동 적용 후 보고 운영 기록: 9/21 전환 이후 실제 자동 적용·자동 원복 건수가 "확인 필요"로 남아 있습니다. 면접에서 성공률을 물으면 답할 수 있게 정리해 두세요.
