## 회사 읽기 (AI 추정)
회사 유형: 사용자 플랫폼 (확신도 높음, AI 추정)
돈 버는 방식: 기업 고객사에 올인원 AI 메신저(고객 상담·CRM·마케팅·AI 에이전트·음성) SaaS를 제공해 구독/사용량 기반으로 매출을 내는 B2B 플랫폼. 고객사 사이트·앱에 SDK가 설치되어 대규모 실시간 트래픽을 처리한다.
중요 지표: 매출·사용자 활성화·리텐션 등 비즈니스 지표 개선, 높은 트래픽·급격한 사용량 변화에서의 안정성(장애 격리, 가용성), 대용량 데이터 조회·실시간 상호작용 성능, 호스트 앱/웹 성능에 영향 없는 SDK 경량성·안정성, Feature 팀 개발 속도·생산성 향상, 아키텍처·기술 부채 개선
안 통하는 지표: 고객·비즈니스 지표와 연결되지 않은 순수 알고리즘/모델 정확도 수치, 구현만 하고 출시·운영 결과가 없는 성과, 단발성 신규 사업 론칭 개수
근거 문구: "기업의 지속 가능한 성장을 돕는 올인원 AI 메신저를 만들며" / "고객이 체감하는 변화와 매출·사용자 활성화·리텐션 같은 비즈니스 결과를 책임지는" / "높은 트래픽과 급격한 사용량 변화에도 안정적으로 동작할 수 있도록 확장성·장애 격리·관측 가능성을 갖춘 시스템을 설계하고" / "호스트 앱의 성능과 안정성에 영향을 주지 않으면서 실시간 기능을 제공하는 문제를 다룹니다" / "모든 Feature 팀이 빠르고 안정적으로 제품을 개발하도록 돕는 기술 플랫폼 조직"

## 자기소개서

저는 AI 결과를 그대로 믿지 않고, 검사하고 관측할 수 있는 구조로 운영해 왔습니다 [E11][E10]. 유튜브 대본 파이프라인에서는 대본을 만드는 AI와 검사하는 AI를 나눴고, 검수 API가 장애일 때는 통과시키되 코드 사후검사는 그대로 유지하게 했습니다 [E11]. 9/7~13에 생긴 재생성 3건은 모두 검수 오탐이었는데, 고전실험형 전용인 "훅" 기준을 저녁 리스트형 대본에도 적용한 탓이었습니다 [E11]. 9/14에 슬롯 정보를 검수 AI에 넘겨 대본 유형별로 기준을 나누는 방식으로 고쳤습니다 [E11]. 자동화 실패와 품질 저하 발행은 바탕화면 경고 파일과 폰 푸시로 알리게 했고, 알림이 실패해도 본 작업은 멈추지 않게 했습니다 [E10]. AI 출력 형식은 흔들리기 때문에 성공 여부는 리포트 파일이 실제로 있는지처럼 관측 가능한 결과물로 판정합니다 [E10][E23].

비용, 신뢰성, 속도 사이의 판단은 실제로 운영하면서 겪은 문제를 근거로 내렸습니다 [E4][E25]. 파이프라인을 부서별 에이전트로 나누자는 안이 나왔을 때, 판단이 없는 공정에 AI를 두면 비용과 실패 지점만 늘어난다고 보고 기각했습니다 [E4]. LLM은 대본 작성·검수처럼 판단이나 글쓰기가 필요한 칸에만 두고, 렌더링·업로드·자막 맞추기는 코드가 맡게 했습니다 [E4]. 그래서 8/04부터 하루 2편씩 돌던 코드 파이프라인을 쪼개지 않고 유지했습니다 [E8]. 사람 승인 위치도 바꿔 왔습니다 [E25]. 처음에는 회고 AI가 플레이북을 바로 반영했고, 9/7부터는 모든 제안을 사람이 승인하게 했습니다 [E25]. 그런데 9/20에는 플레이북이 승인 대기로 하루 묵으면서 적용 시작을 놓쳤습니다 [E25]. 반대로 이미 올린 영상을 지우고 다시 올렸을 때는 16시간 동안 조회가 2회에 그쳤고, 밖으로 나간 것은 되돌릴 수 없다는 것을 겪었습니다 [E25]. 그래서 9/21부터 되돌릴 수 있는 개선은 이전본을 보관한 채 자동 적용하고, 프롬프트는 문법·스모크 테스트에 실패하면 자동으로 원복하게 했습니다 [E25][E5]. 돈이 드는 결정이나 영상 삭제·공개 전환은 계속 사람이 정하게 했습니다 [E5].

데이터 정합성과 권한 통제도 직접 챙겼습니다 [E13][E23]. 프로젝트가 늘면서 리포트가 실제 데이터와 맞는지 아무도 대조하지 않았기 때문에, 읽기 전용 감사 에이전트로 리포트의 주장을 원본 데이터와 대조하게 했습니다 [E13]. 8/27 첫 감사에서 코인봇의 수수료 계산 오류(20.5%)와 AI데일리에 기록된 없는 회차(유령 데이터)를 찾았습니다 [E13]. 같은 날 진행한 주간 감사 시험에서는 8건을 발견했고, 검증을 거쳐 6건을 실제로 고쳤습니다 [E13]. 감사 과정에서 회고 AI가 열려 있던 쓰기 권한으로 임시 스크립트를 만든 전례도 찾았습니다 [E23]. 이를 막으려고 실행 전에 설정·소스 파일 해시를 백업하고, 파일이 바뀌면 자동으로 원복하는 가드를 넣었습니다 [E23]. 9/6에 회고 AI가 다시 임시 스크립트를 만들었을 때 가드가 이를 격리하는 것을 확인했습니다 [E23]. 기반 지식으로는 7개월 과정에서 Java·Spring Boot·React·AWS를 익혔습니다 [E18]. 학습 예제에서는 자유 SQL 대신 정해진 쿼리에 파라미터만 넣는 조회 도구를 만들었습니다 [E36]. 같은 예제에서 조회 도구는 바로 실행하고 쓰기 도구는 사람 승인 뒤에 실행되는 흐름을 시험용 가짜 모델로 돌려 확인했습니다 [E35].

## 이력서 강조

- 만드는 AI와 검사하는 AI를 분리한 대본 검수 게이트를 운영했고, 검수 오탐 3건의 원인을 찾아 슬롯별 기준으로 고쳤습니다 [E11].
- 자동화 실패와 품질 저하를 바탕화면 경고와 폰 푸시로 알리게 했고, 알림이 실패해도 본 작업은 멈추지 않게 했습니다 [E10].
- 판단 없는 공정은 코드로 두어, 하루 2편씩 돌던 파이프라인을 에이전트로 쪼개지 않고 유지했습니다 [E4][E8].
- 되돌릴 수 있는 변경은 이전본 보관과 자동 원복 장치를 둔 채 자동 적용하고, 되돌릴 수 없는 결정은 사람이 고르는 승인 구조로 바꿨습니다 [E25][E5].
- 읽기 전용 감사로 수수료 계산 오류(20.5%)와 유령 데이터를 찾았고, 주간 감사 시험에서 발견한 8건 중 6건을 고쳤습니다 [E13].
- 분석 AI가 설정을 무단으로 바꾸지 못하게 해시 백업·자동 원복 가드를 넣었고, 9/6에 실제로 격리되는 것을 확인했습니다 [E23].

## 보강할 증거

- 안정성 지표: 파이프라인 가동률, 월별 장애 건수, 알림을 받은 뒤 복구하기까지 걸린 시간. 채널톡이 중시하는 장애 격리·관측 가능성을 숫자로 말할 수 있습니다.
- 비용 지표: LLM을 판단 칸에만 둔 구조의 월별 API 비용, 그리고 검수 AI 추가 전후의 비용·시간 변화.
- 사용자·비즈니스 지표: 유튜브 채널 조회수·시청 유지율, 집가 채널별 성과 리포트 숫자. 활성화·리텐션 관점의 근거가 됩니다.
- 꼬리 질문 대비: 감사에서 찾은 노출 API 키의 재발급 여부, 9/21 이후 실제 자동 적용 기록. 둘 다 현재 근거상 미완료이거나 확인이 필요하므로 면접 전에 정리해 두는 것이 좋습니다.
