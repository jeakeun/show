## 회사 읽기 (AI 추정)
회사 유형: 기타 (확신도 높음, AI 추정)
돈 버는 방식: 라프텔(애니메이션 서비스로 알려져 있으나 공고에 사업 설명은 없음)의 사내 AX파트로, 외부 매출이 아닌 사내 업무 효율화를 담당. 지표는 AI 도입으로 업무를 더 빠르고 정확하고 싸게 만드는 것(속도·정확도·비용 절감·자동화된 반복 업무·확산된 구성원 수).
중요 지표: 업무 처리 속도 향상/시간 절감, AI 결과물 정확도, 운영 비용 절감(AI 에이전트 비용 포함), 자동화한 반복 업무·병목 개수, AI 활용 구성원 확산 정도, PoC에서 실제 업무 적용까지의 속도
안 통하는 지표: 외부 사용자 수·DAU·재방문율, 대규모 트래픽 처리 성능, 매출·판매량·조회수, 모델 벤치마크 점수 자체(업무 효과와 무관한 경우)
근거 문구: "AI를 활용해 라프텔의 일하는 방식을 더 나은 방향으로 바꿔나가는 팀이에요." / "만들어낸 결과를 속도, 정확도, 비용 등으로 확인하고 지속적으로 개선해요." / "업무 속도와 정확도, 비용 절감 등 AX의 효과를 측정하고" / "AI 에이전트의 활용 현황과 비용, 성과를 지속적으로 살피며" / "구성원들이 반복적인 업무에서 벗어나 각자의 전문성과 판단이 필요한 일에 더 집중할 수 있도록" / "정답을 오래 고민하기보다 빠르게 만들어보고 검증해요."

## 자기소개서

저는 유튜브 대본 생성 파이프라인과 AX 채용정보 자동 수집기를 설계하고 운영했으며, 구현은 클로드 코딩 에이전트와 함께 했습니다 [E1][E21][E24]. 역할마다 모델을 다르게 쓰고 모든 호출 비용을 기록해 왔습니다 [E8]. 그 기록으로 대본 생성 비용이 주 US$3.72(호출당 약 US$0.16)이고, 하이쿠 검수 도입 검증 호출 1건은 US$0.0015임을 확인했습니다 [E8]. 비용을 줄이려다 사고 토큰 때문에 본문 0자 실패가 나서 US$0.76이 알림 없이 낭비된 적이 있습니다 [E8]. 이후 한도를 24,000으로 올리고, 한도 초과는 명시적 오류로 처리하며, 실패하면 폰으로 알리도록 고쳤습니다 [E8]. 렌더링·업로드처럼 판단이 없는 단계는 에이전트로 쪼개지 않고 코드에 맡겼고, 대본 작성·검수·회고처럼 판단이 필요한 칸에만 LLM을 두었습니다 [E21]. 판단 없는 공정에 AI를 두면 비용과 실패 지점만 늘어난다고 봤기 때문입니다 [E21].

정확도를 위해 작성 AI와 별개로 기준표를 가진 검수 AI를 붙였습니다 [E11]. 도입 검증에서 정상 대본 3편은 지적 없이 통과했고, 의료 조언을 넣은 가짜 대본은 정확히 차단됐습니다 [E10]. 9/7~13 기준선에서는 대본 생성 17회로 14편을 만들었고 재생성이 3건(21%) 나왔는데, 3건 모두 검수 AI의 오탐이었습니다 [E8][E10]. 고전실험형 전용 "훅" 기준을 저녁 리스트형 대본에도 적용한 탓이었고, 9/14에 슬롯 정보를 검수 AI에 넘겨 기준을 나누는 방식으로 고쳤습니다 [E10]. 고정 문자열을 AI가 쓰고 AI가 검사하게 했다가 사흘간 영상이 빠지는 루프를 겪은 적이 있습니다 [E9]. 그 뒤로 매번 같은 답이 나와야 하는 숫자와 고정 문자열은 코드가 맡도록 바꿨습니다 [E9]. 그 결과 카운터 계산 근거가 파일로 남아 감사할 수 있게 됐습니다 [E9]. 읽기 전용 주간 감사도 운영했습니다 [E2]. 1회차 시험에서 8건을 발견해 검증 후 6건을 실제로 고쳤습니다 [E2].

처음 8월에는 회고 AI가 플레이북을 바로 반영하게 했다가, 9/7에 모든 회고 제안을 사람이 승인하도록 바꿨습니다 [E20]. 그러자 9/20에 플레이북이 승인 대기로 하루 묵어 9/21 적용 시작을 놓쳤고, 비개발자인 운영자에게는 승인 판단 자체도 부담이었습니다 [E20]. 그래서 기준을 "되돌릴 수 있는가"로 바꿨습니다 [E20]. 되돌릴 수 있는 플레이북·프롬프트 개선은 이전본을 보관한 채 자동 적용한 뒤 보고하고, 돈이 드는 결정이나 영상 삭제·공개 전환은 계속 사람이 정하게 했습니다 [E19][E20]. 새 프레임워크는 학습 단계에서 직접 실험했습니다 [E24]. langgraph 1.2.16에서 시험용 가짜 모델로 감사관 3개를 병렬로 돌리고, 그 결과를 보고서 노드 하나로 합치는 구조를 실행해 확인했습니다 [E24][E26]. RAG도 학습용으로 제 설계 문서에 청킹과 키워드 검색을 실험했습니다 [E18]. 그 과정에서 제목 기준 분할기의 기본 설정이 제목을 검색에서 빼버려 결과가 뒤집히는 것을 확인했습니다 [E6][E18]. 다만 질문 하나로 한 실험이라 평가셋으로 다시 확인해야 합니다 [E6].

## 이력서 강조

- 역할별로 모델을 다르게 쓰고 호출마다 비용을 기록해, 대본 생성 비용 주 US$3.72(호출당 약 US$0.16)를 측정했습니다 [E8].
- 작성 AI와 검수 AI를 분리했습니다 [E11]. 재생성 3건(21%)이 전부 검수 오탐임을 찾아 9/14에 슬롯별 기준으로 고쳤습니다 [E8][E10].
- 사람 승인 기준을 "되돌릴 수 있는가"로 재설계해, 9/21부터 되돌릴 수 있는 변경은 자동 적용 후 보고로 전환했습니다 [E19][E20].
- 읽기 전용 주간 감사를 운영해, 1회차 시험에서 8건을 발견하고 검증 후 6건을 수정했습니다 [E2].
- 분석 AI가 설정을 바꾸면 자동 원복하고 새 파일은 격리하는 가드를 넣었고, 9/6에 실제 격리를 확인했습니다 [E13].
- 매일 07:00 채용공고, 08:00 논문·뉴스 요약을 자동 수집하는 시스템을 운영하며, 생성 후 검수 에이전트가 형식·링크·한글 깨짐을 다시 검사하게 했습니다 [E1].
