## 회사 읽기 (AI 추정)
회사 유형: 기술 판매 (확신도 보통, AI 추정)
돈 버는 방식: 의료 AI 기업. 인공지능 기술로 의료 서비스 질 개선과 의료진 업무 효율화를 제공하며, 자체 AI 모델을 의료 현장 제품으로 서비스한다. 이 포지션은 모델을 빠르고 안정적으로 제품화하는 AI Serving/Runtime/Agent 플랫폼을 담당한다.
중요 지표: 추론 Latency 단축, Throughput 향상, GPU Memory·GPU 자원 활용 효율(비용 절감), 서비스 안정성·가용성, 모델 배포 속도(Research→Production 리드타임), 여러 제품에서의 플랫폼 재사용성·확장성
안 통하는 지표: 사용자 수·재방문율 등 트래픽 성장 지표, 판매량·조회수 등 마케팅 지표, 신규 사업 출시 개수
근거 문구: "최고의 인공지능 역량을 바탕으로 의료 서비스의 질을 개선하고" / "AI가 실제 의료 현장에서 안정적이고 효율적으로 동작하도록 만드는 엔지니어링을 담당합니다" / "Latency / Throughput / GPU Memory를 고려한 추론 성능 최적화" / "GPU 자원의 효율적인 활용을 위한 Scheduling 및 Runtime 최적화" / "“어떻게 하면 AI를 더 빠르고, 안정적이고, 확장 가능하게 제품화할 수 있을까?”"

## 초안 (사람 확정 직전, 승인 안 함)
## 자기소개서

유튜브 파이프라인을 단계마다 '부서별 에이전트'로 나누자는 안이 나왔을 때, 판단 없는 공정에 감독관만 늘리는 셈이라 이득이 없다고 보고 기각했습니다 [E4]. 대신 대본 작성·검수·팩트체크처럼 판단이나 글쓰기가 필요한 칸에만 LLM을 두었습니다 [E4]. 렌더링·업로드·자막 맞추기는 코드가 맡게 했고, 음성(TTS)·이미지·음성인식 모델은 코드에서 부르는 도구로 두었습니다 [E4]. 렌더나 업로드에 판단하는 AI를 두면 비용과 실패 지점만 늘어나기 때문입니다 [E4]. 덜 '에이전트스러워' 보인다는 대가는 받아들이고, 가장 단순한 방법으로 시작해 필요할 때만 복잡도를 더한다는 원칙을 따랐습니다 [E4][E5]. 그 결과 8월 4일부터 하루 2편 돌던 코드 파이프라인을 쪼개지 않고 유지했습니다 [E5].

자동화 실패와 품질 저하 발행은 바탕화면 경고 파일과 폰 푸시로 알리게 했고, 알림이 실패해도 본 작업은 죽지 않게 했습니다 [E14]. AI 출력 형식은 흔들리기 때문에 성공 여부는 AI의 '완료' 응답이 아니라 관측 가능한 결과물로 판정합니다 [E14]. 매일 23:50에 API 비용 등 운영 기록을 공유 저장소(SQLite)로 모으며, 원본은 읽기만 합니다 [E15]. 같은 장애가 두 번 난 로그인 상태 사전 점검 기능은 우선순위가 높지만 아직 제안 단계입니다 [E14]. 이 운영 경험은 제가 설계·운영하고, 구현은 클로드 코딩 에이전트가 맡은 시스템에서 얻은 것입니다 [E16].

Agent 실행의 상태 관리와 추적은 LangChain·LangGraph를 학습하며 제 운영 시스템과 짝지어 정리했습니다 [E9][E18]. 비교해 보니 제 시스템은 중간에 죽으면 실패 알림을 받은 뒤 수동으로 다시 돌렸습니다 [E18]. 중간 재개와 병렬 처리는 제 시스템에 코드로 없던 부분이라, LangGraph로 채워야 할 부분으로 정리했습니다 [E18]. 실험으로는 읽기 도구는 자유 SQL 대신 정해진 쿼리에 날짜만 넣어 바로 실행하고, 되돌리기 어려운 쓰기 도구만 HumanInTheLoopMiddleware로 승인 뒤 실행되게 하는 에이전트를 만들었습니다 [E3][E10]. 시험용 가짜 모델로 돌려 보니 승인 전까지 DB의 paused 값은 0으로 남았고, 승인 후에야 1로 바뀌었습니다 [E10]. LangGraph의 Send로 감사 작업 3개를 동시에 돌린 뒤 합치는 규칙(reducer)으로 결과를 모아 보고서 작성 노드 하나로 넘기는 예제도 실행했습니다 [E1]. interrupt 후 재개하면 노드가 처음부터 다시 실행된다는 설명을 확인했습니다 [E2][E13]. 그래서 interrupt 앞에는 두 번 실행되면 안 되는 일을 두지 않는다는 기준을 세웠습니다 [E13]. 지금은 공고 분석부터 경력 근거 병렬 검색, 코드로 계산하는 적합도, 초안, 근거 검증, 사람 확정까지 잇는 LangGraph 기반 지원서 에이전트를 개발하고 있습니다 [E15]. 10월 23일에 첫 골격을 만들었고, 10월 27일에 실제 모델로 공고 7개를 처음 실행했습니다 [E15].

## 이력서 강조

- 판단이 필요한 칸에만 LLM을 두고 렌더링·업로드는 코드로 남겨, 비용과 실패 지점을 늘리지 않는 구조를 택했습니다 [E4]. 8월 4일부터 하루 2편 돌던 코드 파이프라인을 쪼개지 않고 유지했습니다 [E5].
- 자동화 실패와 품질 저하 발행을 경고 파일과 폰 푸시로 알리고, 성공 여부는 결과물 기준으로 판정하도록 했습니다 [E14].
- 매일 API 비용 등 운영 기록을 한 저장소로 모으고, 업로드 실패·가드 발동·수집 실패를 폰 푸시로 알립니다 [E15].
- (학습) 읽기 도구는 바로, 쓰기 도구는 사람 승인 뒤 실행되고 도구 호출은 실행당 5회로 제한되는 에이전트를 시험용 가짜 모델로 확인했습니다 [E3][E10].
- (학습) LangGraph로 병렬 실행 뒤 작성 노드 하나로 합치는 구조를 실행해 봤습니다 [E1]. 시도 2회(재생성 1회) 상한을 두고 2회째 실패하면 예비 대본으로 넘어가는 검수 루프도 실행해 봤습니다 [E6][E7].
- LangGraph 기반 맞춤 지원서 에이전트를 개발 중이며, 10월 27일에 실제 모델로 공고 7개를 처음 실행했습니다 [E15].

## 보강할 증거

- 공유 저장소에 모이는 API 비용 실제 수치(월 비용, 편당 비용)가 필요합니다. "LLM을 판단 칸에만 둬서 비용을 줄였다"를 숫자로 말할 수 있어야 합니다.
- 8월 4일 이후 파이프라인의 안정성 숫자를 모아 두면 좋습니다. 업로드 성공률, 실패 횟수, 알림이 온 뒤 복구까지 걸린 시간이 해당됩니다.
- 재생성 상한, 예비 대본 대체, fail-open, 업로드 백오프가 실제로 몇 번 발동했고 그때 서비스가 어떻게 버텼는지 사례가 필요합니다.
- 이 회사의 핵심 지표인 Latency·Throughput·GPU Memory에 대한 근거가 전혀 없습니다. vLLM 등으로 모델을 서빙하고 지연시간·처리량·메모리를 측정한 작은 실험이라도 수치로 남기면 좋습니다. 지원서 에이전트의 공고당 실행 시간과 토큰 수도 함께 기록해 두세요.
