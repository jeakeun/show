돈 버는 방식: 공고에 회사 소개가 없어 수익 구조는 불명확하다. 기존 Legacy System과 연계되는 AI Agent를 구축하는 업무로 보아, 고객사 또는 사내 기존 시스템에 LLM 기반 Agent·RAG 기술을 적용해 업무를 자동화하는 기술 구축(SI/솔루션 성격) 쪽일 가능성이 있으나 추정이다.
중요 지표: RAG 검색·답변 정확도(Chunking·Embedding·Vector 검색 품질), Agent의 작업 수행 성공률, Legacy System 연동 범위와 안정성, 업무 자동화로 줄인 처리 시간·비용
안 통하는 지표: 사용자 수·재방문 등 플랫폼 성장 지표, 판매량·조회수 등 마케팅 지표, 대규모 트래픽 처리량

## 자기소개서

공고의 'Legacy System과 연계 (Agent Action에 필요한)' 업무를 목표로, 레거시 시스템 연계 예제를 직접 실행하며 학습했습니다 [E4]. 조회 도구는 자유 SQL 대신 정해진 쿼리에 파라미터만 넣었고, 조회 범위는 최대 31일로 제한했으며, 합계 같은 숫자는 AI가 아니라 도구가 계산하도록 만들었습니다 [E5]. 자동 업로드 중지처럼 되돌리기 어려운 쓰기 작업은 사람 승인이 필요한 도구로 따로 두었습니다 [E5]. 이렇게 읽기 도구는 바로 실행하고 쓰기 도구는 승인 뒤에 실행하는 구조를 익혔습니다 [E5].

LangChain과 LangGraph는 langchain 1.4.7과 langgraph 1.2.16을 설치해 예제 코드를 실제로 실행하며 학습했습니다. 실제 모델 대신 시험용 가짜 모델과 단순 함수를 써서 구조를 확인했습니다 [E3]. create_agent에 읽기 전용 조회 도구를 붙인 에이전트를 실행했고, '사용자 질문 → AI의 도구 호출 결정 → 도구 결과 → AI 최종 답'으로 이어지는 에이전트 루프를 실행 흐름으로 확인했습니다 [E6]. LangGraph의 Send로 감사 작업 3개를 동시에 돌린 뒤 결과를 합쳐 보고서 작성 노드 하나로 모으는 예제도 실행했습니다. 이 예제로 읽기는 병렬로, 쓰기는 한 곳에서 하는 구조를 확인했습니다 [E9]. 1.0부터 LangChain의 create_agent가 LangGraph 위에서 돌아간다는 점을 정리했습니다. LangFlow가 LangChain 팀 제품이 아닌 별도 오픈소스이고 현재 IBM 소유라는 점도 함께 정리했습니다 [E2]. interrupt는 재개될 때 노드를 처음부터 다시 실행한다는 점을 설치한 버전의 설명 문구에서 확인했습니다 [E1].

RAG는 청킹·임베딩·벡터 검색을 다루는 실험을 실제로 돌려 보며 학습했습니다 [E7]. 검색 정확도를 높이는 방법으로 두 가지 기법을 정리했습니다. 하나는 벡터 검색과 키워드 검색(BM25)을 함께 쓰는 하이브리드 검색이고, 다른 하나는 넓게 20~50개를 뽑은 뒤 더 정확한 모델로 다시 순위를 매기는 재정렬입니다 [E10]. 사내 문서에는 제품 코드·약어·고유명사가 많아 키워드 검색이 중요하다는 점을 익혔습니다. 이미 Postgres를 쓰는 회사라면 pgvector를 레거시 DB 옆에 붙이기 좋다는 점도 저장소 선택 기준으로 익혔습니다 [E10]. 에이전트형 RAG의 흐름도 학습했습니다. 검색을 도구로 주고, 관련성을 채점해 부족하면 질문을 바꿔 재검색한 뒤, 검수 AI가 답의 모든 문장이 검색된 근거에 있는지 검사하는 방식입니다 [E8].

## 이력서 강조

- 레거시 연계 예제 실행: 정해진 쿼리와 파라미터, 최대 31일 제한, 도구가 숫자를 계산하는 읽기 전용 도구 학습 [E5].
- 되돌리기 어려운 쓰기 작업(자동 업로드 중지)을 사람 승인이 필요한 도구로 분리하는 구조 학습 [E5].
- LangChain create_agent 에이전트 루프(질문 → 도구 호출 결정 → 도구 결과 → 최종 답)를 시험용 가짜 모델로 실행해 확인 [E6].
- LangGraph Send로 감사 노드 3개를 병렬 실행하고 결과를 보고서 노드 하나로 합치는 예제 실행 [E9].
- RAG 청킹·임베딩·벡터 검색 실험 실행 [E7].
- 하이브리드 검색(벡터+BM25), 재정렬, pgvector 등 검색 품질 기법과 저장소 선택 기준 정리 [E10].

## 보강할 증거

- RAG 실험의 수치 결과: 청크 크기나 방식별 검색 적중률, 하이브리드 검색과 재정렬 적용 전후의 정확도 차이.
- 실제 모델로 돌렸을 때의 에이전트 작업 성공률: 도구 호출 성공·실패 비율, 실패 시 재시도로 회복한 비율.
- 레거시 연계 범위를 보여 줄 숫자: 연결한 테이블·도구 수, 잘못된 입력이나 승인 거부를 처리한 사례.
- 실제로 설계·운영한 자동화가 있다면 이를 '운영' 종류로 증명할 기록(설계 문서, 운영 로그, 줄인 처리 시간). 지금은 근거가 학습 문서뿐이라 운영 경험으로 쓸 수 없습니다.
