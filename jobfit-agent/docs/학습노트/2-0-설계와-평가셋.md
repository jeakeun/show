# 학습노트 2-0 · 설계와 평가셋 (2026-10-22)

## 오늘 한 것

1. 구조를 정했다: 공고 분석가 → 근거 검색가(병렬) → 적합도 계산(코드) → 작성자 1명 → 검증가 → 사람 확정 → 지원 이력 등록.
2. 각 칸을 왜 나눴는지 [설계 결정 기록](../DESIGN.md) J-01~J-09로 적었다.
3. 평가셋 규칙을 정하고 공고 1개(001)의 요구 항목 정답을 만들었다.

## 핵심 개념

| 개념 | 한 줄 |
|---|---|
| 기준선 (baseline) | 가장 단순한 방법(에이전트 1개가 한 번에 다 쓰기)의 성적. 이걸 이겨야 복잡하게 만든 의미가 있음 |
| 재현율 / 정밀도 | 재현율 = 있어야 할 걸 얼마나 안 빠뜨렸나. 정밀도 = 없는 걸 얼마나 안 만들었나 |
| 근거 번호 | 초안의 모든 주장에 붙는 `[E3]` 같은 표시. 검증가와 사람이 확인하는 손잡이 |
| 동적 병렬 | 공고마다 요구 항목 수가 달라서, 실행 중에 작업자 수가 정해짐 (LangGraph `Send`) |

## 정답 만들며 내린 판단

- "기타 AI Agent의 개발에 필요한 업무"는 무엇을 요구하는지 없어서 **채점에서 뺐다**. 정답이 애매한 항목을 넣으면 점수가 흔들린다.
- 스킬 줄의 "LangChain, AI Agent"는 담당·우대 줄과 겹쳐서 **합쳤다**.
- 정답 근거는 아직 비웠다. 근거로 쓸 경력 문서(`career/`)를 먼저 정해야 한다.

## 스스로 점검

<details><summary>Q1. 왜 코드보다 평가셋을 먼저 만드나?</summary>

멀티 에이전트가 나은지는 같은 문제로 잰 숫자로만 말할 수 있다. 먼저 만들지 않으면, 만들고 나서 결과에 맞춰 기준을 고르게 된다.
</details>

<details><summary>Q2. 공고 분석가를 근거 검색가와 합치면 무엇이 나빠지나?</summary>

공고를 읽으면서 내 경력도 보면, 내가 가진 경력 쪽으로 요구사항을 맞춰 읽게 될 수 있다. 공고만 보는 맥락이 따로 있어야 요구 항목을 있는 그대로 뽑고, 그 정확도도 따로 잴 수 있다.
</details>

<details><summary>Q3. 검증가가 문제를 직접 고치지 않고 지적만 하는 이유는?</summary>

검증가가 고치면 두 번째 작성자가 생겨, 누가 어떤 문장을 바꿨는지 흐려진다. 운영 중인 AI데일리에서 검수 AI가 직접 고치는 구조라 추적이 어려웠던 반성이다.
</details>
