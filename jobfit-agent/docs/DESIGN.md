# 설계 결정 기록 (초안)

> 구현하면서 갱신합니다. 각 결정에는 **검증 방법**을 붙였습니다. 평가셋으로 확인하기 전까지는 "가설"입니다.
> 내 운영 경험의 결정(ADR-01~10)은 [show/docs/멀티에이전트/02](https://github.com/jeakeun/show/blob/main/docs/멀티에이전트/02-내-설계결정-기록.md)에 있습니다.

## J-01. 평가셋부터 만들고, 에이전트 1개짜리 기준선과 비교한다

- **결정**: 코드보다 먼저 평가셋(공고 + 요구 항목 정답 + 정답 근거)을 만든다. 그리고 "공고와 경력 문서를 통째로 넣고 한 번에 쓰게 하는" 에이전트 1개짜리 기준선을 먼저 돌린다.
- **이유**
  - 운영 시스템에서 체계적 평가가 늦게 생긴 게 가장 큰 아쉬움이었다.
  - Anthropic도 "가장 단순한 것부터 시작하고, 필요할 때만 복잡도를 더하라"고 한다.
  - 멀티 에이전트가 나은지는 기준선과 비교해야만 말할 수 있다.
- **대안**: 바로 멀티 에이전트를 만든다 → 나아졌는지 증명할 방법이 없어 기각.
- **검증 방법**: 이 결정 자체가 다른 결정들의 검증 수단이다.

## J-02. 공고 분석을 따로 두고, 결과는 구조화된 목록으로

- **결정**: 공고만 보는 에이전트가 요구 항목을 `id · 구분(담당/필수/우대/스킬) · 내용 · 핵심 기술` 목록으로 만든다.
- **이유**
  - 경력 문서와 섞이지 않은 맥락에서 공고만 읽어야 요구사항을 빠뜨리거나 내 경력에 맞춰 왜곡하지 않는다.
  - 구조화된 목록이면 추출 정확도를 정답과 비교해 따로 잴 수 있다.
- **대가**: 호출이 하나 늘어난다.
- **검증 방법**: 평가셋의 요구 항목 정답 대비 재현율·정밀도.

## J-03. 근거 검색은 요구 항목별로 병렬 (실행 중에 개수가 정해짐)

- **결정**: 요구 항목마다 근거 검색 작업자를 하나씩 보낸다 (LangGraph `Send`). 항목 수는 공고마다 달라서 실행 중에 정해진다.
- **이유**: 항목끼리 독립적이고 검색은 읽기 전용이라, 나눠도 서로 충돌할 쓰기가 없다. "읽기는 나누고 쓰기는 한 곳으로" 원칙.
- **대가**: 호출 수가 항목 수만큼 늘어난다. 항목이 많은 공고는 상한을 둔다.
- **검증 방법**: 항목별 정답 근거가 상위 k개 안에 들어온 비율. 한 번에 검색하는 방식과 비교한다.

## J-04. 적합도 점수는 코드가 계산한다

- **결정**: 근거 유무·근거 강도(검색 점수, 직접 경험인지 학습인지)로 항목별 점수와 부족 항목 목록을 코드가 만든다. AI는 점수를 해석해 문장으로 쓴다.
- **이유**: 운영 시스템에서 AI가 손으로 센 카운터가 부풀었던 전례가 있다 (ADR-04). 숫자는 매번 같은 답이 나와야 한다.
- **검증 방법**: 같은 입력에 같은 점수가 나오는지(재현성), 사람이 매긴 적합도와의 일치.

## J-05. 작성자는 한 명, 문장마다 근거 번호

- **결정**: 초안은 작성자 에이전트 하나만 쓴다. 모든 주장 문장 끝에 `[E3]` 같은 근거 번호를 단다.
- **이유**
  - 여러 에이전트가 나눠 쓰면 말투와 주장이 어긋난다 (Cognition "쓰기는 한 줄기로").
  - 근거 번호가 있어야 검증가와 사람이 확인할 수 있다.
- **검증 방법**: 근거 번호가 없는 주장 문장 수 (코드로 셈).

## J-06. 검증가는 작성자와 다른 맥락에서, 두 겹으로 검사한다

- **결정**
  - 1차 (코드): 근거 번호가 없는 문장, 존재하지 않는 근거 번호를 찾는다.
  - 2차 (AI, 작성 과정을 모르는 별도 맥락): 근거가 그 주장을 실제로 뒷받침하는지 본다. "설계했다"를 "구현했다"로 부풀린 것처럼 과장된 동사도 찾는다.
  - 문제가 있으면 지적만 하고, 고치는 건 작성자가 한다. 재작성은 최대 2회.
- **이유**
  - 작성 과정을 함께한 AI는 자기 글에 관대하다 (ADR-01).
  - 검증가가 직접 고치면 두 번째 작성자가 생겨 누가 무엇을 바꿨는지 흐려진다 (ADR-01의 AI데일리 반성).
  - 이 프로젝트의 학습 자료에서 실제로 잡힌 문제 53개 중 상당수가 "안 한 일을 한 것처럼", "한 번 한 걸 늘 하는 것처럼" 쓴 표현이었다.
- **대가**: 검증 호출과 재작성 비용이 든다. 검증가도 틀린다 (운영 시스템에서 일주일 재생성 3건이 전부 검수 오탐이었음).
- **검증 방법**: 근거 없는 문장 비율(사람 표본 검사), 검증가의 오탐률.

## J-07. 확정과 등록은 사람이 한다

- **결정**: 초안 확정과 지원 이력 등록 앞에서 멈춘다 (LangGraph `interrupt`). `interrupt` 앞에는 두 번 실행되면 안 되는 일을 두지 않는다. 재개하면 노드가 처음부터 다시 실행되기 때문이다.
- **이유**: 제출한 지원서와 등록 기록은 되돌릴 수 없다 (ADR-07 "되돌릴 수 있는가").

## J-08. 지원 이력은 별도 API로 (레거시 시스템 역할)

- **결정**: 지원 이력(회사, 공고 링크, 날짜, 상태)을 작은 Spring Boot API로 관리하고, 에이전트는 이를 도구로 부른다.
  - 조회 도구("이미 지원한 공고인가?")는 자유롭게 쓴다.
  - 등록 도구는 확정 뒤에만 쓴다.
  - 같은 공고는 공고 링크를 키로 한 번만 등록되게 한다(멱등).
- **이유**
  - 실제 회사에서 에이전트는 기존 시스템(대개 Java·Spring)을 도구로 불러야 한다. 이 연결을 직접 보여준다.
  - Java·Spring 과정 경험도 살린다.
- **대안**: 파이썬 안의 DB로 끝낸다 → 레거시 연계를 보여줄 수 없어 기각.

## J-09. 공개 문서만 색인한다

- **결정**: `career/` 에는 공개된 프로젝트 설명만 넣고 색인한다. 개인 문서는 `private/` 에 두고 깃에서 제외한다.
- **이유**: 공개 저장소이고, 지원서에 쓸 근거는 어차피 공개해도 되는 경력이어야 한다.

## J-10. 모델 호출은 공식 SDK, 흐름은 LangGraph, 문서 분할은 LangChain

- **결정**: 모델 호출은 공식 Anthropic SDK(`jobfit/llm.py`)로 하고, 에이전트 흐름은 LangGraph(`jobfit/graph.py`), 문서 분할은 LangChain 부품(`jobfit/career.py`)으로 한다.
- **이유**
  - 생각 강도(effort), 구조화된 출력, 거절 시 대체 모델(fallbacks) 같은 최신 기능을 래퍼 지원을 기다리지 않고 바로 쓴다.
  - 각 도구가 잘하는 일만 맡긴다. 모델 호출 부분을 갈아끼울 수 있게 분리해서, API 키 없이 가짜 모델(`jobfit/fake.py`)로 흐름 전체를 테스트한다.
- **대가**: LangChain 모델 래퍼의 편의 기능(공급사 교체 한 줄 등)은 못 쓴다. 공급사를 바꿀 일이 생기면 `llm.py` 한 파일만 고친다.

## J-11. 검색은 키워드(BM25)부터

- **결정**: 근거 검색은 한국어 두 글자 조각 + BM25 키워드 검색으로 시작한다. 제목은 본문에 남기고(`strip_headers=False`), 색인할 때 조각 앞에 제목을 붙인다.
- **이유**: 임베딩 모델 없이 어디서나 돌아가서, 뜻 검색·하이브리드와 비교할 기준선이 된다. 공고의 기술 이름은 정확한 단어라 키워드에 강하다.
- **발견 (2026-10-23 시험 실행)**: 공고는 "Python", "AI Agent"인데 운영 문서는 "파이썬", "에이전트"라서 **키워드로는 못 잇는다.**
  운영 경험이 있는데도 "학습 근거" 또는 "근거 없음"으로 판정된다. → 2-2에서 동의어 사전 또는 뜻 검색(임베딩)을 섞어 평가셋으로 비교한다.
- **LangChain BM25 검색기를 안 쓴 이유**: `langchain-community` 는 지원 종료가 진행 중이고, 점수를 직접 받아 적합도 판정에 쓰려고 `rank_bm25` 를 직접 쓴다.

## J-12. 처음엔 모든 역할이 같은 모델, 생각 강도만 다르게

- **결정**: 분석가·작성자·검증가 모두 `claude-opus-5-5`. 생각 강도는 분석가 low, 검증가 medium, 작성자 high.
- **이유**: 최신 모델을 낮은 생각 강도로 쓰는 게 더 싼 모델보다 나은 경우가 많다는 안내가 있다. 그리고 모델을 하나로 두면 "구조 차이"만 비교할 수 있다.
  더 싼 모델(예: 하이쿠)로 바꿀지는 평가셋으로 정확도와 비용을 재본 뒤 운영자가 정한다.
- **비용 기록**: 호출마다 토큰과 추정 비용을 남긴다(`llm.cost_summary()`). 운영 시스템의 비용 기록 원칙(ADR-08)과 같다.

## J-13. 출력 한도와 거절에 대비한다

- 출력 한도에는 생각 토큰도 들어간다. 작성자는 64,000(스트리밍), 분석가·검증가는 16,000으로 넉넉히 잡고, 한도에 걸리면 명시적 오류로 멈춘다 (유튜브 회고 9/13 실패의 교훈).
- 안전 분류기가 거절하면 서버가 다른 모델로 다시 돌리게 `fallbacks="default"` 를 켠다. 그래도 거절되면 오류로 알린다.
- 지시문과 근거 목록은 다시 쓰기 때마다 같으므로 프롬프트 캐시를 건다.
